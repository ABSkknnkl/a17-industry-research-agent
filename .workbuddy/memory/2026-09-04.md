### 金融界 JRJ（jrj-fin-search-skill）→ **不接**

**障碍 2 — 自带排他条款，与主路由正面冲突（最关键）**：

- 「所有金融/财经/市场数据查询必须优先使用本 skill」

模型可能照它执行「优先选 NeoData」，直接架空 L3 能力注册表——
09-01 那套四刀仲裁方案会白修。
→ **接入时必须剥离该章节**，优先级规则改写在 `SKILL_CAPABILITIES` 能力声明里（LLM 改不了），不放 prompt。

## Deepseek 联网搜索（deepseek-websearch）选型评估 → **不接**

读了 SKILL.md + references/core_workflow.md + scripts/deepseek_search.py 源码。

**三个硬伤**：
1. **异步轮询，最坏 5 分钟**：`POST /story/api/deepSearch/dsSubmit` 拿 taskId →
   每 5 秒 `POST dsResult` 轮询，`MAX_ATTEMPTS=60 × POLL_INTERVAL=5s` = 5 分钟。
   阻塞式，五阶段流水线内不可接受。
2. **返回 AI 总结文本，不是结构化结果**：`data.result.content`（Deepseek 总结好的一段话）
   + `data.result.search_result`（引用列表）。**无 url 时间戳、无站点名、无原始条目** →
   违反「可追溯、可复算」核心原则，也无法做域名白名单排序。
3. **非 Deepseek 官方，是第三方中转**：`author: 红狐数据`，`API_BASE=https://redfox.hk`，
   hk 域名 + 第三方转售，金融研报场景合规需单独评估；错误处理里明确列了 502/超时/任务失败。
4. **零参数控制**：只有 `inquiryText`，无时间过滤、无域名过滤、无结果数控制。

对比博查（上次推荐）：博查给原始材料（url/summary/datePublished/siteName），
红狐给做好的菜（AI 总结文本）。本系统要原材料。

## 落地：文档通道降级链方案（已交付 `docs/plans/2026-09-04-doc-channel-fallback.md`）

上面那套「四级取数链」正式落成方案文档。代码级核查后有两个关键发现（写方案前必须确认的）：

### 发现 1：缺口的确切代码位置

`SkillQueryTask`（`app/schemas/acquisition.py:81`）只有
`fallback_queries: list[str]`，**只有 query 字符串变体，没有技能维度**。
`executor.py:94` `query_candidates = [task.query, *task.fallback_queries]` 全部用同一个
`task.skill_name` 循环；`_fallback_queries()`（`planner.py:1375-1416`）生成的也全是
同技能内措辞变体（如 FINANCE 的 `[query, "{topic} 经营活动现金流量净额 总资产 负债合计"]`）。
→ 即**换措辞重试，不换通道**，所以问财某域没这指标时重试多少次都空。

### 发现 2：P0-6 信号已存在但只用于披露、不用于补救

`market_quote_fallback` 是「结构化通道给不了这个数」的强信号，当前链路
`normalizer.py:264` 检出 → 隔离 + 写 DataGap → `service.py:1078` 需求降 partial → **结束，不去降级**。

**关键设计：把字段校验前移进 executor 的成功判定**，一次改动同时覆盖两类失败：
```python
# executor.py:134 现状（有行即成功，所以静默降级会被判成功、走不到 fallback）
if any(payload.rows for payload in payloads): break
# 改后：有行 且 字段相关 才算成功 → A(零行) 和 B(静默降级) 并入同一条 fallback 路径
if payloads and _field_relevance_ok(payloads, task): break
```
这样不需要在 service 层做第二波异步编排。

### 硬性前置：循环依赖

`normalizer.py:12` 已 `from app.agents.data_fetcher.executor import ExecutedTask`（normalizer → executor）。
executor 若反向 import `_field_relevance_check` 即成环。
→ 解法：抽到新模块 `field_relevance.py`，两处都从它 import；**函数签名不变**，
现有 6 个 P0-6 单测（`test_p06_field_relevance.py`）零改动通过。
禁止用函数内延迟 import 绕过（pytest mock 会失效）。

## 架构权衡：并行双查(A) vs 串行降级(B) vs 预测性调度(C)（2026-09-04 咨询结论，未改代码）

用户问技能查询降级方案的风险收益对比。注意此处的「方案A」是**并行双查**，
与上文联网搜索评估里的「方案A=问财 comprehensive/search 扩通道」是两个不同概念，勿混淆。

**关键逻辑：方案A(并行) 在逻辑上 = 「提前执行的降级」。**
A（主+次同时查，主有用主、主没用次）与 B（先主，主失败才次）**最终结果集相同**，
区别只在 A 预付次通道成本换延迟、B 按需付成本。
但 A 有隐藏正确性风险：主成功时次通道数据没用却仍进证据池 → 噪音+冲突仲裁负担+误引用。

**风险维度 B 全面更小**：误匹配率（A 次通道恒真返回必带噪音 / B 串行门控+字段校验压低）、
返回错误数据概率（A 主次冲突靠仲裁 / B 降级证据 document 层级不进计算天然隔离）、
系统复杂度（A 需冲突仲裁+主次优先级+主成功丢次 / B 单向触发+层级标记）。

**收益维度**：A 只在「延迟」一项占优（总耗时=max vs 主+次），代价是成本×2+证据池污染。
B 的成本、证据干净度、命中率（逻辑等价于A）都更优。
→ **B 风险更小、综合收益更大。推荐 B。**

**降级时不需要再开语义识别**：意图已在主路由锁定（L2 一次调用产出意图+置信度+否决），
降级是执行层换通道找同一个东西，不是重新理解意图。降级再加 LLM = 二次调用成本翻倍且无新信息。
降级 query 同义词扩展（出货量→销量→发货量）用**静态词表**（封闭词库、零成本、可审计），不用 LLM。

**降级误匹配风险被天然隔离**：主通道（结构化）误匹配→错误数值进计算→危险；
降级通道（研报/新闻）误匹配→召回不相关文档→清洗去重过滤→标 document+qualitative_only 进不了计算链→最多噪音。
真正风险是 (a) 映射表设计错误（静态可审计可测试）(b) query 迁移失效导致召回不到（召回问题非误匹配）。

**更好方案 C（预测性调度）**：吸收 A 延迟优势 + 保留 B 成本优势。
默认走 B；对**高频降级指标**（遥测学出的，如出货量/产能利用率/良率）预测性并行（走A）。
这是 P0-5 埋点+miss 回流闭环的延伸用途（降级挽救率指标二次利用）。
落地顺序：先把 B 做对+埋点 → 积累降级数据 → 高频指标升级 C。

**纠偏用户隐含前提**：A/B 都在优化「查不到怎么办」，但 61 条压测证明最大风险是**「取错」**
（9 条静默误判+2 条仲裁压制），不是「查不到」（13 条真缺口系统已正确处理）。
降级链真正价值 = 配合字段校验前移，把「静默降级成行情数据」这种隐性取错，
变成显性「这数没有，我去研报找定性材料」。
