## 评分体系设计方案（已产出文档）

产物：`output/交付质量评分体系设计方案.md`

### 新增关键发现

**A. `analyzability_score` 结构性虚高（engine.py L398-402）**
```python
completeness = min(1.0, len(numeric)/20)   # 权重 0.35，20 条即封顶 → 恒 1.0
source_score = min(1.0, source_count/3)    # 权重 0.25，3 个来源即封顶 → 恒 1.0
score = 0.35*completeness + 0.3*time_score + 0.25*source_score + 0.1*(1-issue_penalty)
```
已用本次数据验算吻合（0.972078）。**60% 权重白送，结构性下界 = 0.60**，永远不可能低于 60 分。

**B. `data_quality_appendix` 前后端字段完全错位**
- 后端实际产出：`sample_info` / `outlier_items` / `conflict_items` / `non_extrapolation_disclaimers`
- 前端 `ReportQualityAppendix`（types.ts）定义：`data_quality_issues` / `dimension_coverage` /
  `financial_consistency_checks` / `skipped_chart_notes`
- **四个字段无一对应**；且该字段根本没被塞进 report_fusion 的 data（adapters.py L1026-1053）

**C. `outlier_items` 只有 12 条（非 75 条），且每条带 `treatment`**
"单独列示并剔除，不纳入横向基准中位数计算" → 说明系统**已妥善处理**。
→ 这证明「异常检出」是尽责行为而非缺陷，**绝不该扣分**，只能披露。

### 上一轮口径需撤回
"证据引用率 60/502 = 12% vs evidence_coverage 1.0" 的对比**不严谨**：
60/502 的分母（阶段二证据池）不能作为质量分母——采集越多分越低，是反向激励。
正确替代口径 = 证据支撑率（有证据段落/总段落 = 95/98 = 96.9%）。

### 方案核心：三分法
1. **交付完成度**（计分）：结构完整度 0.3 + 证据支撑率 0.4 + 编辑通过率 0.3
2. **数据可信度**（计分）：可分析性 0.35 + 记录质量合格率 0.3 + 时间覆盖 0.2 + 来源多样性 0.15
3. **风险与局限披露**（**不计分**）：已处理离群项 / 数据缺口 / 未消解冲突 / 样本边界 / 生成警告

用户所列 6 项判定：引用率❌（口径错）· 无证据段落✅ · 数据异常❌（反向激励）·
质量问题记录✅ · 可分析性⚠️（需先修算法）· 编辑通过率✅（建议新增）

### 设计原则
- 数据质量 ≠ 交付质量，必须分开计分（责任主体不同，混在一起用户无法归因）
- 系统主动发现的异常**不扣分**（否则系统学会少报异常）
- 分数必须能归因（列出具体扣分项，可定位到段落/指标）

### 实施顺序
P0：`passed`/`issues` 接 `result.consistency` + `delivery_status` 透传真实值 + 计数字段改真实统计
P1：新增三分结构 + 修 `analyzability_score` 封顶 + 透传 `data_quality_appendix` + 重写前端类型
P2：`QualityPanel.vue` 双分 + 披露区改造 + 补测试
