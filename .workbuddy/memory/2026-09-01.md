## 问财数据可得性实测（出货量/产能利用率）— 真实接口，非推断

- 探测方式：直接用 `IwencaiSkillClient` + `.env` 真实 Key 打 8 组查询（脚本 /tmp/probe_skill.py，已用即弃）。
- **核心发现：问财没有公司级（个股）出货量/产能利用率结构化字段**。
  `hithink_business_query` 查"隆基绿能组件出货量"/"隆基绿能 销量"会**静默回退行情数据**
  （返回列 = 最新价/涨跌幅/成交量/换手率/大单卖出量），行数 > 0、能过清洗、能进证据池
  → Agent 2 会误当"查到了出货量"。**这比空返回危险**：空返回会被 data_gaps 披露，静默降级不会。
- 问财**有产业级（行业/宏观）数据**：
  - `hithink_industry_query` "光伏组件行业产量 产能" → `光伏组件:产量:合计` 725,900 兆瓦（年度）
  - `hithink_industry_query` "光伏组件行业产能利用率" → `光伏利用率:全国:当月值` 月度序列
    （2025-09~2026-01：95.0/94.8/93.7/94.6/94.3，%）→ **口径陷阱**：这是发电侧消纳利用率，
    不是制造业产能利用率，指标名相似语义不同。
  - `report_search` "隆基绿能 组件出货量" → 10 条研报命中（公司级数据只能走研报/公告定性通道）
  - `industry_chain_analysis` "光伏组件产业链" → 7 行（业务收入/成本/利润占比 + 行业数据）
  - `hithink_basicinfo_query` "隆基绿能产能" → 0 行
- **结论对方案的影响**：出货量/产能利用率的 `primary_skill` 应注册为 `INDUSTRY`（行业级口径），
  不能是 `BUSINESS`；公司级需求降级路径 = industry_query（须带口径标签）+ report_search/announcement_search。
- 已把该隐患作为 **成因 D** 与 **P0-6（字段相关性校验 `_field_relevance_check`）** 补进
  `docs/plans/2026-08-31-agent1-routing-fix.md`（P0 从 5 项变 6 项）。

### 「改用 LLM 主导能否解决这些 bug」的结论（架构判断）

用户问是否应以 LLM 主导路由。结论：**能解决语义类（12 条），解决不了契约/数据类（7+13 条）；
且真正瓶颈不是"谁主导"，而是 LLM 没有否决权。**

- **代码事实（关键）**：`intent_merger._merge_llm_plan` 第 368 行 `if not valid_skills: continue`
  —— LLM 输出空 candidate_skills 时被直接跳过，**无法否决**；第 477-485 行
  `locked_skill_missing_after_merge` 又把确定性 locked 强制补回 `subs[0]`。
  ⇒ 确定性锁定**永远生效**，LLM 只能补充不能否决。这既是 P0 静默误判（7 条）也是
  关键词误锁（F02/B10）的根因。**只换主导权重而不改这两处 = 无效。**
- **分层结论**：语义理解类 12 条（静默误判 5 + 关键词误锁 2 + 节奏偏移 5）换主导/给否决权可解；
  契约类 7 条（词表 5 + 口径 2）LLM 只能解决"识别"，`query_fields` 仍来自 registry，必须补表；
  数据与机制类 13 条真缺口与主导权无关，**LLM 主导反而更危险**（乐观路由把缺口罩成"查到了"）。
- **反直觉点**：过度阻塞 23 条的根因是置信度阈值策略（0.75/0.90），**换 LLM 主导不会自动解决**。
- **建议（非"LLM 全权主导"）**：LLM 语义优先 + 确定性契约兜底 + **LLM 拥有否决权**。
  改 3 处：① 允许 `candidate_skills=[]` + `intent_type="analysis_only"` 显式否决并移除 locked；
  ② `locked_skill_missing_after_merge` 仅在未显式否决时补回；③ 落实
  `clarification_should_be_advisory` 为真正不阻塞。预期干净通过 20 → 40+，
  12 条静默误判转为"正确识别为不可查"（质改善，消除错误结论）。
