## 一、结论摘要

1. 当前"交付质量评分 100"是 `adapters.py` L1038-1047 硬编码的产物，不代表质量（详见上一轮审计）。
2. 用户列出的 6 个真实信号，**只有 3 个适合进评分**；另外 3 个不进评分有充分理由。
3. 核心设计变更：**从一个总分拆成「交付完成度」+「数据可信度」两个独立分，另设一个不计分的「风险与局限披露」区**。
4. 有两处必须先修的底层问题，否则新体系也会失真：
   - `analyzability_score` 算法结构性下界 0.6（60% 权重白送）
   - 后端 `data_quality_appendix` 与前端 `ReportQualityAppendix` 类型字段完全对不上

## 二、必须先纠正的一个口径错误

上一轮审计中，我把"证据引用率 60/502 = 12%"与 `evidence_coverage: 1.0` 并列对比，暗示 1.0 虚高。**这个对比本身不严谨，需要撤回。**

原因是三个数字量的根本不是一回事：

| 口径 | 计算 | 本次值 | 含义 |
|---|---|---|---|
| 采集入库证据数 | — | 502 | 阶段一/二入库的证据总量 |
| 正文引用 / 入库总量 | 60 / 502 | 12.0% | **不是质量指标** |
| 有证据段落 / 总段落 | 95 / 98 | 96.9% | 报告的自证程度 |

**为什么 12% 不能当质量指标**：一个行业研究任务采集 1015 条记录、入库 502 条证据，正文引用 60 条是完全正常的——报告不可能引用全部采集数据。如果拿它打分，会出现**采集越充分、分数越低**的反向激励，逻辑上就是错的。

另外，`report_view.json` 里报告级 `evidence_catalog` 实际只有 **68 条**（不是 502），说明"502"这个分母是阶段二的证据池，用它做分母从一开始就不成立。

**正确替代**：用「证据支撑率」= 有证据的段落 / 总段落。这才是用户真正关心的——"报告里的结论有没有据可查"。

## 三、设计原则

### 原则 1：数据质量与交付质量必须分开计分

数据是外部给的，报告是自己做的。二者的责任主体不同：

- 数据源缺期末日期 → 不是系统做错了，是数据本身如此
- 如果混进同一个分，用户看到 82 分时**无法归因**——是系统没做好，还是数据本身就差？

分开后，用户能读到「完成度 96 / 数据可信度 92」这种可解释的组合。

### 原则 2：系统主动发现的异常，不扣分

这是最关键的一条。异常检测是**尽责行为**，不是**犯错行为**：

> 如果"检出 75 条异常"导致扣分，那么系统学会的第一件事就是**少报异常**。指标会立刻变好看，但产品失去意义。

所以离群值、时序突变这类"发现的问题"只能**披露**，不能**计分**。

但要区分两类东西：

| 类型 | 性质 | 处理 |
|---|---|---|
| 离群值、时序突变 | 检测发现的现象（且多已处理） | 披露，不计分 |
| 记录质量缺陷（missing_period_end） | 输入数据的客观缺损 | 计入数据可信度 |

### 原则 3：分数必须能归因

用户要的不是一个数字，而是"**我该注意什么**"。所以：

- 每个分数下必须列出**具体扣分项**（哪一段、哪个指标、建议怎么处理）
- 单一条目的问题（如 3 个无证据段落）要能定位到段落 ID

## 五、目标维度体系

### 5.1 总分结构

```
┌─ 交付完成度 (Delivery Completeness)        计分 0-100
│    我们做的：结构、证据、编辑质量
├─ 数据可信度 (Data Reliability)             计分 0-100
│    数据给的：可分析性、记录质量、时间覆盖
└─ 风险与局限披露 (Disclosures)              不计分，只展示
     发现的问题 + 适用边界
```

### 5.2 交付完成度（计分）

| 子项 | 计算式 | 本次 | 权重建议 |
|---|---|---|---|
| 结构完整度 | 实际章节/小节 ÷ 应有章节/小节 | 7/7 · 21/21 = 100 | 0.30 |
| 证据支撑率 | 有证据段落 ÷ 总段落 | 95/98 = 96.9 | 0.40 |
| 编辑通过率 | accepted_edits ÷ (accepted+rejected) | 12/13 = 92.3 | 0.30 |

> 变更点：`chapter_count` / `section_count` 改为**从 `outline_chapters` 实际长度统计**，不再写死。
> 证据支撑率替代原 `evidence_coverage`，口径明确写进 UI 提示。

### 5.3 数据可信度（计分）

| 子项 | 计算式 | 本次 | 权重建议 |
|---|---|---|---|
| 数据可分析性 | `analyzability_score`（修正后） | 97.2 | 0.35 |
| 记录质量合格率 | 1 − `records_with_issues`/`record_count` | 31/1015 → 96.9 | 0.30 |
| 时间序列覆盖 | `dated_numeric`/`numeric` | 520/567 = 91.7 | 0.20 |
| 来源多样性 | min(1, source_count/3) | 7 个 → 100 | 0.15 |

> 加权后本次 ≈ 96.0。注意这里的"来源多样性"同样有封顶问题（见第六节）。

### 5.4 风险与局限披露（不计分）

| 区块 | 数据来源 | 呈现 |
|---|---|---|
| 已处理离群项 | `outlier_items`（12 条） | 中性色，标注"已剔除并单独列示" |
| 数据缺口 | 阶段二 `data_quality` kind 异常（31 条） | 提示色，标注具体缺失字段 |
| 未消解冲突 | `conflict_items`（0 条） | 为空则不显示 |
| 样本边界 | `non_extrapolation_disclaimers`（3 条） | 常驻显示，不可折叠 |
| 生成警告 | `report_view.warnings`（2 条） | 提示色 |

**这一区不显示任何分数**，只用"已处理 / 需注意"两级标记。

## 六、必须先修的两个底层问题

### 6.1 `analyzability_score` 结构性虚高

`agents_core/data-analysis/data_interpreter/engine.py` L398-402：

```python
completeness = min(1.0, len(numeric) / 20)      # 权重 0.35
time_score   = dated / len(numeric)             # 权重 0.30
source_score = min(1.0, source_count / 3)       # 权重 0.25
issue_penalty= issue_count / len(records)       # 权重 0.10
score = 0.35*completeness + 0.3*time_score + 0.25*source_score + 0.1*(1-issue_penalty)
```

用本次数据代入（已验算，与报告值 0.9720780879 完全吻合）：

```
completeness = min(1, 567/20) = 1.0   ← 20 条数值记录就封顶
source_score = min(1, 7/3)    = 1.0   ← 3 个来源就封顶
       ↓ 0.35 + 0.25 = 60% 的权重是白送的
score = 0.35*1.0 + 0.30*0.9171 + 0.25*1.0 + 0.10*0.9695 = 0.972
```

**极端情况验算**：即使 `time_score=0`、`issue_penalty=1`（全是坏数据），分数仍是 **0.60**。
即该指标实际取值区间是 **[60, 100]**，永远不可能低于 60 —— 结构性不可信。

**修正建议**（择一）：

- **方案 A（最小改动）**：提高封顶阈值。`numeric/20` → `numeric/200`；`source_count/3` → `source_count/5`。让大样本任务不再自动满分。
- **方案 B（推荐）**：改为**分档达标制**，每项只有达标/不达标，不达标按缺口比例扣：
  ```python
  def _band(value, target):
      return min(1.0, value / target) if target else 0.0
  completeness = _band(len(numeric), 200)
  ```
  并确保 `score` 能落到 0。
- **无论选哪个**，UI 上要把 4 个子项**分别展示**，让用户看到是哪一项在扣分，而不是只给一个 0.972。

### 6.2 前后端质量附录契约错位

后端 `report_view.json → data_quality_appendix` 实际产出：

```
sample_info, outlier_items, conflict_items, non_extrapolation_disclaimers
```

前端 `frontend/src/api/types.ts` 的 `ReportQualityAppendix` 定义：

```
data_quality_issues, dimension_coverage, financial_consistency_checks, skipped_chart_notes
```

**四个字段无一对应。** 前端类型是照某个早期契约写的，后端后来换了结构，两边都没同步。

同时 `data_quality_appendix` 根本没被塞进 report_fusion 的 `data`（`adapters.py` L1026-1053 的 `data` 字典里没有），所以前端拿不到。

**修正**：以实际产出为准重写前端 `ReportQualityAppendix`，并在 `adapters.py` 中透传该字段。

## 八、前端呈现建议

### 8.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│ 交付质量与融合检查              [ready_with_limits] MARKDOWN…│
├──────────────────────┬──────────────────────────────────────┤

│  数据可信度           │                                       │
│                      │  数据可信度                           │
│                      │   数据可分析性    ███████▊  97%       │
│                      │   记录质量合格率  ███████▊  97%       │
├──────────────────────┴──────────────────────────────────────┤
│ 风险与局限披露（不计分）                                      │
│  ✓ 离群项 12 项已剔除并单独列示        [展开]                 │

│  i 样本适用边界 3 条                   [展开]                 │
└─────────────────────────────────────────────────────────────┘
```

### 8.2 呈现原则

1. **两个分数用并列环形/条形**，标签必须写清"交付完成度""数据可信度"，不要让用户以为是一个综合分。
2. **每个分数下直接列子项**（含 detail），不做二次点击 —— 归因要一眼可见。
3. **披露区用中性/提示色**，不用红黄绿的分数色阶，视觉上明确区别于计分区。
4. `delivery_status = ready_with_limits` 时，标题旁显示显著但不刺眼的标记（如 `el-tag` warning），并在披露区首行说明原因。
5. **移除**现有的"前端聚合口径：章节/结构/覆盖率均值"这行说明 —— 改成"各维度独立计分，不合并为单一总分"。

## 九、兼容与迁移

`quality` 结构变更会影响 `QualityPanel.vue` 与 `ReportQualityReport` 类型，建议：

1. **保留旧字段**：`passed`、`chapter_count`、`section_count`、`expected_*`、`included_chart_count`、`evidence_coverage`、`issues` 继续下发（但改为真实值），供历史 run 与旧前端渲染。
2. **新增结构与旧字段并存**：前端优先读 `delivery` / `data_reliability` / `disclosures`，缺失时回退旧字段（`QualityPanel` 已有回退模式，`BASELINE_FALLBACK` 可复用）。
3. **不要引入新的顶层字段名**（如 `quality_v2`），避免前端要判断两套结构。
4. 前端 `ReportQualityAppendix` 按第六节 6.2 重写；`data_quality_appendix` 需要先在 `adapters.py` 里透传进 `data`。
