## 一、必须修正的三处

### 1.1 本项目 combo **不弱** —— 迁入同花顺的收益要重新定位

原方案对照表写"combo 双轴：本项目弱（compiler 有 dual_axis_combo）"。实测 `compiler.py:113 _compile_combo`：

```python
# 已实现的能力
- 双 Y 轴：y_axis_1 / y_axis_2，各自 "name": unit1 / unit2（单位已披露）
- 系列组合：series[0] bar 走左轴、series[1] line 走右轴
- 零轴对齐：if min1 < 0 or min2 < 0 → 强制 min ≤ 0（见 L148-151）
- 退化保护：第二系列缺失或与第一系列同名 → 回落 _compile_bar，避免重复线
```

**即：双轴 combo 本项目已经能做，且带单位与零轴对齐。**

**真正的缺口是另外几项**，迁入价值应改挂在这些上面：

| 能力 | 本项目 | 同花顺 | 是否迁入 |
|---|---|---|---|
| **dual_panel 双面板**（左右分区，非同轴） | ❌ 完全没有 | ✅ `build_dual_panel_option`（按 `dataset.panels[].position` 分 left/right） | ✅ **迁** |
| **标注能力**（参考线 / 数据标签密度） | ⚠️ 仅 `_compile_scatter` 里有 `markLine`，而该分支将删 | ✅ `reference_line` / `_auto_datalabel`（`DATALABEL_MAX_POINTS = 12`） | ✅ **迁** |
| **主题色板** | ✅ 已有出版级 `PALETTE`（见 §1.4） | ⚠️ 行情风格 `THEMES` | ❌ **不迁色值** |
| **涨跌语义色** | ✅ 本无此概念（见 §1.4） | ⚠️ `UP_COLOR` / `DOWN_COLOR` | ❌ **不迁** |

**结论**：P2 的收益描述应为「**补 dual_panel + 引入标注能力**」，而不是「补双轴 + 迁主题/涨跌色」。这同时降低了对 `build_combo_option` 的迁移优先级——它可选择不迁（本项目已有）。

### 1.2 P1 与 P2 内部矛盾 —— 应改为"移植 schema"

- **P1 说**：输出"与 THS 同构的轻量结构（**不必强绑** pydantic `ChartDataset`）"
- **P2 要迁的 builders**：签名全部是 `(title: str, dataset: ChartDataset, theme: str = "research_blue")`

实测 `builders.py` 内部直接读写 `dataset.points` / `point.period_end` / `point.label` / `point.series` / `dataset.panels` / `panel.position` / `dataset.currency` / `dataset.unit` / `dataset.metric_name` / `dataset.series_meta`。

**若坚持"轻量结构"**，就必须改造全部 builder 的内部实现（8 个函数、1484 行），风险远高于移植模型。

**修正**：P1 改为**直接移植 schema**，这样反而更省事：

```
新增 agents_core/chart-generator/chart_generator/ths_schema.py
├── ChartPoint        （label, value, series, period_end, value_kind, evidence_id）
├── ChartSeriesMeta   （name, unit, currency, render_as: bar|line）
├── ChartPanel        （position: left|right, ...）
└── ChartDataset      （见 §1.3 收窄后的版本）
```

**额外收益**：`ChartPoint.evidence_id = Field(min_length=1)` 是**必填**——移植 schema 天然满足 P1 想要的"点级 evidence 必填"目标，不需要额外设计。

---

### 1.3 `ChartDataset.kind` 携带下排 6 种类型 —— 应从数据契约层面收窄

同花顺原版：

```python
kind: Literal["time_series","categorical","industry_chain","xy","matrix","distribution","hierarchy"]
# 以及配套字段：
xy_points / matrix_cells / distribution_samples / hierarchy_nodes / nodes / edges / chain_template_hint
```

`industry_chain` / `xy` / `matrix` / `distribution` / `hierarchy` 恰好对应下排 6 种图（scatter / bubble / heatmap / boxplot / treemap / industry_chain）。

**若整体移植，等于把禁用类型的数据通路一起搬进来**，只靠上层 `normalize_active_chart_type` 拦截，属于"门禁单点"。

**修正 —— 移植时收窄**：

```python
kind: Literal["time_series", "categorical"]     # 只留能产出六图的两种
# 删除字段：xy_points / matrix_cells / distribution_samples
#           hierarchy_nodes / nodes / edges / chain_template_hint
# 删除类型：XYPoint / MatrixCell / DistributionSample / HierarchyNode / ChainNode / ChainEdge
```

收益：**禁用类型在数据层就没有表达能力**，`chart_type_not_enabled` 从“拦截”变成“不可能构造”。这比 P5 的“删调用路径”更彻底。

### 1.4 配色体系：两个项目**不同源**，涨跌语义色不应迁入

> **本节推翻本文档上一版与外部方案的判断。** 原建议是“迁入主题/涨跌色，并保持涨红跌绿（中国惯例）”。实测后确认：这个建议**不成立**——错在把“行情图表”的视觉惯例套到了“行业研究报告”上。

两个项目的配色是**为不同目标设计**的：

**本项目 —— 行业研究出版级**

```python
# compiler.py L44-50 与 render.py L11-18
PRIMARY_COLOR   = "#155eef"   # Financial Blue
SECONDARY_COLOR = "#0f766e"   # Deep Teal
ACCENT_COLOR    = "#d97706"   # Gold / Amber
NEGATIVE_COLOR  = "#d92d20"   # Muted Red —— 注释是 "Risk / Deficit"，不是“涨”
PURPLE_COLOR    = "#6941c6"
CYAN_COLOR      = "#0891b2"
PALETTE = [PRIMARY, SECONDARY, ACCENT, PURPLE, CYAN, NEGATIVE]
```

- **无 `UP_COLOR` / `DOWN_COLOR`，`PALETTE` 里没有绿色**
- `NEGATIVE_COLOR` 的语义是**风险/赤字**，不是“下跌”
- 唯一处理正负值的地方 `_compile_diverging_bar`（L219-228）：

  ```python
  """...positive (green/blue) and negative (red) color coding."""
  color = PRIMARY_COLOR if v >= 0 else NEGATIVE_COLOR   # 正=蓝，负=红
  ```

  docstring 特意写 `green/blue` —— **用蓝替代绿以规避红绿色盲对**，是出版级设计的常见取舍

**同花顺 —— 行情风格**

```python
# constants.py L32-33
UP_COLOR   = "#C0392B"   # 涨 = 红
DOWN_COLOR = "#1E8449"   # 跌 = 绿
THEMES = { research_blue, colorblind_safe, broker_thin, finance_dashboard }
```

配合 `_is_updown_series()`：系列名命中 `("涨跌","涨跌幅","环比","同比","增速","变化率","变动")` 时，**逐点**按 `value >= 0` 上红/绿。

**为什么不能迁入（五条）**

| 问题 | 说明 |
|---|---|
| **语义错位** | 本项目 `NEGATIVE_COLOR` = 风险/赤字（价值判断）；同花顺 `UP/DOWN_COLOR` = 价格涨跌（行情方向）。同名不同义 |
| **体系打架** | 迁入后同图并存两套规则：diverging bar 用「蓝/红」、updown 系列用「红/绿」 |
| **引入本不存在的绿色** | 本项目 `PALETTE` 六色位无绿，加绿破坏调色板一致性 |
| **破坏色盲友好** | 红绿对是最差组合，而本项目已刻意以蓝代绿 |
| **行业研究语境不适用** | 报告里“同比增长”是**中性事实**，不是“涨”；且「成本同比 +20%」上红色会误导（那是负面）。`_UPDOWN_TOKENS` 还含“变动”“变化率”等中性词，会误触发 |

**结论**：P2 **只迁 `dual_panel` 与标注机制（`reference_line` / `_auto_datalabel`），不迁 `THEMES` 色值与 `UP_COLOR`/`DOWN_COLOR`**。六图一律使用本项目现有 `PALETTE`，正负区分沿用「主蓝 / 警示红」。

> 若将来确需在视觉上强调“变化方向”，应另设**与研究语境绑定**的语义（如用箭头方向或深浅，而非红绿），不要复用行情色。

## 二、补充优化点（原方案未覆盖）

### 2.1 门禁要封住"compiler 兜底路径"

现 `compiler.compile()` L107-110 有静默兜底：

```python
# Fallback to bar or line
if table.axis_type == AxisType.TIME_SERIES:
    return EChartsCompiler._compile_line(table, title, base_grid)
return EChartsCompiler._compile_bar(table, title, base_grid)
```

若上游传入 `scatter` 且未被拦截，会走到 L104 `_compile_scatter`；若传入未知类型，会被**静默**变成 bar/line——**门禁被绕过且无日志**。

**建议**：`compile()` 入口处加显式断言（fail-fast），而不是静默兜底：

```python
canonical = normalize_active_chart_type(chart_type)
if canonical is None:
    raise ValueError(f"chart_type_not_enabled: {chart_type!r}")
```

并把 fallback 分支只保留给"已知六图但数据形态不匹配"的情况。

### 2.2 用 `is_composition` 替代"合计有意义"的启发式

P1 规则写"构成：≥3 且**合计有意义** → pie"。"合计有意义"无法用代码判定。

`ChartDataset` 已有语义标记 `is_additive` / `is_composition`。**建议 bridge 阶段直接计算并填充**：
- `is_composition = True` 仅当该指标跨实体求和有业务含义（占比类、份额类）
- 否则 `is_composition = False`，即使 ≥3 也不出 pie

### 2.3 `value_kind: actual|forecast` 需要数据来源定义

`ChartPoint.value_kind` 是 `Literal["actual","forecast"]`。原方案 §0 提到"单/多系列、actual/forecast"，但**没说这个标记从哪来**。

**这是隐藏工作量**，需明确：
- 数据源侧：`EvidenceRef` / `ResearchRecord` 是否有"预测"标记？
- 若无，只能全部标 `actual`，则该字段暂时是死字段
- **建议**：bridge 阶段从 `period > as_of` 推导（期间晚于研究时点 → forecast）

### 2.4 点级 evidence 要纳入 linter 校验

`linter.py:73` 已有 `invalid_eids = [eid for eid in eids if str(eid) not in evidence_index]` 的**图级**校验。

加字段后，**点级 id 也要校验**：每个 `ChartPoint.evidence_id` 必须 ∈ `report.evidence_index`。否则会重现"图有据、点无据"的伪溯源。

### 2.5 `ChartSpec` 加字段的兼容性确认

`ChartSpec` / `ChartDataset` / `NormalizedDataTable` 全是 `model_config = ConfigDict(extra="forbid")`。

- **后端加字段**：向后兼容（旧数据缺字段走 default）✅
- **新数据下发旧前端**：需确认前端 `FusionChartLoose` / `ChartSpec` 类型是**宽松读取**。若是 `forbid` 语义会炸

> 行动：加字段前，先确认 `frontend/src/api/types.ts` 中对应类型是否带可选标记（`?`）。前几轮已见 `ReportQualityReport` 用可选项，图上契约多半同理，但**必须实测确认**。

### P1　数据对齐层 `dataset_bridge.py`

**输入**：`NormalizedDataTable`（本项目，展平结构）+ `EvidenceRef` 列表
**输出**：`ChartDataset`（ths_schema，点级）

**为什么必须重做而不是"桥接"**：本项目 `NormalizedDataTable` 是展平的——

```python
class NormalizedDataTable(BaseModel):
    categories: list[str]                # X 轴文本
    series_data: dict[str, list[float]]  # 系列名 → 纯数值列表
    series_units: dict[str, str]
    raw_evidence_ids: list[str]          # ← 只是一整个列表，点与 id 的对应关系已丢失
```

`categories[i]` 与 `series_data[k][i]` 靠**下标**对应，`raw_evidence_ids` 无法还原出"第 i 个点用的哪条证据"。

**因此正确做法**：在 `data_formulation.formulate()` **构建表格时就保留点级 evidence**，而不是事后桥接。bridge 的职责是"组装与校验"，不是"还原"。

**规则表**：

| 数据形态 | 判定 | 出口 |
|---|---|---|
| 时序 | 同 entity + metric 有 ≥2 period | line / area |
| 对比 | ≥3 entity 同 metric 同 period | bar（<3 抑制） |
| 构成 | `is_composition=True` 且 ≥3 项 | pie |
| 雷达 | ≥3 维度、≥1 实体 | radar |
| 复合 | 规模序列 + 率/增速序列 | combo（dual_axis） |
| 双面板 | 两指标量纲不可比 | combo（dual_panel） |
| **无 record_id 的点** | — | **丢弃，不进图** |

## 六、风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| `data_formulation` 改动影响既有图表 | 高 | 改动前备份；跑 `chart-generator/tests/`（含 `test_pipeline.py` / `test_agent.py`） |
| `extra="forbid"` 导致新旧契约冲突 | 中 | 加字段前先确认前端类型是否宽松读取（§2.5） |
| 误迁行情配色污染出版级调色板 | 中 | 按 §1.4 不迁 `THEMES` 与 `UP/DOWN_COLOR`；评审时检查是否引入绿色系色值 |
| `dual_panel` SVG 分支缺失 | 低 | 可先走 ECharts 预览，SVG 用单图拼接兜底 |

**回滚点**：本项目无 git，修改前对 `chart_generator/` 整体打包备份：
```bash
cp -r agents_core/chart-generator agents_core/chart-generator.bak-YYYYMMDD
```

## 七、一句话结论

原方案方向正确（**管线用本项目、出图用同花顺、数据对齐用点级契约**），但有三处需修正：

1. **本项目 combo 双轴不弱**——迁入收益应重新定位到 `dual_panel` + 标注能力（**不含主题色板与涨跌色**，见 §1.4）
2. **P1 与 P2 矛盾**——放弃"轻量结构"，直接移植 schema（更省且天然满足点级 evidence）
3. **`ChartDataset.kind` 要收窄**——从数据契约层面堵死下排 6 种，而非只在上层拦截

另补 5 项优化：compiler fail-fast、`is_composition` 替代启发式、`value_kind` 数据来源、点级 linter 校验、**配色保持本项目出版级 `PALETTE`（不迁行情涨跌色，见 §1.4）**。
