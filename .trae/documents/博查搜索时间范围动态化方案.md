# 博查搜索时间范围动态化方案

## 摘要

当前 L3 联网兜底（博查搜索）的 `freshness` 恒为 `oneYear`，用户要近 5 年、近 3 年的资料会被错误过滤。本方案将时间限制改为"以用户要求为主"的动态策略：解析用户/任务的时间要求 → 动态映射博查 `freshness` 档位 → 后置日期硬过滤保证精准（要近 3 年绝不返回 5 年前的旧闻），无时间要求时维持默认近一年（保留防旧闻冒充最新的实测结论）。

## 现状分析（探索结论）

数据流与问题点：

```
用户请求（"近五年"）→ Agent1 意图拆解 → IntentTimeRange(raw_text="近五年")
  → planner 构造任务：query 含时间词，但 SkillQueryTask.time_range 是全局值（默认近3年区间）
  → executor L3 触发：_run_web_fallback → fallback_query_for() 重组 query
      ⚠ 问题1：fallback_query_for 只用 entities+expected_fields 重组，时间词全部丢失
  → ToolGateway.execute(arguments={query, page, limit, call_type})
      ⚠ 问题2：SkillQueryArgs 无时间字段，时间信息传不到客户端
  → WebSearchClient.execute：body["freshness"] 恒为 DEFAULT_FRESHNESS="oneYear"
      ⚠ 问题3：用户要近5年时 2022~2024 年资料全被过滤
```

关键事实：
- 博查 `freshness` 仅支持 5 档枚举：`oneDay/oneWeek/oneMonth/oneYear/noLimit`（见 `docs/2026-09-04-联网搜索兜底方案选型.md:110`），**没有 3 年/5 年档** → 大窗口只能 `noLimit` + 客户端后置过滤
- `SkillQueryArgs` 为 `extra="forbid"`，所有技能共用（`app/integrations/skillhub/models.py:8`）
- `SkillQueryTask.time_range: str` 已存在（`app/schemas/acquisition.py:102`），值形如 `"2024-01-01至2026-09-06"` 或短语
- `app/agents/common/feedback_interpreter.py:249` 已有中文相对时间解析 `resolve_time_range()`（支持 近N年/季度/月/半年/今年/最新/N年），可参照复用
- 现有测试断言：`backend/tests/agents/data_fetcher/test_cascade_fallback.py:656` C-14 断言 `DEFAULT_FRESHNESS == "oneYear"` 及请求体携带 `freshness=oneYear`

## 改动方案（4 个文件）

### 1. `backend/app/integrations/skillhub/models.py` — 参数通道扩展

`SkillQueryArgs` 增加可选字段：

```python
time_range: str | None = Field(default=None, min_length=1, max_length=100)
```

- optional + 默认 None：问财客户端/MockWebSearchClient 不读取，零影响
- 附注释说明：仅 L3 WEB_SEARCH 消费，用于动态 freshness 与后置过滤

### 2. `backend/app/agents/data_fetcher/executor.py` — 时间信息传递 + query 保留时间词

**2a. `_execute_task`（约 422-432 行）**：`ToolCall.arguments` 增加 `"time_range": task.time_range`（所有技能统一传，非 WEB_SEARCH 技能忽略该字段）。

**2b. `fallback_query_for`（104-117 行）**：重组降级 query 时保留时间词：

```python
def fallback_query_for(main_task: SkillQueryTask, fallback_skill: SkillName) -> str:
    entities = " ".join(main_task.target_entities[:3])
    metrics = " ".join(
        field for field in main_task.expected_fields[:4]
        if field not in _FALLBACK_QUERY_META_FIELDS
    )
    # 新增：时间词保留——先从主任务 query 提取用户时间短语（意图任务含用户原话，
    # 如"近五年"），提取不到再用任务级 time_range（基线任务的全局区间）。
    time_text = _extract_time_phrase(main_task.query) or _friendly_time_text(main_task.time_range)
    return f"{entities} {metrics} {time_text}".strip() or main_task.query[:120]
```

- `_extract_time_phrase(query)`: 小正则提取时间短语（近N年/近N月/近半年/今年/去年/最新/20XX年/20XX年以来/不限），返回 None 表示无
- `_friendly_time_text(time_range)`: 区间文本 `"2024-01-01至2026-09-06"` → `"2024年以来"`；短语原样返回
- L2 降级（问财文档技能）同样受益：query 带时间词符合问财查询语法
- 注意总长 ≤500（SkillQueryArgs.query 约束），entities+metrics 已截断，时间词最长约 20 字符，安全

### 3. `backend/app/integrations/websearch/client.py` — 核心动态化

**3a. 新增时间窗口解析**（模块级函数）：

```python
def _resolve_search_window(query: str, time_range: str | None, today: date) -> tuple[date, date] | None | Literal["unbounded"]:
```

解析优先级（以用户原话为主）：
1. `query` 中的时间短语（用户原话，如"近五年"）→ 窗口
2. `time_range` 参数：区间格式 `YYYY-MM-DD至YYYY-MM-DD` 直接解析；中文短语（近N年/今年等）参照 `resolve_time_range` 逻辑解析
3. 显式"不限/全部/任意" → 返回 `"unbounded"`（noLimit 且不过滤）
4. 都解析不出 → None（走默认 oneYear）

**3b. freshness 动态映射**（`execute` 方法内）：

```python
window = _resolve_search_window(args.query, args.time_range, today)
freshness = self._freshness_for(window)   # 新方法替代恒定 DEFAULT_FRESHNESS
body = {"query": ..., "freshness": freshness, "count": ..., "summary": True}
```

映射规则（跨度 = end - start）：

| 窗口 | freshness | 后置过滤 |
|---|---|---|
| ≤1 天 | oneDay | freshness 已过滤，无需 |
| ≤7 天 | oneWeek | 同上 |
| ≤31 天 | oneMonth | 同上 |
| ≤366 天 | oneYear | 同上 |
| >366 天（近3年/近5年/近十年…） | noLimit | **必须**：published_at < start 丢弃 |
| "不限" | noLimit | 不过滤 |
| 解析失败/无时间要求 | oneYear（DEFAULT_FRESHNESS） | 无 |

`DEFAULT_FRESHNESS = "oneYear"` 保留为默认值语义（无时间信息时的兜底），类常量不删除（C-14 断言兼容）。

**3c. `_clean_hits` 后置过滤**：增加 `window_start: date | None` 参数——仅 noLimit + 有明确窗口时启用：
- `published_at` 缺失或 < window_start → 丢弃，计数 `discarded["out_of_window"]` 并 logger.warning 留痕（与 §7.3 缺陷上报口径一致）
- 这是"要近 3 年就不出近 5 年旧闻"的精准性保障——博查枚举表达不了 3 年/5 年档，靠该过滤兜底

**3d. 更新模块 docstring**：第 10-11 行"freshness 恒为 oneYear"改为动态策略描述。

### 4. `backend/tests/agents/data_fetcher/test_cascade_fallback.py` — 测试更新

- **更新 C-14**（`test_c14_web_request_must_carry_freshness`）：保留"无时间词 → freshness=oneYear"断言（默认行为不变）
- **新增用例**：
  - `test_c14a_freshness_dynamic_five_years`：query 含"近五年" → body freshness == "noLimit"，命中中 2021 年旧闻被过滤（out_of_window）、近 5 年内保留
  - `test_c14b_freshness_dynamic_three_years`：time_range="2023-09-06至2026-09-06"（近3年）→ noLimit + 2022 年资料被过滤（验证"要3年不出5年"）
  - `test_c14c_freshness_within_one_year`：query 含"今年" → oneYear（窗口 ≤1 年走枚举）
  - `test_c14d_freshness_unbounded`：query 含"不限" → noLimit 且旧闻保留
  - `test_fallback_query_preserves_time_phrase`：`fallback_query_for` 对含"近五年"的主任务 query 产出含"近五年"的降级 query

## 决策与理由

1. **无时间要求时默认仍 oneYear**：用户原话"看实际具体情况"——没提时间就用现行默认（实测结论 D8：不带 freshness 会混入 2022/2025 旧闻冒充最新），不放宽。
2. **大窗口用 noLimit + 后置硬过滤而非仅靠 query 时间词**：搜索引擎的时间词召回是软约束；后置按 `published_at` 过滤是硬约束，两者叠加才做到"精准"。
3. **时间解析优先 query（用户原话）而非 task.time_range（全局值）**：用户说近 5 年时全局 time_range 可能仍是默认近 3 年，以用户要求为主。
4. **`SkillQueryArgs` 加 optional 字段而非新建 WEB_SEARCH 专用 schema**：改动最小，registry（`create_skillhub_gateway`）无需分支处理。
5. **无日期命中在 noLimit+有窗口时丢弃**：与"精准"诉求一致；博查实测 19 条命中均带 datePublished，误伤面小；丢弃计数进 discarded 留痕，不静默。
