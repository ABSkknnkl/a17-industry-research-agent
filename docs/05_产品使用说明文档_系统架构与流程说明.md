## 一、项目概述

### 1. 项目做什么

这是一个面向证券投研场景的行业研究报告智能生成系统。使用者输入一个行业主题（例如「动力电池」「半导体设备」「创新药」）和若干关注问题，系统自动完成从数据采集到报告成稿的全过程，最终交付一篇结构完整的行业深度研究报告。

报告按投研行业通行的七章二十一节体例组织，可导出为三种格式：便于编辑的 Markdown 文档、带交互图表的网页、以及可直接打印的出版级 PDF。

系统的特别之处在于"可控"：它不是黑箱式的一键生成，而是把报告生产拆成五个环节，每个环节结束后都停下来，让使用者检查中间成果、提出修改意见，确认无误后再继续。用一句话概括产品定位：**写得出，也审得过**。

### 2. 要解决的问题

传统行业研究报告的撰写有两个长期痛点。

一是数据整合成本高。一篇深度报告涉及宏观环境、行业规模、竞争格局、公司财务、估值水平、政策动向等多类信息，分析师需要在多个数据源之间反复检索、核对、整理，这部分工作通常占据撰写时间的大半。

二是内容质量难追溯。生成式技术可以快速产出文字，但投研报告对数字的准确性要求极高，一个错的数字可能误导投资判断。如果只靠提示词约束，模型仍然可能凭空编造数据，而且编造的内容读起来同样通顺，很难被发现。

本系统针对这两点分别设计：用多智能体协作把数据检索与整理自动化；用可追溯的证据机制让每个数字都能回查到原始数据。

### 3. 主要能力一览

| 能力 | 说明 |
|---|---|
| 自动取数 | 把一句自然语言需求拆解为多条精确检索指令，组合调用金融数据技能，自动完成多轮补采 |
| 数据解读 | 对结构化数据做确定性计算（增速、集中度、比率、估值分位等），并提炼关键事实、趋势与风险 |
| 图表生成 | 根据数据形态自动选择图表类型，生成矢量图表并嵌入报告正文对应位置 |
| 章节撰写 | 按七章二十一节大纲逐节撰写，正文数字自动关联证据编号 |
| 报告融合 | 整合各章节、统一口径与术语、生成摘要与结论，输出三种格式 |
| 人机协同 | 五个环节均设审核卡口，支持追加检索、补充背景、调整图表、定向重写章节 |
| 断电续跑 | 环节失败或中断后可从断点恢复，不必整篇重跑 |

## 二、总体架构与实现思路

### 2.1 四层架构

系统分为四层，各层职责清晰、通过标准接口通信。

**第一层：交互层（前端工作台）**
面向使用者的操作界面。提供任务创建、运行进度实时监控、阶段成果预览、审核意见提交、报告在线预览与下载等功能。图表在浏览器端渲染，支持缩放与数据点查看。

**第二层：调度层（后端服务）**
系统的中枢。负责接收任务、驱动五个处理环节依次执行、在设定的节点暂停等待人工确认、记录全过程状态与事件、向外推送实时进度。同时提供配置管理与技能目录查询等辅助能力。

**第三层：处理层（五个智能体）**
系统的实际生产力，五个智能体各自独立、职责单一，按固定顺序协作完成报告生产。

**第四层：数据层（金融数据技能）**
对接同花顺问财 SkillHub，使用其官方金融数据能力。系统注册可用技能六十余项，覆盖宏观数据、行业数据、公司财务、行情量化、产业链分析、研报检索、新闻资讯等类别。

### 2.2 五个智能体的分工

| 环节 | 智能体 | 职责 | 主要产出 |
|---|---|---|---|
| 一 | 数据获取 | 理解研究需求，拆解为多条检索指令，组合调用数据技能，多轮迭代补全缺口 | 结构化数据集、数据来源清单 |
| 二 | 数据解读 | 用确定性计算得出关键指标，提炼事实、洞察、趋势、风险与异常 | 解读报告、证据索引 |
| 三 | 图表生成 | 判断数据形态与展示意图，选择合适图表类型，编译为矢量图形 | 图表规格、图表文件 |
| 四 | 章节撰写 | 按七章二十一节大纲逐节撰写正文，为每个数字标注证据编号 | 章节正文、质量自检结果 |
| 五 | 报告融合 | 汇总各章节，校验内部一致性，统一术语与口径，生成摘要结论，导出多格式成品 | 完整报告、一致性报告 |

这五个智能体不是简单地串行调用模型，每个都有明确的输入输出契约和内部质量控制：数据获取层有需求拆解与检索指令规范化；解读层的关键指标由确定性计算引擎完成；图表层有图表类型准入与数据不足时的抑制机制；章节层有反幻觉校验；融合层有一致性审计。

### 2.3 三个关键设计

**设计一：证据编号贯穿全链路。**
数据进入系统时获得唯一编号，之后在解读、图表、章节中每一次被引用都带编号。报告成稿后，正文中的任意数字都能沿着编号回查到最初的那条原始数据及其来源。这是"数字可追溯"的实现基础，也是防止模型编造内容的关键手段：模型可以写错语气，但写不出一个不存在的编号。

**设计二：关键统计不由模型计算。**
增速、集中度、各类财务比率的计算，全部由确定性计算引擎完成，模型只负责归纳和表述。模型擅长组织语言，不擅长精确算术，把两者分开，可以从架构上避免"数字算错但表述流畅"这类最难发现的问题。

**设计三：审核门与版本留痕。**
每个环节结束都进入待审核状态，必须由人确认才能推进。修订意见提交后，系统重跑当前环节并再次回到同一个审核门等待确认，**不会因为提交了一次修订就自动放行**。每次带意见的提交都会生成一个新版本，版本历史与意见全文完整保存，可逐条回查。

## 三、核心业务流程

### 3.1 五阶段流水线

一次完整的研究任务按五个阶段推进：

```
输入行业主题与关注问题
        │
        ▼
阶段一 数据获取 ── 拆解需求 → 组合检索 → 迭代补采 → 结构化入库
        │
        ▼
阶段二 数据解读 ── 确定性计算 → 事实提炼 → 趋势与风险识别
        │
        ▼
阶段三 图表生成 ── 数据形态判断 → 图表选型 → 矢量编译
        │
        ▼
阶段四 章节撰写 ── 按七章二十一节逐节撰写 → 数字挂证据编号
        │
        ▼
阶段五 报告融合 ── 一致性校验 → 术语口径统一 → 摘要结论 → 三格式导出
        │
        ▼
输出：研究报告（编辑文档 / 交互网页 / 出版级 PDF）
```

每个阶段结束后若配置了审核卡口，系统会暂停等待人工确认。使用者可在此追加检索关键词、注入专家背景、调整图表形态、提交章节修改意见，或直接批准继续。

### 3.2 人机协同怎么运作

协同的实质是"人在关键节点介入，系统按意见重跑"。

**介入点。** 五个阶段各有一个审核卡口，可在创建任务时按需勾选启用哪几个。不需要介入的阶段直接自动推进。

**介入方式。** 系统提供多种干预入口，覆盖不同粒度的调整需求：追加或修改检索范围、发起增量数据补采、注入专家背景知识、切换图表形态、对指定章节提出修改意见、直接编辑阶段成果。

**反馈如何生效。** 意见提交后，系统重跑当前阶段。重跑完成后**再次停在同一审核卡口**等待确认，形成"提交意见 → 重跑 → 复核 → 确认"的闭环。这样设计的原因很直接：修订过程本身也可能出错，如果修订后自动放行，等于把风险转嫁给下游环节。

**留痕。** 每次提交都会记录提交时间、所属阶段、意见全文，并生成递增的版本号；阶段成果的每个版本可单独调阅，方便对比修订前后的差异。

### 3.3 一次完整运行的时间线

以实测的一次完整运行为例：

| 时点 | 事件 |
|---|---|
| 起始 | 创建任务，启用四个审核卡口 |
| 约 3 分钟 | 阶段一首次完成，进入待审核 |
| — | 提交修订：追加检索关键词，系统重跑阶段一 |
| 约 8 分钟 | 阶段一再次进入待审核，确认通过 |
| 约 12 分钟 | 阶段二完成，提交专家背景，系统重跑 |
| 约 15 分钟 | 阶段二再次待审核，确认通过 |
| 约 21 分钟 | 阶段三完成，图表核对通过 |
| 约 25 分钟 | 阶段四完成，提交章节修订意见，系统重跑 |
| 约 28 分钟 | 阶段四再次待审核，确认通过 |
| 约 30 分钟 | 阶段五完成，报告签发，三格式交付就绪 |

全程共七次人工介入（三次修订、四次确认），版本依次递增至第四版。

## 四、技术选型与理由

### 4.1 选型总览

| 层面 | 选型 | 主要理由 |
|---|---|---|
| 后端服务 | Python 异步框架 | 报告生成是长耗时任务，需要异步执行与实时事件推送；Python 生态对数据处理与模型接入支持最好 |
| 前端工作台 | 主流前端框架 + 开源图表库 | 需要高频状态刷新与丰富的图表交互；图表库对多种图表类型支持完整 |
| 流程编排 | 自研状态机 | 通用编排框架的检查点机制面向自动重试，不直接支持"暂停等待人工介入再续跑"，自研更贴合业务 |
| 智能体组织 | 五个独立智能体 | 职责隔离便于定位问题；单个环节失败可局部重跑，不必整篇重来；各自可独立测试 |
| 关键统计 | 确定性计算引擎 | 精确计算不交给模型，从架构上避免数字错误 |
| 内容溯源 | 证据编号贯穿 | 数字可回查原始数据，是防幻觉的核心手段 |
| PDF 生成 | 无头浏览器排版 | 复用网页样式直接生成印刷级 PDF，避免维护两套排版 |
| 可复现性 | 接口快照录制回放 | 同一次测试可在任意环境下复现，不受外部服务波动影响 |

### 4.2 几个关键取舍

**为什么不做一个单体智能体，而要拆成五个。**
报告生产包含性质完全不同的子任务：检索取数是接口调用密集型，数据解读是计算密集型，章节撰写是文本生成密集型。混在一起会导致提示词臃肿、职责不清、出了问题难定位。拆开之后，每段逻辑更简单，也更容易单独验证。实际效果是：单个环节出问题时，只需重跑该环节。

**为什么自己实现流程编排，不用现成框架。**
报告生产的关键需求是"停下来等人"。通用编排框架擅长自动重试与故障转移，但人工介入是业务需求而非异常处理，需要的是可控的暂停与恢复、以及暂停期间的状态固化。自研状态机可以直接表达这套语义，也不必为框架的抽象付出额外复杂度。

**为什么不让模型直接算数。**
模型做数学题的错误率无法通过提示词消除，而且算错时表述往往依然流畅，这类错误在成稿中极难被发现。把计算剥离给确定性引擎后，模型只做归纳与表达，数字的正确性由可复算的代码保证，出问题也能精确定位。

**为什么要做证据编号。**
投研内容的可信度建立在"数字有来源"之上。给每条数据编号并全程携带，使报告的每个数字都可回查。这同时形成对模型的硬约束：正文引用的编号必须真实存在于证据库中，凭空编造的编号会被校验拦下。

**为什么 PDF 用浏览器排版。**
报告需要同时交付网页与印刷版。用浏览器直接对网页排版生成 PDF，可以复用同一套样式，不必维护两套模板；同时利用浏览器的分页与字体能力，得到接近印刷品质的排版效果。

## 五、运行环境与部署

### 5.1 环境要求

| 项 | 要求 |
|---|---|
| 操作系统 | Linux、macOS 或 Windows（Windows 建议使用 WSL） |
| Python 运行时 | 3.10 及以上，建议使用虚拟环境隔离 |
| Node.js 运行时 | 18 及以上 | 
| 硬件建议 | 四核以上处理器、16GB 以上内存、10GB 以上可用磁盘 |
| 外部依赖 | 大模型服务凭据、同花顺问财数据服务凭据 |

### 5.2 部署步骤

1. **准备代码与后端依赖**：在项目主目录创建并激活 Python 虚拟环境，安装后端依赖清单。
2. **安装浏览器内核**（用于 PDF 导出）：执行一次浏览器内核安装命令即可，后续无需重复。
3. **准备前端依赖**：进入前端目录安装依赖。
4. **配置服务凭据**（二选一）：
   - 界面配置：启动系统后，在工作台右上角打开配置面板，选择大模型服务商，填入大模型凭据与问财凭据，点击测试连通性，通过后保存即可生效，无需重启。
   - 文件配置：复制配置模板为本地配置文件，按模板注释填入凭据与运行参数。
5. **一键启动**：执行项目自带的一键启动脚本。脚本会自动检查端口占用、启动后端服务并等待其就绪、启动前端服务。按终止快捷键可一并安全退出前后端。

启动完成后，浏览器访问前端工作台地址即可开始使用。

## 六、使用指南

### 6.1 发起一次研究

1. 打开工作台，进入发起研究页面；
2. 填写研究行业主题；
3. 选择市场范围与报告币种；
4. 填写关注问题，每行一个（关注问题会直接影响检索方向与报告侧重）；
5. 选择分析深度与配图密度；
6. 勾选需要人工审核的环节。建议首次使用勾选数据获取与章节撰写两个环节，既能控制关键质量，又不至于介入过频；
7. 提交任务。

### 6.2 在审核环节介入

任务执行到已勾选的审核环节时会自动暂停，工作台显示该环节的成果摘要与可用的干预入口。

| 环节 | 可做的事 |
|---|---|
| 数据获取 | 查看覆盖的数据领域与记录条数；追加或修改检索关键词；指定补充采集的公司与指标 |
| 数据解读 | 查看关键指标与洞察；写入专家背景知识，该背景会传导至后续章节撰写 |
| 图表生成 | 查看生成的图表；切换图表形态；核对单位与数据口径 |
| 章节撰写 | 查看各章节正文；对指定章节提出修改意见或直接编辑 |
| 报告融合 | 通篇审阅；提出整体修订方向；确认后完成签发 |

每次提交修订后，该环节会重新执行并**再次回到同一个审核点**等待确认，不会自动进入下一环节。

### 6.3 查看与下载成果

任务完成后，可在成果页在线预览完整报告，并从下载中心导出所需格式。此外还可调阅任意历史版本的阶段成果，用于对比修订前后的差异。

## 七、最终效果

### 7.1 一次真实运行的实测结果

| 指标 | 实测值 |
|---|---|
| 完成时间 | 约 30 分钟（五阶段全自动推进，含七次人工介入） |
| 采集数据 | 1064 条结构化记录，来自 185 个数据来源 |
| 报告结构 | 七章二十一节，全部齐备 |
| 图表 | 14 张，自动选型后嵌入正文对应位置 |
| 交付格式 | Markdown、交互式网页、出版级 PDF（37 页，2.15MB） |
| 一致性评分 | 90 分（满分 100） |
| 证据覆盖度 | 0.97 |
| 人工介入 | 7 次（3 次修订、4 次确认），版本递增至第四版 |

### 7.2 质量保障的实际表现

**数字可追溯。** 报告正文中的数字均可通过证据编号回查至原始数据记录。在一次实测中，系统还主动识别出一处数据问题：同一家公司的毛利率在两个数据来源中数值不一致，系统在报告中标注了该矛盾并提示以原始记录为准，而不是任选一个使用。

**缺口如实披露。** 当数据不足时，系统的处理方式是明确告知而非掩饰。实测中系统对采集到的数据做了完整性检查，发现超过半数的数值记录缺少日期字段、无法支撑严格的趋势分析，这一限制被明确写入报告的质量提示中，同时报告交付状态标记为"有条件交付"，提示读者注意数据边界。

**降级有据可查。** 当某个交付格式未能成功生成时，系统会如实播报实际交付的格式，并在阶段质量信息中记录缺失原因，不会出现"声称已交付但实际没有"的情况。

### 7.3 稳定性

系统在交付前经受了批量真实运行验证：四十八个研究主题的连续批跑全部正常完成，一百个主题的并发阶梯测试全部到达预期状态，无异常中断、无状态丢失。相关质量缺陷在测试过程中发现并修复，修复后回归测试全部通过。

## 八、常见问题

**问：启动时提示端口被占用怎么办？**
答：关闭占用端口的程序后重新启动；系统的一键启动脚本在启动前会自动检查并释放端口。

**问：导出 PDF 时报错怎么办？**
答：这是缺少浏览器内核导致的。执行一次浏览器内核安装命令即可解决；也可以先导出网页格式，其内容与 PDF 一致。

**问：数据接口调用失败或提示凭据失效怎么办？**
答：打开工作台右上角的配置面板，重新填入数凭据并测试连通性，通过后保存即时生效，无需重启服务。

**问：某个环节执行中途失败怎么办？**
答：系统会保留现场并支持从断点恢复，无需从头重跑。在工作台可对失败环节单独触发重新执行。

**问：生成过程耗时较长是否正常？**
答：正常。一个完整主题涉及多轮数据检索、解读计算、图表编译与七个章节的撰写，实测单份报告约需三十分钟。过程中可在工作台实时查看进度。
