## 三、后端契约缺口（“完全对齐”的真正成本）

交接版前端不是“换皮”，它默认后端已经有一套新契约。主仓库缺的如下：

| 前端依赖 | 主仓库现状 | 只换前端的后果 | 补法 | 工期 |
| --- | --- | --- | --- | --- |
| `GET /runs/{id}/exports/compact` | 只有 `POST`（带 `mode/expected_revision`） | 报告下载页“一键打包”按钮 404 | 新增 GET，复用现有 `build_package_bytes` / `_compact_snapshot`；当前版本可用，历史 revision 先返回 404 | 0.5-1 天 |
| `data.decision_package` | 后端零实现，只有 schema 字段 | `accept_with_risks` 直接报“缺少可校验的决策包”，风险审核、章节缺口继续都走不通 | 移植 `review_decisions.py`（385 行）+ `ReviewDecision` 模型 + 阶段进入 `waiting_review` 时挂载 + 审核时校验；旧 run 自动补包 | 1.5-2 天 |
| `edited_data.certify_chain` | 后端完全不处理 | 点“认证产业链”会当成普通批准，**没认证却放行**，比报错更危险 | 移植 `state_machine` 认证块 + `chain_research.certify_bundle`（`service.py` 约 +229 行、`store.py` +1 行） | 1-2 天 |
| 8 个 `/remediation*` 路由 | 一个都没有 | `ReviewView` 每个待审任务都会挂 `RemediationWorkbench`，加载直接报错/404 | 先做只读：`GET /remediation` + `GET /remediation/sources`；动作/应用/自动暂返回 501 | 1-1.5 天 |
| `verification_status` / `verification_summary` | A5 不产出 | 报告预览的“部分核验”提示、质量面板标注数不显示 | 移植 A5 标注通道（2-3 天）；不影响页面可用 | 2-3 天 |
| `editorial_changes` | A5 不产出 | 报告预览“编辑说明”为空 | 移植 `EditorialChange` + `_build_editorial_changes` | 1 天 |
| `review_decisions` 历史 | 无模型、无接口 | 前端类型有，但当前 UI 没读；不阻塞 | 随决策包一起加 | 含在上面 |
| `chain_delivery` 的 `evidence_tier_summary` / `scope_applied` / `scoped_chart_id` | 只有 `verified_relations` 等部分字段 | 产业链认证/有限覆盖提示不完整，`ready_scoped` 可能被判 blocked | 补 A3 的 scoped delivery 字段；与认证一起做 | 1-2 天 |

### M1.5：后端兼容层，让页面“能点不报错”（3-5 天）

按优先级：

1. **`GET /exports/compact`**（0.5-1 天）
   - 新增 GET 路由，参数 `revision: int | None`。
   - 当前版本复用现有 `POST` 的 `_compact_snapshot` + `build_package_bytes`，返回同样的 ZIP 与 `Content-Disposition`。
   - 历史 revision 先返回 404“该历史版本没有独立产物快照”，等 M2 的版本隔离。
2. **决策包**（1.5-2 天）
   - 复制 `backend/app/engine/review_decisions.py`；在 `schemas/workflow.py` 加 `ReviewDecision`。
   - 在阶段进入 `waiting_review` 时调用 `attach_decision_package`；审核入口调用 `validate_review_request`。
   - 旧 run 首次审核前调用 `refresh_waiting_review_packages`，避免 409。
   - 验收：`accept_with_risks` 不再报“缺少可校验的决策包”；两个标签页同时审核时旧页面被 409 拒绝。
3. **补救工作台只读**（1-1.5 天）
   - 复制 `agents_core/artifact_paths.py`（52 行，带 `artifact_pointer` 缺失时回退 `run_dir/artifacts`，正好兼容旧 run）。
   - 复制 `backend/app/schemas/remediation.py`（71 行）。
   - 复制 `backend/app/engine/remediation_issues.py`（259 行）。
   - 新增 `GET /runs/{id}/remediation`：返回 `build_remediation_snapshot`，但把 `item.actions` 置空，避免用户点到不存在的写接口。
   - 新增 `GET /runs/{id}/remediation/sources`：返回 `[]`。
   - 写接口（上传/动作/apply/auto）暂不实现，返回 501 + 明确文案。
4. **认证链守卫**（0.5 天，或直接做完整 1-2 天）
   - 如果暂不移植 `certify_bundle`，至少在 `state_machine` 里拦截 `certify_chain=true`，返回 422“认证功能尚未接入”，**绝不能静默当普通批准放行**。
   - 若要完整对齐，移植 `certify_bundle` 与 `state_machine` 认证块，保证认证后从 `chart_generate` 重跑。

M1.5 验收：
- 新建任务 → 审核 → 风险确认 → 批准 → 下载，全链路页面不报 404；

- 认证按钮要么可用，要么明确报“未接入”，不能静默放行。

### M2：功能完全对齐（1-2 周）

## 七、风险与回滚

1. **首页变化**：交接版把任务列表放根路径，Landing 挪到 `/welcome`，新用户首次访问会被重定向一次。若答辩要求“先看产品介绍”，把 `router.ts` 的 `beforeEach` 重定向去掉，或把 `/` 指回 Landing。
2. **RevisionDiffViewer**：不要用交接版覆盖主仓库版，否则接口失败会静默显示“初始版本”；保留主仓库版 + spec 已验证 190 用例通过。
3. **StageInterventionModal**：交接版比主仓库旧，带“脏数据清洗与剔除”，主仓库 11-14 版已去掉。若坚持用主仓库版，需要改 3 个 spec，约 1-2 天，不建议在 M1 做。
4. **决策包旧 run**：严格校验会让旧 `waiting_review` 第一次批准 409；必须自动补包或给迁移开关。
5. **补救只读会误导**：工作台显示问题列表但动作按钮不可用；建议 M1.5 在写接口返回明确的 501 文案，或在验收时说明“当前只读”。
6. **版本隔离未做**：`remediation_apply` 不能直接写 `artifact_revisions`；M2 前不要开放 apply。
7. **回滚**：`frontend_backup_20261116` 整目录可回滚；后端每个补丁独立 commit，按 M1.5 的 4 个 bundle 逐个回滚。

## 八、建议的下一步

- 如果目标是**尽快让页面与交接版一致**：先做 M1（0.5-1 天），当天就能看到完整前端。
- 如果目标是**答辩时能演示审核+补救闭环**：做 M1 + M1.5 的决策包与补救只读（3-5 天），补救写路径留到 M2。
- 如果目标是**功能 100% 对齐**：按 M2 排 1-2 周，先做版本隔离，再做补救 apply/auto。

一句话：**前端换起来很快，别手改 39 个文件；真正要排期的是决策包、compact GET、补救只读这三个后端补丁。**
