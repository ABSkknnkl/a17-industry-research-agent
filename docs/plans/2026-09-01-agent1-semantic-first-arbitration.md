## 0. 一句话结论

四刀实施后 61 条中 58 条行为正确，**剩余 4 个 bug 全部是同一病灶：确定性层的"锁"仍然拥有压制 LLM 正确判断的特权**——关键词锁与指标诉求脱钩（BUG-2/4）、严格合并路径无能力护栏（BUG-3）、公司口径别名无实体上下文（BUG-1）。最终方案采纳用户"LLM 先理解语义"的方向，但把"两次回路"优化为**一次 LLM 调用 + 规则并行供证 + 确定性仲裁 5 规则收口**（语义优先并行仲裁），在此架构下修掉 4 个 bug。

## 2. 架构路线评估（正式回应用户提议）

### 2.1 三个候选路线

| 维度 | A. 用户串行三明治<br>LLM(1)→主路由→LLM(2) | **B. 语义优先并行仲裁（本方案）** | C. LLM 全权主导 |
|---|---|---|---|
| LLM 调用次数/查询 | **2 次** | **1 次** | 1 次 |
| 端到端延迟 | LLM + 规则 + LLM | ≈ 一次 LLM（规则并行免费） | ≈ 一次 LLM |
| 上下文理解 | LLM 负责 ✅ | LLM 负责 ✅ | LLM 负责 ✅ |
| "判断不了"信号 | 依赖规则层自我评估——**61 条证明它永远 conf=1.0，没这个能力** ❌ | 不需要：LLM 一次输出置信度+否决 ✅ | 不需要 |
| 防 LLM 幻觉的刹车 | 主路由仍是决策者（但正是它在压制正确判断） | **仲裁 5 规则 + L3 能力注册表，确定性代码收口** ✅ | 无刹车 ❌ |
| 契约校验（技能存在/能力匹配/实体口径） | 规则层做，但角色错位（既当选手又当裁判） | L3 只做可枚举校验，不做语义判断 ✅ | LLM 自判，会幻觉技能能力 ❌ |
| 改造成本 | 新增回路状态机 + 二次调用装配 | 仲裁规则收敛进现有 `_merge_llm_plan` + validator | 推翻确定性层，风险最高 |

### 2.2 为什么不选 A（串行三明治）

1. **第二次 LLM 调用 99% 是重复劳动**：一次调用即可同时输出技能候选、`analysis_only`/`reject_reason`、置信度——"两次理解"是一次结构化输出的两个字段。
2. **"主路由判断不了"是伪信号**：61 条实测中 L1 锁错时同样 `conf=1.0`，规则层没有自我怀疑的能力维度，回路永远不会触发到该触发的时候。
3. **主路由仍是决策者**：A 方案里规则层保留"主路由"决策权——但 4 个 bug 的病灶恰恰是规则层的决策权。换汤不换药。

### 2.3 为什么不选 C（LLM 全权）

用户自己已经排除了：LLM 会幻觉技能能力（编造不存在的 skill、高估自己的能力边界）、有概率性漂移、成本与可追溯性差。**L3 能力注册表和仲裁规则必须是确定性代码**——这是刹车片，不能给。

### 2.4 B 方案：语义优先并行仲裁

```
用户问句
   ├─ L1 确定性层（并行，微秒级）：指标命中 + 关键词命中 + 派生词否定表
   │     ↓ 产出「候选证据」，不再产出「锁定」
   ├─ L2 LLM 语义层（一次调用）：ResearchIntentPlan
   │     ↓ 技能候选 + analysis_only/reject_reason + 置信度
   ▼
仲裁层（确定性代码，5 条写死的优先级规则）：
   R1. L2 显式否决 > 一切确定性命中（指标锁/关键词锁都含）→ analysis_notes 透传
   R2. L2 与 L1 一致 → 直接执行
   R3. L2 与 L1 冲突 → L2 优先，但过 L3 能力注册表硬校验（实体类型+指标类型）
   R4. 仅 L1 有结果 → 指标锁可执行；关键词锁降级为「披露型查询」（不声称满足诉求）
   R5. 都无 → 澄清门
```

**角色重新划分**：LLM = 理解者 + 提案者（唯一懂上下文的）；L1 = 证据提供者（微秒级词表命中，不再决策）；L3 = 契约校验者（技能存在性/能力匹配/实体口径，可枚举、不会错）；仲裁 5 规则 = 法官（写死的确定性收口，用户"不让 LLM 全权"的落点）。

**与四刀的关系**：不是推翻，是把四刀的"否决权"从特例通道升级为**主数据流**。四刀修的合并/否定表/口径/词表全部保留，作为 L1 证据的质量保障。

## 3. Bug 修复方案（4 个根因级 bug）

> Bug 卡格式：现象/期望/影响/验收句。修复顺序按报告建议：**BUG-3 → BUG-1 → BUG-2+4 合并修**。每刀独立 feature flag。

### BUG-3（最重，先修）：严格匹配路径无能力护栏，L2 正确路由被整单丢弃

- **现象**：「动力电池竞争格局怎么样？」L2 给出 `STOCK_SELECTOR+市场份额`（正确），但 L2 碎片与确定性碎片文本相同 → 严格匹配路径合入同一子需求（**该路径无能力校验**）→ R3 对 hybrid 子需求的全部候选做能力校验：INDUSTRY 服务不了 market_share → `skill_capability_mismatch` → 整单 block → 回退确定性重建 → L2 成果清零。
- **期望**：L2 正确补充独立存活，与确定性锁定并行存在。
- **验收句**：给定"动力电池竞争格局"，最终 plan 应含 STOCK_SELECTOR 子需求；当前只剩 INDUSTRY。
- **修复**（改合并，不改门禁语义，报告推荐方向 1）：
  - `intent_merger` 严格匹配路径补能力护栏（与放宽路径护栏 2 对齐）：目标碎片既有技能无法服务合并后指标类型时**不合入**，L2 碎片独立成子需求；
  - 效果：锁定技能（INDUSTRY）继续独立执行，L2 补充（STOCK_SELECTOR）并行存在，两不相害；
  - 这正是仲裁规则 R3 的落地：冲突不合并、各自存活、L3 校验各管各的。
- **文件**：`intent_merger.py`（严格匹配分支）；**测试**：`test_arbitration.py` 新增 3 例（含 6.2 回归）。

### BUG-1：公司口径别名无实体上下文，行业问句静默误路由（一票否决项）

- **现象**：「行业出口占比数据」→ 子串命中「出口占比」（第三刀给 `overseas_revenue_share` 补的别名）→ 锁 `hithink_business_query`，静默取**公司级**数据，无澄清无低置信标记。L2 显式否决也压不住。
- **期望**：公司财报口径别名（外销/出口占比、库存周转等）仅在**公司实体在场**时可作指标锁；行业问句命中 → 澄清/unsupported 披露。
- **验收句**：给定"行业出口占比数据"，应走澄清/unsupported；当前静默锁 BUSINESS。
- **修复**：
  1. **口径护栏**（`metric_registry.py` / `deterministic_intent_parser.py`）：`MetricSpec` 新增 `requires_company_entity: bool` 标记，公司口径别名命中但无公司实体 → 不作指标锁，转 `unresolved_metric` 走披露；
  2. **词表回退**：从 `overseas_revenue_share` 移除「出口占比」，仅保留「外销占比」（公司语境更强）；「行业出口占比」登记研究边界词表；
  3. 同族处理：「库存周转」（OBS 4.5，行业库存周转误路由 FINANCE）一并加口径护栏。
- **测试**：`test_metric_granularity.py` 新增 3 例（2.18 回归、2.11 回归、公司实体在场时正常命中）。

### BUG-2 + BUG-4（合并修）：关键词锁与指标诉求脱钩

- **现象**：「产业链各环节良率」——「产业链」∈ `CHAIN_KEYWORDS` → 关键词锁 `industry_chain_analysis`，`metrics=[]` 无澄清（BUG-2：缺口被掩盖）；L2 显式否决后，R4 `locked_skill_not_routed` 把关键词锁复活，否决成果全丢（BUG-4：否决通道被绕过）。
- **根因共性**：确定性层有两种"锁"——**指标锁**（已注册指标命中，有词表契约，可信）与**关键词锁**（技能关键词表的话题词，与指标诉求脱钩）。两者享有同等 lock 特权是错的。
- **验收句**：给定"产业链各环节良率"，应标 `unresolved_metric` 走缺口披露；给定 L2 否决的该类问句，终态应保留 analysis_notes、锁不复活。
- **修复**：
  1. `parse.locked_skills` 打类型标记：`lock_type: "metric" | "keyword"`（`deterministic_intent_parser.py`）；
  2. **关键词锁降级**（仲裁规则 R4 落地）：纯关键词锁、同碎片无已注册指标 → 不作路由成功，产出「披露型查询」（保留关键词查询能力，但标 `unresolved_metric` 进缺口披露通道，不声称满足诉求）；
  3. **R4 豁免**：否决清空计划时，关键词锁不触发 `locked_skill_not_routed` 复活；指标锁维持现有守护不变（`intent_merger.py` / validator）。
- **测试**：`test_arbitration.py` 新增 4 例（2.10 直跑回归、探针 E 否决回归、指标锁仍受 R4 守护、披露型查询标记正确）。
