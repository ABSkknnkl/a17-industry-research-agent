## 1. 背景与根因

### 1.1 数据流现状

```
用户创建 run（种子证据进 input_data）
        │
        ▼
Agent 1（data_fetch）：fuse_evidence 融合种子+采集 → 产出规范化证据包 + chart_datasets
        │
        ▼
Agent 2（data_interpret）：source_data = {**input_data, **A1.data}
        │                     revision 推进时，白名单字段用 input_data 覆盖 ←── 洞在这里
        ▼
Agent 3（chart_generate）：_source_payload = {**input_data, **A1.data}（无覆盖逻辑，只认 A1）
```

`DataInterpretReviewEdits`（backend/app/schemas/workflow.py L152-158）允许用户在 A2 人机审核时提交 `evidence_items`；工作流把它合入 `input_data`（backend/app/workflow/graph.py L537-539）；A2 的修订覆盖循环（backend/app/agents/data_interpreter/service.py L269-289）在 revision 推进后采用它。**但 A3 永远只认 A1**——于是 A2 与 A3 的证据池分叉。

### 1.2 三个已确认的缺陷

| # | 触发条件 | 后果 |
|---|---|---|
| 洞① | 用户在 A2 审核修正证据数值（同 ID 新值） | A2 用新值出结论，A3 图表渲染 A1 旧值——**静默不一致** |
| 洞② | 用户在 A2 审核新增证据，A2 候选引用新 ID | A3 数据集无此 ID → 图表被抑制（reason_code=unknown_evidence）——**图表丢失** |
| 洞③ | 创建 run 带非空种子证据，用户在 A2 审核只改研究问题 | L274 的覆盖循环把 A1 完整证据包**替换成裸种子**——A1 采集与标准化全部丢失，A2/A3 静默分叉（2026-09-02 的空列表特判只挡住空列表，挡不住非空种子） |

根因唯一：**证据有两个写者**（A1 的 fuse_evidence 和 A2 的审核编辑），而 `input_data.evidence_items` 无法区分"创建时的种子"与"A2 审核的编辑"。

### 1.3 为什么不打同步补丁

任何"A2 编辑后同步给 A3"的方案都在承认两个写者，然后打补丁追平——逻辑重复、永远有漂移风险。正确做法是**消灭第二个写者**：A1 是证据唯一所有者，A2/A3 是纯消费者，池分叉在结构上不可能发生。用户在 A2 阶段要求改数据时，应回到 A1 修改（合法通道见 §6）。

---

## 2. 方案原则

**证据单写者（Single Writer）**：

- A1 独占证据的采集、融合、标准化输出；
- A2 的 `DataInterpretReviewEdits` 白名单删除 `evidence_items`——越权提交在契约层被硬拒绝（`ContractModel` 的 `extra="forbid"`）；
- A2 的修订覆盖循环不再触碰证据字段——A2 分析池在任何 revision 下恒等于 A1 证据包；
- A3 零改动——它本来就只认 A1，原"缺陷"变成"正确设计"。

由此得到全程不变量：**A2 分析池 ≡ A3 图表池 ≡ A1 证据包**。

## 7. 二期衔接：审核门 LLM 意图判别（所有者构想，本期不实现）
