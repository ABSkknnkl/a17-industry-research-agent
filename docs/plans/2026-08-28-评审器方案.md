# 评审器方案：Agent 4 写作提示词优化 + 可读性评审器

## 目标

解决 Agent 4（章节写作）产出"句子不通顺、人类难以读懂"的问题。方案分两层：

1. **生成端治本**：优化 `prompt.md` 写作规则，让句子"天生通顺"；
2. **评审器兜底**：确定性 Linter 做锚 + LLM 软分评审做补充，发现生成端漏网的难读段落，转人工或触发定点改写。

## 核心原则（不可违反）

1. **评审器只"发现"，不"落笔"**——修改正文永远由 Agent 4（重新生成）或人工（`manual_edits`）执行。
2. **软硬门分离**——可读性结果绝不写入 `ChapterQualityReport.passed`；`passed` 仅由确定性 `audit` 规则决定。
3. **输入隔离**——LLM 评审器只喂 `paragraph.text` 与 `kind`，不喂 summary、标题、自我评价或人工 comment，防止自夸文本带偏打分。
4. **重写上限**——同一段落最多触发 N 轮改写（默认 2，与 `_MAX_REVISIONS_PER_CHAPTER` 对齐）；达到上限转人工，绝不无限打回，也不静默放行。
5. **9:1 混合裁判**——能确定性判断的交给 Linter 规则；LLM 只处理规则判不了的"通顺、通俗、连贯"软维度。

## 架构总览

```text
                  ┌──────────────────────────────────────────────────┐
 Agent 4 生成端    │ generate → audit(合规硬门) → review(可读性软门)    │
                  └──────────────────────────────────────────────────┘
                              │                        │
                     证据/红线/结构规则           ReadabilityLinter（确定性锚）
                     决定 quality.passed       + ReadabilityLLMReviewer（软分）
                              │                        │
                              ▼                        ▼
                    WAITING_REVIEW / COMPLETED    findings → 定点改写(有上限) → 转人工
```

模型分工：

| 角色 | 模型 | 说明 |
| --- | --- | --- |
| Agent 2 / Agent 4 | 全局 `LLM_MODEL`（Qwen 系） | 保持两家智能体中文行文口径一致 |
| 评审器 LLM | 独立配置位 `LLM_JUDGE_MODEL` | 默认等于 `LLM_MODEL`，为将来换供应商留口 |
| 仲裁模型 | 暂不引入 | 仅当"judge 与人工抽查一致率 < 80%"等指标触发时，引入第二模型做分歧仲裁 |

# 写作规则

## A. 表达基调与合规
1. 使用专业、克制、可核验的证券行业研究表达。
2. 先写结论，再写证据，最后写限制条件。
3. 区分事实、分析推断、情景假设和风险提示，不得混为一谈。

7. 跨市场比较必须保留币种、会计准则、报告期和证券类型差异。
8. 如果口径不可比，应明确说明，不得直接排名。
9. 章节之间可以引用相同事实，但不得生成相互冲突的数值或结论。

## B. 句子与段落结构（可读性硬规范）
10. 每个 analysis 段落遵循"三句式"骨架：①结论句（不超过40字）→②证据句（1~2句，绑定 claim_id 与 evidence_id）→③限制或边界句。一句只承担一个职责。
11. 单句不超过45字；超过必须拆分为两句，用句号断开。
12. 禁止双主语与句式杂糅：不得出现"由于……使其……""通过……从而……""随着……使得……""经过……使得……"等结构。

14. 每段聚焦一个论点；一段内不得堆叠三个以上互不从属的要点。

## C. 术语与受众
15. 专业术语首次出现时，须用一句白话解释其含义；受众为非专业人员时必须解释全部关键术语。
16. 不得为显专业而堆砌术语；单句术语密度过高视为堆砌。
17. 不得输出自我评价或自夸语句，如"本报告深入剖析""我们严谨地认为"。
18. 输出内容应适合专业投研报告，同时保证具备行业常识的读者能够读懂。

## D. 负面示例与改写示范
负面示例一（裸标签拼接，禁止）：

"样本企业数量为10家；鉴于样本仍需扩充，该结论的适用范围有限。"

负面示例二（双主语病句，禁止）：
"由于光伏产业链利润池向中游迁移使其议价权增强。"

- 规则与 prompt.md 写作规则 B/C 段一一对应（R1↔规则12、R2↔规则11、R3↔规则17、R4↔规则16、R5↔规则13）。

### 2.2 实现代码

```python
"""Deterministic readability linting for chapter paragraphs.

Pure, dependency-free rules that flag objectively poor readability. This is the
rule-verifier "anchor" in the 9:1 judge design: it only emits findings and never
decides quality.passed or stage status, so it is safe to run on any paragraph.
"""

from __future__ import annotations

import re
from dataclasses import dataclass

# 中文句末标点切分
_SENTENCE_SPLIT = re.compile(r"[。！？；!?]")
MAX_SENTENCE_CHARS = 45

# R1 双主语 / 句式杂糅
_DOUBLE_SUBJECT_PATTERNS = (
    re.compile(r"由于[^。！？；]{0,30}使其"),
    re.compile(r"由于[^。！？；]{0,30}让"),
    re.compile(r"通过[^。！？；]{0,30}从而"),
    re.compile(r"随着[^。！？；]{0,30}使得"),
    re.compile(r"经过[^。！？；]{0,30}使得"),
)

# R3 自我评价 / 自夸
_SELF_PRAISE = ("本报告深入", "本文严谨", "我们严谨地", "深入剖析")

# R4 金融术语词表（堆砌检测）
_JARGON = (
    "估值锚", "利润池", "景气度", "咽喉节点", "护城河",
    "议价权", "信用利差", "久期", "贝塔", "阿尔法",
)
_JARGON_THRESHOLD = 3

# R5 裸标签拼接：句号后紧跟 2~6 字中文标签 + 冒号
_BARE_LABEL = re.compile(r"。[\u4e00-\u9fa5]{2,6}：")


@dataclass(frozen=True, slots=True)
class LintFinding:
    rule_id: str
    dimension: str   # 通顺度 / 通俗度 / 连贯性 / 客观性
    severity: str    # must_fix / suggest
    reason: str
    snippet: str


def lint_paragraph(text: str, *, kind: str = "analysis") -> list[LintFinding]:
    findings: list[LintFinding] = []
    findings.extend(_check_double_subject(text))
    findings.extend(_check_sentence_length(text))
    findings.extend(_check_self_praise(text))
    findings.extend(_check_jargon_stack(text))
    findings.extend(_check_bare_label(text))
    return findings


def _check_double_subject(text: str) -> list[LintFinding]:
    for pattern in _DOUBLE_SUBJECT_PATTERNS:
        match = pattern.search(text)
        if match:
            return [LintFinding(
                rule_id="R1_DOUBLE_SUBJECT", dimension="通顺度", severity="must_fix",
                reason="双主语/句式杂糅，主谓搭配混乱", snippet=match.group(0),
            )]
    return []


def _check_sentence_length(text: str) -> list[LintFinding]:
    for sentence in _SENTENCE_SPLIT.split(text):
        sentence = sentence.strip()
        if len(sentence) > MAX_SENTENCE_CHARS:
            return [LintFinding(
                rule_id="R2_SENTENCE_TOO_LONG", dimension="通顺度", severity="suggest",
                reason=f"单句超过{MAX_SENTENCE_CHARS}字，应拆分", snippet=sentence[:20] + "…",
            )]
    return []


def _check_self_praise(text: str) -> list[LintFinding]:
    for phrase in _SELF_PRAISE:
        if phrase in text:
            return [LintFinding(
                rule_id="R3_SELF_PRAISE", dimension="客观性", severity="must_fix",
                reason="包含自我评价/自夸语句", snippet=phrase,
            )]
    return []


def _check_jargon_stack(text: str) -> list[LintFinding]:
    for sentence in _SENTENCE_SPLIT.split(text):
        hits = [term for term in _JARGON if term in sentence]
        if len(hits) >= _JARGON_THRESHOLD:
            return [LintFinding(
                rule_id="R4_JARGON_STACK", dimension="通俗度", severity="suggest",
                reason=f"单句堆砌{len(hits)}个专业术语且未解释", snippet="、".join(hits),
            )]
    return []


def _check_bare_label(text: str) -> list[LintFinding]:
    match = _BARE_LABEL.search(text)
    if match:
        return [LintFinding(
            rule_id="R5_BARE_LABEL", dimension="连贯性", severity="suggest",
            reason="用裸标签机械拼接句子，缺少逻辑衔接", snippet=match.group(0),
        )]
    return []
```

### 3.1 Schema

```python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field


class ReadabilityContract(BaseModel):
    model_config = ConfigDict(extra="forbid")


class ReadabilityFinding(ReadabilityContract):
    rule_id: str | None = None      # Linter 命中时填写（如 R5_BARE_LABEL）
    locator: str                     # 定位：P-04-01-01 或 SEC-04-01
    dimension: Literal["通顺度", "通俗度", "连贯性", "客观性"]
    severity: Literal["must_fix", "suggest"]
    reason: str                      # 具体哪里读不懂
    rewrite_hint: str                # 建议修改方向（供 Agent 4 / 人工参考）


class ReadabilityReport(ReadabilityContract):
    paragraph_id: str
    score: float = Field(ge=0, le=1)             # LLM 软分，1 为完全可读
    findings: list[ReadabilityFinding] = Field(default_factory=list)
    needs_human_review: bool = False             # 软分过低或达到改写上限
```

## Task 4：评审节点接入 chapter_writer graph

**Files:**
- Modify: `backend/app/agents/chapter_writer/graph.py`
- Test: `backend/tests/agents/chapter_writer/test_readability_reviewer.py`

### 4.1 挂载方式

与确定性 `audit` 节点分离，新增独立 `review` 节点：

```text
generate → audit(合规硬门) → review(可读性软门) → 路由
              ↓没过→revise              ├─ 无 findings → accept
                                        ├─ 有 findings 且未达改写上限 → 定点改写
                                        └─ 达上限/软分过低 → needs_human_review
```

### 4.2 关键逻辑

1. `review` 只处理 `kind == "analysis"` 的段落（正文论述），`summary`/`key_points` 暂不评审，控制成本。
2. `review` 输入隔离：仅 `paragraph.text` + `kind`。
3. `quality.passed` 仍只由 `issues`（确定性规则）决定；`finalize` 不变。
4. 评审 findings 通过 `readability_reports` 独立字段进入 `ChapterWritingResult`。
5. 达到 `READABILITY_MAX_REWRITES` 或 `score < READABILITY_THRESHOLD` 时，产出 `ChapterCollaborationRequest`（`request_id="READABILITY"`）触发人工，而非静默放行或无限卡死。
6. 定点改写复用既有 `target_section_ids` 机制（可扩展到段落级），Agent 4 只重写被标记的段落。

## Task 6：人审结合与防作弊运营

### 6.1 评审 findings 与人工闭环的结合

评审器产出 findings（带 locator + rewrite_hint）进入审核界面，用户二选一：

| 用户行为 | 路径 |
| --- | --- |
| 认可评审建议 | 把 rewrite_hint 并入 `instruction` → Agent 4 定点重写该段落 |
| 用户自有措辞 | 走 `manual_edits`（key 为段落 id）直接替换文本 |

改完后评审器复跑该段落，确认达标才算过（外部验真，防止"改了白改"）。

### 6.2 防作弊运营（LLM-as-Judge 防护）

1. **Linter 做锚**：大部分判断是确定性规则，LLM 只占小头。
2. **输入隔离**：见 Task 4。
3. **人工抽查回流**：定期抽样标注 judge 与人工的一致率；一致率 < 80% 时触发引入仲裁模型（如 DeepSeek 系）做分歧样本交叉仲裁——由指标触发，不预先引入。

### 6.3 验收

- [ ] 评审 findings 在审核界面可见且可定位到段落。
- [ ] 采纳建议 / manual_edits 两条路径均可用现有 review API 表达。
- [ ] 人工抽查一致率指标有落点（可先以日志/统计形式起步）。
