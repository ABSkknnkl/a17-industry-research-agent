## 0. 一句话结论

这次 `required_data_unavailable` **不是"技能太少"，也不是"路由模型不行"，而是意图拆解粒度缺陷 + 泛称实体未解析 + 个别真数据缺口三件事叠加**。修复分三期：P0 修拆解与查询构造（本周，纯代码）；P1 建观测与仲裁（两周，数据驱动）；P2 才轮到模型训练与联网搜索（按 P1 数据决定是否启动）。

**不要做的事**：不要急着加技能、不要急着接联网搜索、不要急着训练路由模型。这三个动作都治不了本次 bug 的主因。

## 1. 故障复盘：9 条待澄清的真实成因分类

对光伏任务前端展示的 9 条待澄清逐条归因（依据：`service.py:808-888` 的 `_apply_unresolved_intent_gaps` / `_build_partial_intent_results` 代码路径 + 前端路由表）：

### 成因 A：裸实体碎片不可路由（拆解粒度 bug，占 4 条）

现象：

> 【无法处理】"隆基绿能"、"晶科能源"暂无对应查询技能，请修改后重试。

关键证据：同一问题内 **"天合光能组件出货量"拿到了 18 条数据**，"市场份额对比"也执行了。三家公司同为 company 实体，待遇不同。

机制：

1. 问题"隆基绿能、晶科能源、天合光能组件出货量与市场份额对比？"被拆成 4 个子需求碎片；
2. 其中"隆基绿能""晶科能源"是**只有实体、没有指标**的碎片；
3. 能力注册表（`skill_capabilities.py`）中每个技能都要求"实体 + 指标类型"组合：`FINANCE` 要 company+financial，`BUSINESS` 要 company+business。**裸实体没有指标类型，任何技能的能力边界都匹配不上**；
4. `service.py:796-797` 把 `candidate_skills` 为空的碎片记入 unresolved，最终渲染为"暂无对应查询技能"。

定性：**这是拆解器把"并列实体"错误地拆成了独立子需求**。正确语义是"隆基绿能【的】组件出货量与市场份额"——指标应从同问题的兄弟碎片继承。**加再多技能也接不住裸实体**，因为它没说要查什么。

### 成因 B：分析型诉求被误当取数需求（意图类型缺失，占 1 条）

现象：

> 【无法处理】"其对组件成本的影响"暂无对应查询技能。

机制："X 对 Y 的影响"是**分析问题**，应由 Agent 2 拿着已采集的价格数据去推理，不是任何数据技能能"查"出来的。`LLMSubRequirement.intent_type` 枚举（`semantic_router.py:138-152`）有 13 种意图类型，**全部是取数型意图，没有 analysis/causal 类型**；确定性层只有 `_is_presentation_directive`（过滤"画成折线图"这类展示指令），没有因果型过滤。

定性：意图分类体系缺一个 `analysis_only` 出口，导致分析诉求被硬塞进数据路由碰一圈再报错。

### 成因 C：泛称实体未解析导致空调用（查询构造缺陷，占 5 条）

现象：

> 未查询到足以完成"指定指标：出货量/产能利用率/营业收入/净利润/毛利率"的数据。相关检索任务未返回可用数据。

机制：第 4 问"光伏组件行业**主要企业**营业收入、净利润及毛利率变化趋势？"路由成功（→ `hithink_finance_query`），但"主要企业"是**泛称**，查询构造时未展开成具体公司名单，问财接口不知道查谁，返回空或清洗后全被隔离。

定性：**路由没错，是查询构造时实体未落地**。这类失败可以从运行详情的 `skill_calls`（各技能行数/错误码）和 `quarantined_records`（被隔离行）进一步区分"源没返回"还是"返回了被洗掉"。

### 成因 D：静默降级为行情数据（2026-09-01 真实接口实测发现，比空返回更危险）

用真实问财接口探测"出货量/产能利用率"的可得性，发现一种**不报错、但会污染证据**的失败：

| 探测                                   | 返回                                  |
| ------------------------------------ | ----------------------------------- |
| `hithink_business_query` "隆基绿能组件出货量" | 1 行，列 = `股票代码/股票简称/最新价/最新涨跌幅/大单卖出量` |
| `hithink_business_query` "隆基绿能 销量"   | 1 行，列 = `成交量/成交额/振幅/换手率/最新价/最新涨跌幅`  |
| `hithink_basicinfo_query` "隆基绿能产能"   | 0 行                                 |

即：**问财没有公司级（个股）的出货量/产能利用率结构化字段，查询会静默回退到行情数据**。这个结果行数 > 0、能过清洗、能进证据池——Agent 2 会把它当"查到了出货量"，实则是当日行情。空返回会被 `data_gaps` 捕获并披露，**静默降级不会**。

问财**有**产业级（行业/宏观维度）数据，但存在口径陷阱：

| 探测                                     | 返回                                                                  |
| -------------------------------------- | ------------------------------------------------------------------- |
| `hithink_industry_query` "光伏组件行业产量 产能" | `光伏组件:产量:合计` 725,900 兆瓦（年度，中国）                                      |
| `hithink_industry_query` "光伏组件行业产能利用率" | `光伏利用率:全国:当月值` 月度序列（2025-09\~2026-01：95.0/94.8/93.7/94.6/94.3，单位 %） |
| `report_search` "隆基绿能 组件出货量"           | 10 条研报命中（公司级数据只能走这条定性通道）                                            |
| `industry_chain_analysis` "光伏组件产业链"    | 7 行（业务收入/成本/利润占比 + 行业数据）                                            |

口径陷阱：搜"产能利用率"命中的是**发电侧消纳利用率**，不是制造业产能利用率。指标名相似、语义不同，必须靠口径标注和证据分级拦住。

定性：这是"技能返回成功但字段不对"的一类错误。现行 quality gate 只查空结果、有效性、一致性，**没有字段相关性校验**。已列入 P0（见 P0-6）。

### 真正的数据缺口（本次基本不涉及）

"多晶硅料价格走势"经 `hithink_futures_query` 已取 20 条——说明期货价格域不缺技能。本次 9 条澄清里**没有一条**是"该有而没有的数据技能"。

## 2. 外部项目实证研究（2026-08-31 实际调研，非转述）

本节是对 6 个候选项目的实际研读结论。每条都给出"它到底是什么、能抄什么、**不能抄什么**"。

### 2.1 liangyuzhe/financial-copilot-platform ★★★ 主参考

**它是什么**：LangChain+LangGraph 的企业财务 NL2SQL 平台。链路：自然语言 → 意图识别 → 证据召回 → 选表 → SQL 生成 → 人工审批 → 执行。与本系统的"意图 → 路由 → 采集 → 审核"四层结构几乎同构。

**可抄（3 条，全部进 P1）**：

1. **规则引擎与 LLM 并行仲裁**：意图规则存 MySQL 由 Admin 页面维护，规则引擎与 LLM **并行运行、最终由仲裁层收口**，明确"避免业务关键词硬编码进代码"。这直接回答"纯规则 vs LLM 谁说了算"——答案是并行 + 仲裁，与我们 L1/L2 分权一致。
2. **语义模型表外置**：`t_semantic_model` 存"业务名/同义词/描述"的字段级映射，权威源收敛到 MySQL/Redis。对应我们的 `metric_registry.py`——**别名表应从代码搬到配置/库表，改词不发版**。
3. **单次召回复用**：`recall_context` 每轮只召回一次，后续选表/SQL 生成复用同一状态。对应我们的澄清门——用户改写后的新查询应带上原 context，不要从零重跑。

**不能抄**：它是 NL2SQL（选表+生成 SQL），我们是 NL→数据技能路由，"选表画像""表关系自动发现"这些层对我们无意义。

### 2.2 aurelio-labs/semantic-router（3.8k★）★★ 方法参考

**它是什么**：utterance-embedding 路由器。每个 `Route` 挂一组 `utterances` 示例句（官方示例每路由约 5 条），编码进向量空间，查询按语义相似度匹配；`SemanticRouter(encoder, routes, auto_sync)` 调用后**低于阈值返回** **`None`，由业务层兜底**；阈值有专门优化流程（`docs/06-threshold-optimization.ipynb`，按路由分别训练阈值）；另有 `HybridRouteLayer`（稠密+稀疏混合）。

**可抄（2 条，进 P1）**：

1. **每路由独立阈值**：不要全局一个 0.90。`AGENT1_SEMANTIC_ROUTER_CONFIDENCE` 应按技能分别校准——`FINANCE` 和 `NEWS` 的边界模糊度完全不同。
2. **utterances 组织法**：每技能 5\~10 条代表性查询句（含正例变体），作为 L2 prompt 的 few-shot 或（P2 若转 embedding 路由）直接作 anchor 语料。

**不能抄**：它是纯 embedding 路由，无 LLM 分类器；我们的 L2（`OpenAICompatibleSemanticRouter`）是 LLM 分类，架构不同。它的 `None→fallback` 我们已有等价物（置信度不足走澄清门）。

### 2.3 Red Hat《Improve vLLM Semantic Router accuracy with fine-tuning》（2026-06）★★ 唯一训练方法论

原始 URL 已迁移，现行地址：`developers.redhat.com/articles/2026/06/02/improve-vllm-semantic-router-accuracy-fine-tuning`。实测数据（已从原文核实，与用户转述一致）：

| 阶段                                                     | 数量/指标                                                           |
| ------------------------------------------------------ | --------------------------------------------------------------- |
| 基线（all-MiniLM-L6-v2 预训练 embedding，4 类路由）               | 准确率 80%，错配率 \~20%                                               |
| seed anchors（手写，代表 SIMPLE/MEDIUM/COMPLEX/REASONING 四类） | 48 条                                                            |
| SDG 扩样（改写/领域迁移/边界用例/难负例，大模型生成+交叉校验）                    | 1,157 条 → 过滤后 1,009 条                                           |
| 训练/测试                                                  | 805 / 204                                                       |
| 训练方式                                                   | sentence-transformers，BatchAllTripletLoss 对比学习，**纯 CPU < 2 小时** |
| 结果                                                     | **98.53%，错配率 \~1.5%**                                           |

**关键结论（原文）**：预训练 embedding 的失败是结构性的——它理解"语义相似"而不理解"路由决策"，会把"描述详细的长 prompt"误判为"复杂任务"。解法是**让路由决策可学习：收集真实路由记录 → 评估 → 反馈训练**，而不是靠人拍脑袋加规则。

**对我们的适用性修正**：该结论直接适用于"用预训练 embedding 当路由器"的系统。**我们的 L2 是 LLM 分类器**（`semantic_router.py:56-124`，temperature=0、只能从 14 个 SkillName 枚举中选、带结构化校验），LLM 自带金融语义先验，不需要 805 条样本教它"出货量≈销量"。所以 Red Hat 路径对我们**是 P2 备选，不是 P0 必需**——触发条件见 §5 决策树。

### 2.4 findesk-ai/findesk-ffd-mcp（0.6.5）★★ 同构参照

**它是什么**：中文金融 MCP 服务器（A 股/基金/板块/宏观/资金流/新闻/研报），主打 **"smart routing, not tool sprawl"**——不做 200 个碎片工具，而是稳定高价值工具面 + 路由规划 + fallback 链。`ffd_route_plan` 返回推荐工具+参数+fallback；`ffd_capabilities` 做渐进式能力发现；失败消息要求"告诉用户下一步怎么办"（缺代码/字段错/试用到期/配额限制各有明确指引）。

**可抄（2 条）**：

1. **fallback 链作为一等公民**：每个路由结果带"主选技能 + 备选技能链"，主选空调用自动落备选——我们目前是"主选空 → 报缺口"，缺这一层。
2. **失败消息分门别类给行动指引**：澄清门文案应按失败类型（无技能/空调用/权限/限流）给出不同下一步，而不是统一"请修改后重试"。

**不能抄**：它是 MCP 工具服务器（卖数据订阅），不是意图拆解系统；它的路由是"问题→工具"，粒度比我们"子需求→技能"粗。

### 2.5 pywencai ★ 词表素材（**修正此前的错误推荐**）

**实测修正**：原仓库地址（github.com/pywencai/pywencai）当前 404（迁移或转私有）。更关键的事实是——**pywencai 没有内置指标同义词库**。它是瘦客户端：把自然语言透传给问财服务端 NLP，别名解析全部发生在服务端。**此前方案里"抄 pywencai 词表"的说法不成立，特此更正。**

**正确用法（进 P1）**：把问财当"别名解析服务"**反向建表**——

1. 拿候选别名（"出货量"/"销量"/"销售量"…）逐个调 `pywencai.get(query=..., query_type="stock")`；
2. 观察返回 DataFrame 的**列名**（即问财解析出的标准指标名）；
3. 沉淀"别名 → 标准指标"映射进我们的别名表；
4. 批量跑时注意限频（hexin-v token + `sleep`），结果需人工抽检。

`query_type` 覆盖：stock/zhishu/fund/hkstock/usstock/threeboard/conbond/futures——也可用来校验我们 SkillName 与问财数据域的对应关系。

### 2.6 lm-sys/RouteLLM（5.4k★）★ 只取一个结论

**它是什么**：强弱 LLM 间的成本路由器，4 种实现（matrix factorization / sw\_ranking / bert / causal\_llm），训练数据是 Chatbot Arena 5.5 万条人类偏好 + GPT-4 裁判增强。效果：成本降 85% 同时保持 95% GPT-4 性能。

**只取这一个结论**：RouteLLM 官方发现**路由器训练一次即可跨模型对泛化，换模型不需要重训，只需要按业务查询分布重新校准阈值**（`calibrate_threshold`）。这佐证了 §5 的立场——**"校准阈值"和"重训模型"是两件事，前者便宜且经常够用**。

**不能抄**：它路由的是"选哪个 LLM"，我们路由的是"选哪个数据技能"，问题不同构。

### 2.7 明确不看

FinRobot（7.9k★）、ai-financial-agent、DISC-FinLLM：端到端金融 Agent 框架，解决"有没有 Agent"，不解决"指标级路由精度"，看了只会带偏。litellm（57k★）只在 ToolGateway 增强时参考字段设计（成本/预算/重试），与路由无关，本方案不展开。

## 3. P0：bug 本体修复（本周，纯代码，6 项）

原则：每一项都对应 §1 的一个成因，可独立交付、独立回归。

### P0-1 裸实体继承兄弟碎片指标（治成因 A）

**改动点 1——拆解提示词**（`semantic_router.py` `_DECOMPOSER_SYSTEM_PROMPT`，第 246-264 行）加一条拆解规则：

```
5. 多实体对比/并列问题（"A、B、C的X指标对比"）必须将所有实体保留在同一个
   子需求内（entities 数组放全），禁止把单个实体拆成无指标的独立子需求；
6. "X对Y的影响/传导/关系/贡献"属于分析诉求，不是数据查询，不得生成取数
   子需求；若用户问题中只有分析诉求，将其写入 clarification_questions 说明
   "该诉求将由分析阶段基于已采集数据完成"。
```

**改动点 2——确定性兜底**（`intent_merger.py`，在 `_merge_llm_plan` 之后加一道后处理 `_inherit_metrics_from_siblings`）：

```python
def _inherit_metrics_from_siblings(plan: ResearchIntentPlan) -> ResearchIntentPlan:
    """同一 plan 内：candidate_skills 为空、有实体、无指标的子需求，
    继承兄弟子需求的指标与技能；无兄弟可继承时保持原样（走澄清门）。"""
```

规则：

- 触发条件：`not sub.candidate_skills and sub.entities and not sub.metrics`；

- 继承源：同 plan 内 `candidate_skills` 非空且 metrics 非空的子需求的并集；

- 继承后重跑 `capability_supports` 校验（继承来的技能必须支持该实体类型）；

- 全部继承失败 → 保持空，仍走澄清门（不静默吞掉）；

- 继承动作写 `warnings`（如 `metric_inherited_from_sibling:隆基绿能←组件出货量`），可审计。

**为什么两道都做**：prompt 规则管 LLM 拆解的新增路径，确定性兜底管确定性解析器（`deterministic_intent_parser.parse_intent` 按顿号切段同样会产生裸实体段）和 LLM 不听话的残留。**两道缺一不可**——只改 prompt 是概率修复，确定性层才是契约。

**回归用例**：输入"隆基绿能、晶科能源、天合光能组件出货量与市场份额对比？"，断言：澄清清单无"隆基绿能/晶科能源 暂无对应查询技能"；三个实体均出现在带 `hithink_business_query`/`hithink_stock_selector` 的子需求中。

### P0-2 分析型碎片识别（治成因 B）

**改动点**（两处）：

1. `intent_models.py` / `semantic_router.py` 的 `intent_type` 枚举增加 `"analysis_only"`；
2. `intent_merger.py` 加确定性识别（与 `_is_presentation_directive` 并列的 `_is_analysis_directive`）：

```python
_ANALYSIS_PATTERNS = re.compile(
    r"(对.{1,12}的(影响|传导|贡献)|带动|拉动|拖累|联动|弹性|敏感性|归因)"
)

def _is_analysis_directive(text: str) -> bool: ...
```

判定为 analysis\_only 的碎片：不进数据路由、不报"暂无对应查询技能"，而是记入 plan 的 `analysis_notes` 字段（透传给 Agent 2 作为分析提示；Agent 2 无视该字段也不影响现有契约）。

**注意**：正则只打高置信模式，拿不准的宁可送去路由（错配为取数需求的代价 < 误吞真实取数需求）。

### P0-3 泛称实体解析（治成因 C）

**改动点**（`planner.py` 查询构造阶段，加 `_resolve_generic_entities`）：

- 识别泛称词表：`主要企业|龙头|头部公司|同行|可比公司|代表企业|行业前列`；

- 解析路径：**优先**用已采集证据中的实体（本轮已查到的公司名集合）；**其次**调 `hithink_sector_selector`（板块成分，本来就在 P1 技能清单里）取该行业成分股按市值/龙头排序取前 N（默认 5，可配）；

- 解析失败（板块成分为空）→ 不静默降级为泛称查询，而是该子需求标记 `entity_resolution_failed` 走澄清门（"请指定具体公司"）；

- 解析结果写 `retrieval_plan.resolved_entities`，来源（证据推断/板块成分）留痕。

**回归用例**："光伏组件行业主要企业营业收入、净利润及毛利率变化趋势？"→ 断言 `hithink_finance_query` 的实际查询里含 ≥3 个具体公司名，且这些公司来自光伏板块成分。

## 4. P1：观测驱动的仲裁与词表外置（两周）

前提：P0-5 已积累 ≥2 周真实路由日志（或 ≥500 条有效记录）。

### P1-1 离线评测 harness（先于一切调优）

- 从 telemetry 日志构建评测集：`eval/routing_cases.jsonl`，每行 = {文本、人工标注的正确技能集、当时的系统决策、是否 miss}；

- 标注来源：澄清门里用户"改条件重跑"的改写对（原查询=错、改写=对）、人工抽标 100\~200 条；

- 回放脚本：`eval/routing_replay.py`，离线对 L1（注册表+关键词）与 L2（LLM 路由）分别跑，输出**分层准确率、错配率、miss 率、按技能分面的混淆矩阵**；

- 红线指标：**错配率 < 1%**（路由到错技能拿错数据编报告，比 miss 可怕得多）；目标：合并准确率 ≥ 95%。

### P1-2 并行仲裁层（抄 financial-copilot-platform）

当前是串行兜底（先注册表，未命中才 LLM）。改为：

```
子需求文本
  ├─ L1 确定性（注册表+关键词）── 出决策 + 命中强度
  ├─ L2 LLM 语义路由 ────────── 出决策 + 置信度
  └─ 仲裁器（新模块 arbiter.py）
        两路一致          → 直接放行
        仅 L1 有          → 放行（L1 是契约，天然可信）
        仅 L2 有          → 按该技能的分面历史准确率加权，
                            高于校准阈值放行，否则澄清门
        两路冲突          → 不硬选，进澄清门（列出两个候选让用户挑）
```

仲裁器的"分面历史准确率"就来自 P1-1 的混淆矩阵——**这是数据驱动，不是拍脑袋权重**。

### P1-3 词表外置（抄 t\_semantic\_model）

- 把 `metric_registry.py` 的 `aliases` 与 `_METRIC_TYPE_KEYWORDS` 合并为单一权威词表，落 SQLite（`data/` 已有库）或 YAML 配置；

- 代码启动时加载、支持热更新（改词不发版）；Admin 编辑界面暂不做，先脚本维护；

- 用 pywencai 反向建表法（§2.5）批量扩充别名，人工抽检后入库；

- 保留代码内一份只读兜底词表，库表不可用时 fail-closed 回退（与系统既有 fail-closed 哲学一致）。

### P1-4 分技能阈值校准（抄 aurelio threshold optimization + RouteLLM calibrate）

- 用 P1-1 评测集，对每个技能画"置信度-准确率"曲线，按技能分别定阈值，替换全局 `AGENT1_SEMANTIC_ROUTER_CONFIDENCE=0.90`；

- 产出 `config/routing_thresholds.yaml`，语义路由器按技能读阈值；

- 复跑评测集验证：错配率不升、miss 率下降。

### P1-5 澄清门体验分级（抄 findesk）

按失败类型给不同文案与行动项：

| 失败类型     | 文案要点           | 给用户的动作                    |
| -------- | -------------- | ------------------------- |
| 无匹配技能（真） | "该指标暂无数据技能"    | 换指标说法 / 接受缺口继续            |
| 技能空调用    | "查到了技能但数据源未返回" | 换时间范围/公司 / 触发 fallback 技能 |
| 实体未解析    | "请指定具体公司"      | 输入公司名                     |
| 权限/限流    | "数据源配额/鉴权问题"   | 联系管理员，不重试                 |

### P1 验收

离线评测集：合并准确率 ≥95%、错配率 <1%；改词不发版（改库表后新查询即时生效）；澄清门 4 类文案上线。

## 5. P2 触发式演进与"要不要训练"决策树

**结论先行：埋点收集（P0-5）是必须的，模型训练当前不做。** 决策树（每个判断都有客观触发条件，不凭感觉）：

```
P1-1 离线评测结果
  │
  ├─ 合并准确率 ≥95% 且错配率 <1%
  │     → 不训练。持续每月回放监控，漂移超阈值再议。
  │
  ├─ 准确率 <95%
  │     → 第一步：查混淆矩阵，改 prompt / SKILL_CAPABILITIES 描述 / 词表
  │       （LLM 路由的错误 90% 是描述模糊，不是模型能力）
  │     → 复评仍 <95%？
  │         ├─ 否（达标）→ 不训练
  │         └─ 是
  │            → 第二步：检查是不是技能数膨胀（>20 个）或类间边界模糊
  │              → 是：启动 embedding 路由微调（Red Hat 路径）：
  │                 1) 每技能手写 10~20 条 seed anchors（utterances 组织法 §2.2）
  │                 2) LLM 扩样：改写/边界/难负例，交叉模型校验
  │                 3) sentence-transformers + BatchAllTripletLoss，CPU 训练
  │                 4) 与 LLM 路由器并行灰度：embedding 作主、LLM 作仲裁
  │                 5) 评测集上超过 LLM 路由才切主
```

**为什么现在不训练（三条硬理由）**：

1. **架构不适用**：Red Hat 的 80% 基线是"预训练 embedding 当路由器"——embedding 无业务先验才必须训练。我们的 L2 是 LLM 分类器（temperature=0、14 个枚举类、带结构化校验），金融语义先验内置；
2. **本次 bug 与模型无关**：成因 A/B 是拆解与类型体系缺陷，成因 C 是查询构造缺陷——训练一个更准的路由器，碎片该错还是错；
3. **成本不对称**：训练本身便宜（805 条/2 小时 CPU），但**训练管线**（标注规范、数据版本、模型管理、灰度回滚）是长期负债。RouteLLM 的实证（§2.6）也说明：先校准阈值，多数时候够用。

**P2 同时排期的联网搜索插件**（与训练无关，独立评审，红线不动）：

- 独立 `SkillName.WEB_SEARCH`，`SkillCapability(qualitative=True)` 注册进能力表；

- 走 ToolGateway（超时/预算/错误码/脱敏统一）；

- 证据**恒为最低层级**，报告强制披露"公开网页，未经交叉验证"；

- 只补定性内容（政策、竞争格局描述、技术趋势），**严禁填财务数值缺口**；

- 计入核心数据组完整性判定 = 否；

- 用结构化搜索 API（Tavily/博查），配域名白名单（交易所、公司公告页优先），不裸爬。
