# 架构评估报告：智能体并行化 与 功能封装为 Skill

- 日期：2026-09-07
- 评估对象：同花顺问财 SkillHub 五阶段报告生成系统（Vue3 + FastAPI + LangGraph）
- 评估方式：基于当前代码事实（附行号）与真实评测数据，不做空想式架构设计
- 范围：两项候选优化方案的改动风险、对大模型的影响、可行性结论与优先级

---

## 0. 结论先行

| 方案 | 风险评级 | 结论 |
|---|---|---|
| ① 智能体**全量并行化**（5 阶段改并行） | 🔴 **高** | **不建议**。依赖链决定无并行空间，唯一可并行点收益≈0，且破坏赛题核心的人机协同审核语义 |
| ①-改 阶段**内**并行（章节并行写 / 分段并行生成） | 🟡 **中** | **这才是真正的提速金矿**，收益显著，单独立项 |
| ② 功能封装为 Skill（确定性能力） | 🟢 **低**（A 档）/ 🔴 高（发布平台） | **推荐 A 档**，复用性收益大；平台发布后置 |

**一句话**：想提速，不要动"5 个智能体的编排顺序"，要动的是**单个智能体内部的串行 LLM 调用**（Agent 4 的 7 章、Agent 2 的 2 段）——这是收益最大、风险最小的切入点。

---

## 1. 现状基线：时间到底花在哪

先用实测数据说话。2026-09-06 真实 LLM 全链路评测（`docs/2026-09-06-agent1-4-real-llm-eval-report.md`），3 条用例耗时 **281s / 352s / 513s**。耗时构成按阶段拆解如下：

| 阶段 | 性质 | 耗时构成 | 代码证据 |
|---|---|---|---|
| ① 数据获取 Agent 1 | SkillHub 网络调用 | **内部已并发**（`Semaphore(4)` + `asyncio.gather`） | `executor.py:135,182,188` |
| ② 数据解读 Agent 2 | LLM | 分段 **2 段串行**，单轮 170–260s，超时 240s，最多 3 轮修复 | `openai_compatible.py:863`（for 循环依次生成）；`factory.py:33,37` |
| ③ 图表 Agent 3 | **确定性代码** | **秒级**，默认不生图 | `chart_generator/service.py:1` "Public deterministic StageAgent"；`config.py:103 INDUSTRY_CHAIN_IMAGE_ENABLED=False` |
| ④ 章节撰写 Agent 4 | LLM | **逐章串行写 7 章**，每章（写作 + 可选评审）最多 2 次 LLM | `chapter_writer/graph.py:293,608-611`（`current_index` 递增 + accept 路由回 generate）；`service.py:273` |
| ⑤ 报告融合 Agent 5 | **确定性代码** | 装配 + Playwright PDF | `report_fusion/service.py:1` "Deterministic Agent 5" |

**关键结论**：五个智能体里，**②④ 是 LLM 大头（分钟级），① 是网络大头（已并发），③⑤ 是确定性（秒级）**。串行的总时长 ≈ ① + ② + ④ 的 LLM/网络等待之和。

## 2. 方案一：智能体并行化

### 2.1 依赖矩阵：只有一个理论并行点，而它几乎不占时间

五阶段的真实数据依赖（全部有代码证据）：

```text
① 数据获取 ──证据包──▶ ② 数据解读
                            ├──chart_candidates──▶ ③ 图表
                            └──claims/dimensions/risks──▶ ④ 章节撰写（强依赖 ②，缺则 WAITING_REVIEW）
③ 图表 ──charts──▶ ④ 章节撰写（弱依赖：chart_result 为 None 时降级 planned_charts）
{①..④} ──────────────▶ ⑤ 报告融合
```

- **强依赖**：1→2（`chapter_writer/service.py:130-144` 明确"缺 Agent 2 分析结果则停"）；4→5；2→3/4。
- **唯一弱依赖**：3→4（`chapter_writer/service.py:163` 读 Agent 3 的 `charts`，但 `:49-50` 当 `chart_result is None` 时用 `planned_charts` 降级）。

所以**唯一能做"阶段间并行"的是 ③∥④**。但 Agent 3 是确定性秒级（默认连生图都关着），并行掉它**省下的是"秒"，不是"分钟"**——收益趋近于零，却要付出完整的并行编排成本。

**其他四个阶段无法并行**，不是因为"没做"，而是因为它们是**数据上下游**：解读要等取数，融合要等所有产物，这是流水线本身的性质，不是工程欠账。

### 2.2 收益测算（用实测数据算）

| 并行方案 | 理论省时 | 依据 |
|---|---|---|
| ③∥④（阶段间并行） | ≈ 秒级（Agent 3 本身耗时） | Agent 3 确定性，`INDUSTRY_CHAIN_IMAGE_ENABLED=False` |
| ④ 章节并行写（阶段内，7 章并发） | **≈ ④ 的 6/7**（7 章串行 → 最长 1 章） | ④ 是主要耗时源，逐章串行 7 次 LLM |
| ② 分段并行（阶段内，core∥supplement） | **≈ 一轮 LLM（170–260s）** | 两段同一输入、`payload.update` 合并，无依赖 |

对比结论：**全量并行化的收益≈0，而两个"阶段内并行"的收益占到了报告总耗时的绝大部分。**

### 2.3 "其他好处"的真实评估（避免被话术带偏）

| 声称的好处 | 本项目实际情况 | 判定 |
|---|---|---|
| 资源利用率提升 | 串行阶段空闲期是 **I/O 等待（等 LLM/网络）**，不是 CPU 空转；CPU 利用率本来就低 | ❌ 不成立 |
| 可扩展性 | 可扩展性来自"单进程内并发多任务"，LangGraph 已支持（每个 run 独立 `thread_id`）；**阶段并行≠吞吐扩展** | ⚠️ 与并行无关 |
| 容错/鲁棒性 | 并行引入"部分失败"语义（一个分支成功一个失败），反而**降低**终态可预测性 | ❌ 反效果 |
| 硬件利用 | 服务器若有多核，多任务并发（而非单任务内并行）才是正确路径 | ⚠️ 另议 |

### 2.4 风险评级：🔴 高（全量并行）

| # | 风险点 | 说明 |
|---|---|---|
| R1 | **状态合并冲突** | `workflow/state.py:20` 的 `stage_results` 是普通 dict **无 reducer**，`graph.py:133-134` 每个阶段各写自己的 key；LangGraph 并行分支同一步写同一 key 会抛 `InvalidUpdateError`。全量并行要重构整个图的数据流契约 |
| R2 | **破坏人机协同审核语义** | 赛题核心得分点是"**每阶段人工审核**"（`workflow/graph.py:318-324 review_gate`）。并行后两个阶段同时到 WAITING_REVIEW，审核门要么合并（粒度变粗）要么引入复杂的多门协调，直接削弱赛题卖点 |
| R3 | **审核/修订的级联语义丢失** | 现在的修订是"上游打回 → 下游过期重跑"（`revision` 递增）。并行后"部分阶段重跑、部分复用"的边界需要重定义 |
| R4 | **runtime 预算核算变复杂** | `graph.py:90` 每个阶段有 `asyncio.timeout` 与 RuntimePolicy 预算；并行阶段共享预算的记账规则要重做 |
| R5 | **评测回归成本** | V8 评测体系 101 用例 + 61 金标准全部按串行终态断言（`expected_stages/expected_handoffs`），改编排顺序会触发大面积用例重写 |

### 2.5 对大模型的负面影响（并行化特有）

| 影响 | 说明 | 证据/依据 |
|---|---|---|
| **并发调用限流（最大风险）** | 当前 LLM 供应商为火山方舟 `ark-code-latest`（Auto 路由到 deepseek-v4-flash），存在 RPM/TPM 配额。并行化会把单任务内的 LLM 调用从"串行 1 路"瞬间拉到"N 路并发"，触发 429 限流的概率陡增 | 评测期间曾靠 `concurrency=1` 规避 |
| **截断与漂移风险放大** | 项目有 B4/B5 截断史（thinking 未禁吃光 `max_output_tokens=8192`、flash 系空 evidence 漂移）。并发会提高同时触发这些问题的概率，且更难定位 | `openai_compatible.py:744`；`factory.py:37 max_repair=3` 已就位作安全网 |
| **上下文冲突** | 阶段间并行时，多个阶段同时读同一 `stage_results` 快照——读无冲突，但**写冲突是实打实的**（R1） | `state.py:20` |
| **输出稳定性** | 并行本身不改变单次调用质量，但把"串行可预测的失败面"变成"部分成功部分失败"的集合，终态更不确定 | 2.3 |

**结论**：并行化对大模型不是"零影响"，而是**把系统推向了供应商限流与自身截断史这两个已知故障点的叠加区**。

### 2.6 真正值得做的提速点（按性价比排序）

既然"阶段间并行"不可取，但"并行"思路本身有真金，落在**智能体内部**：

| 优先级 | 改动 | 收益 | 风险 |
|---|---|---|---|
| ⭐ P0 | **Agent 4 章节并行写**：7 章从串行改并发（章节间本就通过固定大纲解耦，`chapter_ids` 列表可 `asyncio.gather`） | 省 ④ 的 6/7 时间 | 中——需验证章节间无交叉引用（术语/口径一致性由 finalize + 评审器兜底） |
| ⭐ P1 | **Agent 2 分段并行**：core 与 supplement 两段同输入、无依赖（`openai_compatible.py:863` 的 for 循环改 gather） | 省一轮 170–260s | 中低——两段 schema 独立，仅需保证 `_validate_payload` 合并顺序 |
| ✅ 已做 | Agent 1 内部并发（Semaphore=4） | — | — |

> 注意：这两个改动**都发生在单智能体内部**，完全不碰五阶段编排、不碰审核门、不碰赛题人机协同语义——是"安全并行"。

## 3. 方案二：功能封装为 Skill

### 3.1 候选模块分级

按"是否确定性、是否可独立复用、发布通道"分三档：

| 档 | 模块 | 现状 | 封装价值 |
|---|---|---|---|
| **A 档（确定性能力，推荐）** | `calculations.py` 财务计算（20+ 指标，注释明写"模型永不执行这些计算"） | 已被 Agent 2 内部调用 | 复用性最高，零 LLM 成本，可跨系统共享 |
| | `anomaly.py` 异常检测（3σ/IQR/突变） | 同上 | 同上 |
| | `normalizer.py` 清洗/单位归一 | Agent 1 内部 | 通用数据工程能力 |
| | `reconciliation.py` 口径对账（币种/单位/期间/审计） | Agent 2 内部 | 金融域通用 |
| **B 档（半确定性，中风险）** | `chart_generator` 图表 spec 生成 | 确定性 | 可复用于其他报告系统 |
| | `readability_linter` 可读性评审器（10 规则） | 确定性 + LLM 软分 | 评审能力可独立售卖/复用 |
| | `metric_registry` 指标路由词表 | 确定性 | 金融指标语义资产 |
| **C 档（发布到同花顺 SkillHub 平台）** | 上述任一，走平台发布 | — | 对外生态价值，但受合规与契约约束 |

### 3.2 风险评级

| 档 | 风险 | 风险点说明 |
|---|---|---|
| A 档 | 🟢 低 | 已是确定性纯函数，边界清晰；唯一风险是"抽象成通用接口"时丢失本项目特有约束（如 `research_as_of` 前视防护、口径标签） |
| B 档 | 🟡 中 | 评审器/图表 spec 依赖本项目 schema，抽象需重新定义输入输出契约 |
| C 档 | 🔴 高 | 平台发布涉及：金融合规审查（买卖建议红线）、平台技能契约对齐、密钥/授权分发、技能版本管理、供应链安全。**不是技术问题，是流程问题** |

### 3.3 对大模型的影响（这里几乎全是正面）

| 影响 | 方向 | 说明 |
|---|---|---|
| 上下文负担 | ✅ 减轻 | 确定性计算/异常检测的结果直接作为结构化输入注入（`data_interpreter/graph.py:116` 已有此模式），**模型不参与计算**，上下文更短、更稳 |
| 输出稳定性 | ✅ 提升 | 把"让 LLM 算"改成"调用确定性 Skill"，消除心算错误与口径漂移（这正是项目现有 `calculations.py` 的价值，封装后外溢到更多场景） |
| 幻觉 | ✅ 减少 | 确定性 Skill 输出不受 temperature 影响，天然防幻觉 |
| 唯一注意点 | ⚠️ | Skill 若返回大体积数据，注入上下文会撑爆（Agent 2 的"证据封顶 60 条"机制就是防线，封装时需保留类似上限） |

### 3.4 封装的真实收益（不是速度）

**要说清楚：封装成 Skill 本身不提速**（确定性功能本来就零 LLM 成本）。真正的收益是：

| 维度 | 收益 |
|---|---|
| **复用性** | 财务计算/异常检测/口径对账从"本项目私有"变成"任意 Agent（OpenClaw 生态）可调用"，一次实现处处用 |
| **维护性** | 职责单一、独立版本化、可独立测试（现在这些模块混在 Agent 内部，改一处要跑全链路回归） |
| **调用效率** | 若把当前仍由 LLM 做的活（如长尾指标语义路由 L2）下沉为确定性 Skill，则**省 LLM 调用 + 省钱 + 提速** |
| **生态价值** | 对应赛题"问财 SkillHub 技能生态"的题眼，封装是"从使用者变成贡献者" |

## 4. 综合可行性结论与实施优先级

| 优先级 | 事项 | 类型 | 理由 |
|---|---|---|---|
| **P0** | Agent 4 章节并行写 | 阶段内并行 | 收益最大（④ 是主要耗时源），不碰编排与审核门 |
| **P1** | Agent 2 分段并行生成 | 阶段内并行 | 省一轮 LLM（170–260s），改动小 |
| **P2** | A 档确定性能力封装为 Skill | 功能封装 | 低风险高复用，可与 P0/P1 并行推进 |
| **P3** | SkillHub 平台发布 | 功能封装（C 档） | 合规审查后置，技术已就绪 |

### 红线（不可触碰）

1. **任何提速都不得牺牲"每阶段人工审核"**——这是赛题的核心得分点，也是本系统区别于"端到端黑箱生成"的立身之本。
2. **任何并行都不得绕过"证据单写者"与"层级锁死"红线**——证据只能由 Agent 1 写入、层级只降不升。
3. **并发上限必须可配**——LLM 与 SkillHub 都有配额，并行收益要建立在"受控并发"（Semaphore 有界）之上，而非无脑放开。
