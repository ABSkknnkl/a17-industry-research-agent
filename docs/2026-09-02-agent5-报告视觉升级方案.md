# Agent 5 报告视觉升级方案（交付前端实施）

- 日期：2026-09-02
- 目标：让 Agent 5 合成的 HTML/PDF 报告从"能看"变成"能交付给客户"；同时建立一套**与前 4 个智能体解耦**的视觉测试闭环
- 读者：前端工程师（实施主体）；后端只需配合 §6 的夹具与 §7 的少量接口
- 关联文档：`docs/REPORT_VISUAL_DESIGN.md`（内容编排：何时用图/表/文字）、`docs/agent5-layout-generation-spec.html`（**版式样板，本方案的视觉基线来源**）

---

## 0. 一句话结论

**PDF 丑的根因不是"没设计"，而是"设计没落地 + 打印引擎能力被误判"**：项目里已经有一份很好看的版式样板（`agent5-layout-generation-spec.html`，含完整 design token 与组件），但它从没被应用到真正的报告模板上；同时现有模板里有一批 **Chromium 根本不生效的 CSS**（页码、水印），等于裸奔。

三条路线（前端选一条，我推荐 **B**）：

| 路线 | 做法 | 能拿到页码/页眉吗 | 工程量 | 风险 |
|---|---|---|---|---|
| A | 纯 CSS + Chromium 原生分页 | ❌ 拿不到 | 2-3 天 | 只能做"能看"，做不出券商研报质感 |
| **B（推荐）** | **引入 Paged.js 做打印分页 polyfill** | ✅ 页码/页眉/页脚/脚注/命名页全有 | 5-8 天 | 多一个前端依赖，需跑通无头渲染 |
| C | 服务端自行分页分块 | ✅ 全都要自己算 | 15 天+ | 高度计算易碎，维护成本高 |

**关于"让大模型写 HTML"：不要让它写整份 HTML**，具体判断与替代位置见 §4（推荐"LLM 生成 design token + 版式编排 plan，渲染仍是确定性模板"）。

## 1. 现状：链路与真实缺陷

### 1.1 三条产物同源，但视觉是两套

```
ReportViewModel (Pydantic, app/schemas/report.py)
   ├─ render_markdown()  → report_markdown → 前端 ReportReader.vue 用 marked 渲染 → 浏览器看到的
   ├─ render_html()      → report_html     → app/reporting/templates/report.html.j2
   └─ render_pdf(html)   → report_pdf      → Playwright Chromium，A4，print_background=True
```

**关键事实**：前端 `ReportReader.vue` 读的是 **markdown**，不是 HTML。所以浏览器里看到的样式和 PDF 完全是两套——你在前端 CSS 里改的东西，**PDF 一个像素都不会变**。这是第一个要拍板的架构问题（见 §8 开放问题 Q2）。

### 1.2 硬约束：Chromium 打印不支持 CSS Paged Media

`render_pdf` 用的是 Playwright Chromium（`app/reporting/pdf.py`）。Chromium 的打印实现：

| 特性 | Chromium 支持 | 现状模板里用了吗 |
|---|---|---|
| `@page { size/margin }` | ✅ | ✅ 用了 |
| `break-before/after/inside`、`orphans/widows` | ✅ | 部分用了 |
| `print-color-adjust: exact`（保留背景色） | ✅ | ❌ **没用**（背景色可能丢） |
| `@page { @bottom-center { content: counter(page) } }` | ❌ **不支持** | ❌ **用了，等于死代码** |
| `string-set` / `content: string()`（页眉抓章节名） | ❌ 不支持 | 未用 |
| `target-counter()`（目录页码） | ❌ 不支持 | 未用 |
| `position: fixed` 元素多页重复 | ❌ **只渲染在第一页** | ❌ **水印用了，只出现在封面** |

⇒ **现在导出的 PDF 里根本没有页码**，草稿水印也只在封面上。这两条是"看起来廉价"最直接的来源。

### 1.3 缺陷清单（按"丑的观感贡献"排序）

| # | 现象 | 根因 | 位置 |
|---|---|---|---|
| 1 | 没有页码、没有页眉页脚 | `@page @bottom-center` Chromium 不支持 | 模板 99 行 |
| 2 | 草稿水印只在封面 | `.draft-watermark{position:fixed}` 打印只渲染首屏 | 模板 45 行 |
| 3 | 长表格被跨页切断（来源索引 200 行必现） | 缺 `tr{break-inside:avoid}`；`thead{display:table-header-group}` 已有（这个做得对） | 模板 50-65 行 |
| 4 | 图表被切成上下两半 | `.chart` 只写了 `break-inside:avoid`，但外层 `figure` 与 SVG 高度在 print 下被 `max-height:78mm` 二次约束，实际会溢出 | 模板 36/113 行 |
| 5 | 中文两端对齐字距被拉爆 | `p{text-align:justify}` + CJK，Chromium 按 inter-character 拉伸 | 模板 23 行 |
| 6 | 7 列来源表在 A4 宽下溢出 | `table-layout:fixed` + 部分列 `white-space:nowrap`，中文宽字符撑爆 | 模板 55-63 行 |
| 7 | 目录无页码、且 `columns:2` 多列在分页处行为怪异 | 多列 + 无 `target-counter` | 模板 29-30 行 |
| 8 | 封面高度 `245mm` + 页边距，可能溢出到第二页留白 | A4 可印区高 297-14-16=267mm，245mm 加内容后临界 | 模板 104 行 |
| 9 | 整体"Bootstrap 默认感"：无阴影/无层次/无 KPI 组件 | 只有 8 个 CSS 变量，无设计系统 | 模板 8 行 |
| 10 | 图表配色硬编码在 Python SVG 里，前端改不动 | `app/reporting/svg.py:18` `DEFAULT_COLORS` 写死 | 后端 |

### 1.4 现成资产：spec.html 的视觉语言没被用上

`docs/agent5-layout-generation-spec.html` 本身是一份**已经做完设计的高质量样板**：

- 12+ design token：`--brand:#0b4fa3`、`--brand-2`、`--cyan`、`--success`、`--warn`、`--radius`、`--shadow`（`0 12px 36px rgba(31,57,91,.10)`）
- 封面：10px 品牌色顶边 + `linear-gradient(145deg,#fff 0 64%,#eef7fb 64% 100%)` 斜切渐变
- 组件：`.stat-grid`（数字统计卡）、`.matrix`（规整数据矩阵表，含 `.num` 数字列、`.note` 注释列、`.avoid` 反例列）、`.token`（令牌徽章）
- 排版：44px 标题 / 19px lead / 13px 正文辅文，层级清楚

**结论：前端不需要从零设计，把这套 token 与组件移植进报告模板即可**，这是最快的美化路径。

## 2. 目标与验收指标（可量化，别用"好看"当标准）

### 2.1 分页正确性（硬性，一票否决）

| 指标 | 目标 | 现在 |
|---|---|---|
| 每页有页码且连续 | 100% | ❌ 0%（无页码） |
| 表格行被跨页切断 | 0 处 | 长表必现 |
| 图表被跨页切断 | 0 处 | 存在 |
| 标题孤立在页底（orphan） | 0 处 | 未控 |
| 封面独占一页且不溢出 | 通过 | 临界 |
| 目录页码与实际页码偏差 | ≤1 页 | 无页码 |
| 内容溢出页边距（横向/纵向） | 0 处 | 宽表存在 |
| 背景色/图表色在 PDF 中保留 | 100% | 未设 `print-color-adjust` |

### 2.2 视觉质量（人评 + 可选机评）

- **人评 5 维**（1-5 分，≥4 分达标）：信息层级、留白节奏、配色质感、图表可读性、专业感（像不像券商研报）
- **盲测**：把新旧两版 PDF 混在 5 份同业研报里，找 5 个非项目同事排序，新版不应垫底
- **可选机评**：用 LLM 对 PDF 逐页截图打分（注意：只能当辅助信号，不能当门禁——见 §4）

### 2.3 工程指标

- PDF 渲染耗时 ≤ 现状 +30%（现在单次 Chromium 冷启约 1-3s）
- PDF 体积 ≤ 8 MB（超了要排查是否误嵌大图/全字库）
- 同一夹具重复渲染 2 次，PDF 二进制稳定（字体/时间戳除外）→ 保证产物可复现（`ReportArtifactManifestEntry` 里有 sha256，不能因为样式改动破坏可追溯性）

## 3. 三条实现路线（前端选一条）

### 路线 A：纯 CSS + Chromium 原生分页（2-3 天）

- 做法：重写 `report.html.j2` 的 CSS，用 `break-*` 控制分页；页码用"每章末尾页脚块"假页码或干脆不做
- 得到：配色/组件/留白大幅提升，但**没有页码、没有页眉**（Chromium 硬限制，CSS 无解）
- 适用：只要浏览器里好看、PDF 是附属产物

### 路线 B：引入 Paged.js（推荐，5-8 天）

- Paged.js 是 W3C Paged Media 的 JS polyfill，正好补上 Chromium 缺的那块：命名页（`@page chapter`）、页边距盒（`@bottom-center`）、`string-set` 页眉、`target-counter` 目录页码、脚注
- 做法：`render_pdf` 在 `set_content` 后注入 Paged.js（本地文件或 CDN，推荐**本地内联**避免网络依赖），等 `window.PagedPolyfill` 完成后再 `page.pdf()`
- 得到：**页码、页眉（章节名）、目录页码、脚注、水印每页重复**全部可用——这是券商研报的质感底线
- 代价：多一个依赖（约 200KB）；需处理"Paged.js 未就绪就导出"的竞态（用 `page.wait_for_function` 等分页完成标记）
- 后端配合点：`pdf.py` 需要支持"注入本地 JS 文件 + 等待就绪信号"，改动很小（见 §7）

### 路线 C：服务端分页（15 天+）

- 自己测高、切块、拼页；最可控但最易碎（字体度量、图片异步加载都会导致高度算错）
- 除非 B 路线在极端夹具下翻车，否则不建议

## 4. "要不要让大模型写 HTML"——我的判断

### 结论：不要让大模型写整份报告 HTML。让它写"皮肤参数"和"编排决策"，渲染仍交给确定性模板。

### 4.1 为什么反对（五条，按严重度）

1. **分页不可控（致命）**。LLM 看不见分页——它不知道这段文字会落在第几页、这张图会不会被切一半。分页是布局引擎算出来的，不是写出来的。LLM 写得再漂亮，PDF 里照样断得难看。
2. **破坏产物可复现**。`ReportFusionResult` 里每个产物都有 `sha256`（`app/schemas/report.py`）。LLM 生成 HTML ⇒ 同一份数据两次导出得到两个 PDF，报告作为交付物失去可追溯性，也过不了现有的产物校验。
3. **安全边界被绕过**。现在 `html.py` 是 `autoescape=True` + `StrictUndefined`，报告正文一律当不可信内容转义。LLM 写模板等于把这道边界交给概率。
4. **校验成本 ≈ 写模板的成本**。你还是得写一套校验器：HTML 是否闭合、有没有外链、有没有 `<script>`、有没有丢字段、分页有没有崩——这套东西的复杂度接近直接写模板。
5. **改样式的成本被放大**。改一个配色，现在改 1 行 CSS；LLM 方案要改 prompt + 重跑 + 重新校验，还可能有回归。

### 4.2 那 LLM 该待在哪（推荐位置，可多选）

| 位置 | LLM 干什么 | 输出物 | 风险 | 收益 |
|---|---|---|---|---|
| **① Design token 生成器（强烈推荐）** | 按行业/风格生成配色、字号阶梯、间距节奏 | 一个 JSON（几十个键值） | 极低（白名单校验键值范围） | 每份报告有"行业气质"：新能源青绿、金融深蓝、消费暖橙 |
| **② 版式编排 plan（推荐）** | 读章节内容，决定"这节用双栏/放 KPI 卡/图占半栏/表全宽" | 结构化 plan（章节 → 组件 + 尺寸） | 低（plan 走枚举校验，非法值回退默认） | 真正的"AI 排版"，且完全可控可回归 |
| **③ 图表皮肤参数（可选）** | 给 `svg.py` 输出配色/网格/标注密度参数 | 参数对象 | 低 | 图表与报告主色自动协调 |
| **④ 一次性主题 CSS（实验项，需沙箱）** | 直接生成一段主题 CSS | CSS 文本 | **中**：必须过沙箱 | 自由度最高，但要写校验器 |

**④的沙箱校验清单（如果要做，必须全过）**：
- 只允许 `CSS 变量` 与显式白名单选择器，禁止 `@import`、`url()`、`position:fixed`、`expression`
- 体积上限 8 KB
- 用 Chromium 实际渲染一次，捕获 console error 与 CSS parse 失败
- 对比度检查（正文 ≥ 4.5:1）
- 任一不过 → 静默回退默认主题（不要报错给用户）

### 4.3 关于"用 LLM 给 PDF 美观度打分"

可以当**辅助信号**，不能当**发布门禁**：LLM 对版式的审美不稳定，同一份 PDF 两次打分可能差 1 分。建议用法：人工评分为准，LLM 评分用来做"批量夹具的粗筛"（先机器过一遍 20 个夹具，人只看可疑的那几个）。

## 5. 视觉设计基线（给前端的具体指引）

### 5.1 Design token（从 spec.html 移植，前端可扩展）

```css
:root {
  /* 品牌与语义色 */
  --brand:#0b4fa3; --brand-2:#0b78b8; --cyan:#0da9d6;
  --ink:#142033; --muted:#607087; --line:#cad5e2;
  --soft:#f4f7fb; --paper:#fff;
  --success:#18794e; --warn:#9a6700; --danger:#b42318;
  /* 尺度 */
  --radius:10px; --shadow:0 12px 36px rgba(31,57,91,.10);
  /* 排版阶梯（屏幕 / 打印两套，见 5.2） */
  --fs-h1:44px; --fs-h2:28px; --fs-h3:20px; --fs-body:15px; --fs-note:12px;
  --lh-body:1.75; --measure:70ch;   /* 版心：单行不超过 ~35 个汉字 */
}
```

三套风格（`VisualStyle`：data_manual / analysis_note / deep_research）已有骨架，建议扩成完整主题包：

| 风格 | 语气 | 建议主色 | 字体 | 版心 |
|---|---|---|---|---|
| data_manual 数据手册 | 冷峻、数值优先 | `#17365d` 深蓝 | 无衬线 + 等宽数字 | 1120px，密度高 |
| analysis_note 分析笔记 | 平衡、亲和 | `#0b4fa3` 品牌蓝 | 无衬线 | 1040px |
| deep_research 深度研究 | 沉稳、论证感 | `#7c2d12` 赭石 | **衬线（Songti/Noto Serif CJK）** | 920px，行距大 |

### 5.2 双媒介：屏幕 vs A4（同一份 HTML 两种呈现）

| 项 | 屏幕（浏览器） | 打印（A4） |
|---|---|---|
| 版心 | `max-width:1040px` 居中，卡片圆角+阴影 | `max-width:none`，去阴影（省墨、更专业） |
| 正文 | 15px / 1.75 | 10.5-11pt / 1.6 |
| 页边距 | 页面留白 | `@page{margin:14mm 12mm 16mm}` |
| 背景 | `#eaf0f6` 页面底 + 白纸卡片 | 全白，`print-color-adjust:exact` 保住图表色 |
| 交互 | 目录吸顶、来源悬浮、图表放大 | 全静态（`text-decoration:none`） |
| 页码 | 不需要（连续滚动） | Paged.js 渲染 |

### 5.3 组件清单（建议前端先做这 9 个，做精比做多重要）

1. **封面**：品牌色顶边 + 斜切渐变 + 标题 + 一行 headline + 5 格元信息 + 视觉编排说明
2. **目录**：两列 + 点线引导 + `target-counter` 页码（Paged.js）；浏览器端可点击跳转
3. **KPI 卡片组**（新增，收益最高）：章节开头 3-4 个"关键数字"卡（数值 32px 等宽数字 + 标签 + 同比涨跌），这是研报"专业感"最便宜的来源
4. **结论块**：`.conclusion` 升级——左侧色条 + 置信度徽章 + 来源 chips + 不确定性说明
5. **正文段落**：首段可考虑"结论句加粗"，段间距 10px，首行不缩进（中文研报惯例）
6. **图表框**：`.chart` 加 §5.2 阴影（屏幕）/ 细边框（打印）+ 图表编号 + 来源脚注 + 分析目的
7. **数据表**：斑马纹、数字列右对齐 + `font-variant-numeric:tabular-nums`、表头重复、脚注行、单位行
8. **风险/不确定性框**：浅黄底 + 图标 + 圆角
9. **来源索引表**：7 列改 5 列（把"获取方式/层级"合并），超长文本 `overflow-wrap:anywhere`

### 5.4 分页控制清单（逐条加，逐条验）

```css
h1,h2,h3          { break-after:avoid; }        /* 标题不落单 */
.chart, figure    { break-inside:avoid; }
table             { break-inside:auto; }
tr, li            { break-inside:avoid; }
.uncertainty      { break-inside:avoid; }
.chapter          { break-before:page; }        /* 每章另起页（可选，见 Q6） */
p                 { orphans:2; widows:2; }
body              { print-color-adjust:exact; -webkit-print-color-adjust:exact; }
```

## 6. 测试隔离方案（这是本方案最有价值的部分）

### 6.1 为什么能隔离

`render_html(report: ReportViewModel) -> str`（`app/reporting/html.py:28`）是**纯函数**：输入一个 Pydantic 对象，输出 HTML 字符串，不碰数据库、不调 LLM、不访问网络。`render_pdf(html)` 只依赖 HTML 与 Chromium。

⇒ **只要有一个 `ReportViewModel` 的 JSON 夹具，就能完全跳过 Agent 1-4，直接验证 Agent 5 的视觉产物**。这正是你要的"前 4 个智能体数据全由大模型捏造、假定全正确"的隔离测试。

### 6.2 夹具矩阵（5 套，冻结进 git）

| 夹具 | 内容 | 用途 | 优先级 |
|---|---|---|---|
| `golden-photovoltaic.json` | 光伏组件，7 章 × 3 节，8 图，60 条来源，标准深度 | 主视觉基线 | P0 |
| `golden-baijiu.json` | 白酒消费，7 章 × 2 节，5 图，30 条来源，brief 深度 | 短报告/少图场景 | P0 |
| `golden-semiconductor.json` | 半导体，7 章 × 3 节，12 图（含 radar/heatmap/boxplot 复杂图），deep 深度 | 复杂图表类型全覆盖 | P0 |
| `stress-extreme.json` | 60 字标题、单章 21 节、30 图、200 条来源、20 行 × 8 列宽表、超长数字串、负数/百分比/单位混排 | **版式鲁棒性**（真实生产会遇到） | P0 |
| `degraded-dirty.json` | 空来源、0 图表、draft 水印模式、超短段落、quality issue 满配 | 降级场景不能崩 | P1 |

> ⚠️ **重要提醒**：只测"理想数据"会做出在生产上崩掉的版式。真实报告一定有数据缺口（你现在 P0 遗留的出货量/产能利用率缺口就是），`degraded-dirty` 夹具必须做。

### 6.3 夹具怎么造（LLM 造 → 校验 → 冻结）

```
1. 把 app/schemas/report.py 的 ReportViewModel 定义 + 一个最小示例喂给 LLM
2. 让 LLM 按行业主题生成完整 JSON（一次生成一份夹具）
3. 用 pydantic 严格校验：ReportViewModel.model_validate(json)  ← 过不了就重生成
   （注意约束：chapters 恰好 7 个；scenarios 恰好 3 个；chart_id 匹配 ^CHART-[\w-]+$；
     claim_id 匹配 ^C-[\w-]+$；placement_section_id 匹配 ^SEC-\d{2}-\d{2}$；
     svg 字段非空；evidence_ids 必须能在 evidence_catalog 里找到对应）
4. 人工审一遍"业务自洽"：数值不互相矛盾、结论有对应证据、行业常识不离谱
5. 冻结为 JSON 提交 git，之后只增不改（改了要重拍基线截图）
```

**SVG 从哪来**：夹具里的 `EmbeddedChart.svg` 可以直接用 `app/reporting/svg.py` 对已审计的 ECharts option 生成（复用真实渲染器，别让 LLM 手搓 SVG）。

### 6.4 视觉回归怎么做

```
render_fixture.py <fixture.json>
  → ReportViewModel.model_validate(...)
  → render_html()  → artifacts/visual/<fixture>/report.html
  → render_pdf()   → artifacts/visual/<fixture>/report.pdf
  → Playwright 逐页截图 → page-01.png ... page-NN.png
```

- **基线**：首轮人工确认后把截图存为基线（`artifacts/visual/baseline/`）
- **回归**：后续改动重跑，逐页像素 diff（可用 `pixelmatch`，阈值建议 ≤0.5% 差异面积）
- **人工门禁**：像素 diff 只告诉你"变了"，不告诉你"变好还是变坏"——每个迭代仍需人看一次完整 PDF
- **CI 建议**：挂 `nightly`，不挂 PR（PDF 渲染慢 + 容易因字体版本产生噪声）

### 6.6 分页硬指标怎么自动断言

PDF 侧能程序化检查的：

- **页数与页码**：用 `pypdf` 读页数；用 Paged.js 渲染时页码是真实文本，可提取校验连续性
- **表格/图表跨页切断**：这条**从 PDF 侧很难验**。更可靠的做法是在 HTML 侧断言——用 Playwright 在浏览器里跑一段 JS，遍历 `.chart`/`tr`，检查元素边界是否跨越了"虚拟页边界"（Paged.js 会给每页加 `.pagedjs_page` 容器，直接判断元素是否被 split 即可）
- **溢出**：检查 `document.documentElement.scrollWidth > pageWidth`
- **字体**：`page.pdf()` 后检查是否嵌入了中文字体（`pdffonts` 或 pypdf），没嵌 = 换机器必乱码

## 8. 需要前端拍板的开放问题（请逐条给结论，不要我替你决定）

**架构类**
- Q1. 页码/页眉页脚走哪条路线？（A 不做 / **B Paged.js** / C 服务端分页）
- Q2. **浏览器里到底该读 markdown 还是 HTML？** 现在前端读 markdown（`ReportReader.vue` + marked），PDF 走 Jinja 模板——两套视觉必然不一致。要不要统一成"前端也渲染 HTML 产物"？统一后 CSS 只要维护一份，但前端要处理 HTML 注入安全（建议 `DOMPurify` 或后端保证可信）。
- Q3. 设计单一事实源放哪？① CSS 内联在 `report.html.j2`（后端文件，前端改要跨仓）② **抽独立 `report.css` 被前后端共用** ③ 前端样式编译后注入后端。

**排版类**
- Q4. 正文两端对齐 vs 左对齐？（我的建议：**左对齐**，中文两端对齐在窄栏下字距会很丑，见 §1.3 #5）
- Q5. 单栏还是双栏？研报主流是单栏 + 边注/侧栏；A4 双栏会让图表被迫缩小。
- Q6. 每章是否强制另起一页？（现在是 `page-break-before:always`；好处是章节感强，坏处是留白多、页数涨 20%+）
- Q7. 页边距/版心：现在 14/12/16mm。要不要加大留白走"高端感"？（代价：页数增加）

**视觉类**
- Q8. 中文字体：系统字体（PingFang/雅黑，零体积但跨机不一致）vs 内嵌思源黑体/宋体（体积 +10~20MB，但任何机器都一致）？**PDF 交付给外部客户的话，我倾向内嵌**，你来评估体积可接受度。
- Q9. 封面要不要放主题图（AI 生成的行业概念图）？研报封面常见做法，但要控制体积与"AI 味"风险。
- Q10. 品牌元素：要不要放 logo / 公司名 / 分析师署名区？有没有现成品牌规范？
- Q11. 深色模式要不要做？（PDF 只能浅色，浏览器可以；做了又要维护一套 token）

**图表类**
- Q12. 图表皮肤谁管？① 后端 `svg.py` 改配色常量（改一处全局生效）② **前端用 CSS 覆盖 inline SVG**（`svg text{fill:var(...)}` 可行，但系列色要 `nth-child` 逐个覆盖，脆弱）③ 前端接管图表渲染（ECharts 在浏览器画，PDF 时再由后端 SVG 兜底）。
- Q13. 图表尺寸分级：主图全宽 / 次要图半宽 / 小图并排三列——这套规则谁来定？现在是全宽一刀切。

- Q16. 来源引用：现在是 `〔来源1〕` 静态文本，浏览器端要不要做悬浮显示来源详情（PDF 里只能静态）？做了又是两套呈现。

## 9. 风险与"不做"清单

**风险**
- Paged.js 在超长文档（>100 页）下分页耗时可能显著增加 → 用 `stress-extreme` 夹具实测
- 内嵌中文字体后 PDF 体积可能到 15-20MB → 先做子集化（只嵌用到的字形）
- 前端改的是后端 Jinja 模板 → 需要前后端约定改动流程，避免互相覆盖
- 视觉基线截图会因操作系统字体渲染差异产生噪声 → 基线必须在**同一台机器/同一个 Docker 镜像**里产出

**这轮明确不做**
- 不改 7 章 21 节的内容结构（硬约束）
- 不改 `ReportViewModel` 契约（除非 P3/P4 需要加字段，要单独评审）
- 不为了让 PDF 好看而牺牲产物可复现性（sha256 必须稳定）
- 不引入联网字体/CDN（离线渲染，现在 `svg.py` 也刻意无 CDN）
