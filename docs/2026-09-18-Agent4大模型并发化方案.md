# Agent 4（chapter_write）大模型并发化改造方案

> 目标：把 Agent 4 的 LLM 调用从串行改为并发，缩短阶段耗时。
> 基线：2026-09-18 代码状态。**所有事实均经实测核实（附行号）**，无推测成分。

|---|---|
| **可并行度** | **7**（章节数）。7 章之间**零依赖**，已核实 |

## 一、现状测绘（实测事实）

### 1.0 ⚠️ 首先：阶段有 600s 硬超时，串行已在危险边缘

`workflow/graph.py:88-104`：

```python
try:
    with runtime_session_scope(session):
        async with asyncio.timeout(runtime_policy.stage_timeout_seconds):   # ← 600s
            result = await registry.get(stage).run(context)
except TimeoutError:
    result = StageResult(stage=stage, status=StageStatus.FAILED,
                         data={"runtime_alert": {"code": "stage_timeout", ...}},
                         error="stage_timeout")
```

配置（`config.py`）：
- `STAGE_TIMEOUT_SECONDS = 600`
- `LLM_TIMEOUT_SECONDS = 600`（**单次调用超时与整阶段预算相同**）
- `LLM_MAX_OUTPUT_TOKENS = 8_192`
- `WORKFLOW_TIMEOUT_SECONDS = 2400`

**关键点**：这个超时在**阶段外层**，`chapter_writer` 自己的 `except Exception → build_fallback_writing`（`service.py:292-301`）**兜不住它**。

| 失败路径 | 结果 | 严重度 |
|---|---|---|
| 章节内部异常（如解析失败） | 单章降级 → 整份报告变兜底稿 | 中 |
| **阶段超时** | **`StageStatus.FAILED`，连兜底稿都没有** | **高** |

串行 7 章要在 600s 内完成 → **每章平均必须 < ~85s**（还没算修订轮）。一旦某几章偏慢或触发一次修复重试，就会撞线。

→ **并发在这里不是「优化」，是「保命」。** 这一条比加速比本身更重要。

### 1.1 串行执行链

Agent 4 用 LangGraph 表达，但**并行度为零**：整张图是一个**按 `current_index` 推进的逐章状态机**。

| 节点 | 位置 | 作用 |
|---|---|---|
| `generate` | `graph.py:289-343` | 处理**一章**：`chapter_id = state["chapter_ids"][state["current_index"]]`（`:293`）→ 1 次 LLM 调用（`:299`） |
| `audit` | `graph.py:345-355` | 纯 CPU 校验，无 LLM |
| `revise` | `graph.py:366-370` | 记录 attempt，回 `generate` |
| `accept` | `graph.py:459-504` | 写入 `chapters[chapter_id]`（`:481`）→ **持久化**（`:489`）→ `current_index + 1`（`:501`） |
| `finalize` | `graph.py:509-` | 汇总 |

边定义（`graph.py:587-613`）：

```
START → generate → audit → ┬ revise ──────────→ generate   （修订回环）
                           ├ review ─→ revise_readability → generate
                           └ accept → ┬ generate   （下一章：串行游标）
                                      └ finalize → END
```

`route_after_accept`（`graph.py:506-507`）：
```python
return "finalize" if state["current_index"] >= len(state["chapter_ids"]) else "generate"
```

**这就是串行点**：一章写完才启动下一章。

### 1.2 调用次数与修订上限

| 项 | 值 | 证据 |
|---|---|---|
| 默认路径 LLM 调用数 | **7**（每章 1 次） | `test_agent.py:208` `assert model.calls == 7` |
| 单章需修订时 | **8** | `test_agent.py:230/283` `assert model.calls == 8` |
| 每章修订上限 | **1** | `graph.py:37` `_MAX_REVISIONS_PER_CHAPTER = 1` |
| 可读性评审（**默认关闭**） | 21 次 | `service.py:103`「评审器默认不启用」；`test_readability_reviewer.py:129` `counting.calls == 21` |

→ **默认路径是 7 次串行 LLM 调用**，最坏 14 次（7 章各修订 1 次）。可读性软门是**第二个串行热点**（逐段循环 + `await`，`graph.py:388-407`），但默认不启用，可作二期。

### 1.3 关键：章节之间真的互相独立 ✅

`generate` 构造 prompt 只用这些输入（`graph.py:295-313`）：

```python
allowed_claims = select_chapter_claims(analysis, chapter_id, ...)   # 只看本章
build_chapter_runtime_prompt(analysis, chapter, charts=charts, options=options,
                             review_feedback=..., rejected_claim_ids=..., ...)
```

**不读任何其他章的草稿或产出** → 7 章可无依赖并行。

且累加器天然无顺序依赖：
- `chapters: dict[str, dict]`（`graph.py:71`）→ 按 `chapter_id` 写入（`:481`），**键不冲突**
- `finalize` 按 `REPORT_OUTLINE` 顺序取出（`graph.py:512-515`）→ **输出顺序与并发无关** ✅

这是本次改造成立的根本原因。

### 1.4 并发安全性逐项核实

| 项 | 结论 | 证据 |
|---|---|---|
| LLM 客户端 | ✅ **并发安全** | `openai_compatible.py:981-991` 用 LangChain `ChatOpenAI`（底层 httpx AsyncClient，为并发设计） |
| 结构化输出 Runnable | ✅ **无状态可重入** | `_structured_output`（`:286-297`）返回 `.with_structured_output()` 的 Runnable |
| 调用计数 | ✅ **原子** | `guard.py:93-102` check 与 `+= 1` 之间**无 await** → 单事件循环下原子 |
| 会话传递 | ⚠️ **ContextVar** | `guard.py:140` `ContextVar[RuntimeSession]`；gather 创建的子任务**复制引用** → 共享同一 session ✅（前提是 session 在 gather 之前建立） |
| 入站限流 | ✅ **不拦 LLM** | `rate_limit.py:39` 只用于 `api/routes.py` 的入站请求 |
| 模型调用耗时埋点 | ❌ **完全没有** | 只有工具调用有 `duration_ms`（`tool_gateway.py:217`、`data_fetcher/executor.py:492`） |
| **持久化并发** | ❌ **有写竞争缺陷** | 见 §1.5 |

### 1.5 ⚠️ 缺陷：SQLite 写竞争会让整个阶段失败

`ChapterRepository`（`chapter_repository.py`）现状：
- 每个方法**新开连接**：`async with aiosqlite.connect(self._db_path)`（`:35/52/74/86`）
- **未启用 WAL，未设 `busy_timeout`** —— 全仓 `journal_mode` / `WAL` / `busy_timeout` **零命中**
- 同一文件：`CHECKPOINT_DATABASE_PATH = ./data/checkpoints.sqlite`（`config.py:34`），全仓**只有这一个仓储**用它
- 主键 `(run_id, chapter_id, revision)`（`:24`）→ **逻辑上不冲突，但物理写锁会冲突**

而 `graph.py:485-486` 明确写着：

```python
# 持久化是接受章节的一部分：写入失败必须使阶段失败，不得静默跳过。
```

**后果**：并发写 7 个章节时，SQLite 默认 `busy_timeout=0`（立即返回 `SQLITE_BUSY`），一旦撞锁 → `sqlite3.OperationalError: database is locked` → 抛到 `service.py:290` → 被 `except Exception` 捕获 → **整份报告降级为确定性兜底稿**（`service.py:292-301`）。

即：**并发改造若不同时修这里，会把「慢一点」变成「整篇报告变成兜底稿」** —— 这是本方案最需要提前处理的项。

## 二、并发策略与实现思路

### 2.1 方案选型

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. 节点内 `asyncio.gather`（推荐）** | 把 per-chapter 链路（generate→audit→revise→持久化）抽成一个 async 函数，新节点 `generate_all` 并发调用 7 次 | ✅ 改动集中、可控、易加限流/埋点；图拓扑大幅简化（`START → generate_all → finalize → END`）<br>✅ 已核实**无测试锁图拓扑**，可安全重构 |
| B. LangGraph `Send` / map-reduce | 用 `Send` 为每章发一条并行分支，fan-in 到 collect | ⚠️ 需把 per-chapter 状态机改成 subgraph + 为 `chapters` 装 reducer（`Annotated[dict, merge_dict]`）；调试复杂度高、收益与 A 相同 |
| C. 外层多进程 | — | ❌ 无效：瓶颈是网络 I/O 等待，不是 CPU |

**推荐 A**，把 B 列为后续演进（若将来需要 LangGraph 级的 per-chapter trace）。

### 2.2 实现思路（方案 A）

```
START → generate_all → finalize → END

generate_all:
  sem = asyncio.Semaphore(settings.CHAPTER_WRITE_CONCURRENCY)
  async def write_one(chapter_id):
      async with sem:                      # 限流：保护供应商 TPM
          for attempt in range(_MAX_REVISIONS_PER_CHAPTER + 1):
              draft = await model.generate_chapter(...)   # 原 generate 逻辑
              issues = _audit_chapter(draft, ...)          # 原 audit 逻辑（纯 CPU）
              if not issues: break                          # 原路由逻辑
          await repo.save_chapter(...)                      # 原 accept 持久化
          return chapter_id, draft, issues

  results = await asyncio.gather(
      *(write_one(cid) for cid in chapter_ids),
      return_exceptions=True,              # ★ 关键：单章失败不取消其他章
  )
```

**四个设计要点**：

1. **`return_exceptions=True` 是必须的**。现有语义是「单章失败只降级该章」（`graph.py:321-338` 的 per-chapter fallback）。`gather` 默认在任一任务抛异常时**取消其余任务**，会破坏这个语义。要逐章判断结果类型，异常章走 `build_single_chapter_fallback`。

2. **`Semaphore` 定位是「安全阀」，不是「节流阀」**。今天 7 章就配 7 路全量并发 —— 7 个并发请求对任何商业 LLM API 都是微不足道的负载，**供应商侧不构成约束**（见 §4.3）。
   保留 Semaphore 的真实理由有两个：
   - **未来大纲扩容**：若 `REPORT_OUTLINE` 从 7 章增到 20 章，无上限 `gather` 会一次打 20 路。安全阀的意义在这里。
   - **故障放大抑制**：`max_retries=2`（`openai_compatible.py:987`）意味着失败请求会 ×3 重放。若供应商真的返回 429，限流能避免「重试风暴」。但这是**兜底**，不是默认档位。
   → 默认值给**全量并发**（`= len(chapter_ids)`），配置上限放宽（`le=16`）。

3. **`chapter_ids` 已支持子集**（`service.py:232-237` 的 `selected_chapter_ids`），并发只需对现有列表 gather，无需额外逻辑。

4. **`finalize` 不动**。它按 `REPORT_OUTLINE` 顺序取（`graph.py:512-515`），已是顺序无关的 ✅。

### 2.3 可读性评审（二期）
`review` 节点（`graph.py:388-407`）是「逐段 `await`」的双层循环，粒度比章节更细（fixture 21 段）。同样可 `gather`，且它只读单段文本、**无跨段依赖**。默认关闭，建议二期做。

## 四、性能提升预估

### 4.1 估算模型

设 7 章，第 i 章耗时 $t_i$（单次 LLM 生成 + 审计 + 持久化，**主要项是 LLM**），并发上限 $c$。

$$T_{serial} = \sum_{i=1}^{7} t_i \qquad T_{parallel} \approx \sum_{w=1}^{\lceil 7/c \rceil} \max_{i \in wave_w} t_i + T_{cpu} + T_{merge}$$

- $T_{cpu}$（audit 等纯计算）与 $T_{merge}$（gather 汇总）相对 LLM 延迟**可忽略**
- 修订轮次：最坏每章 +1 次，且在并发下也是**一轮并发**（不是 7 轮串行）

### 4.2 不同并发度（等耗时假设）

| 并发 c | 波次 | 加速比 | 评价 |
|---|---|---|---|
| 1（现状） | 7 | **1×** | 基线，且**有撞 600s 超时风险** |
| 4 | 2 | ~3.5× | ❌ **不推荐**：为不存在的供应商压力自我设限，白丢一半收益 |
| **7（推荐）** | **1** | **~7×** | ✅ 全量并发，一次到位 |
| >7 | 1 | ~7× | 无额外收益（只有 7 章） |

> **为什么推荐 7 而不是 4**：并发上限的唯一现实约束是**供应商能力**，而 7 路并发远低于任何商业 API 的承载能力。
> 把默认压到 4 等于**主动放弃一半性能**，换来的只是心理安慰 —— 这是设计缺陷，不是稳妥。

### 4.3 现实修正：为什么实测会略低于 7×

**注意：以下折损与「供应商能不能扛住并发」无关**，它们是数学与工程的必然：

| 因素 | 影响 | 与供应商容量有关吗 |
|---|---|---|
| **尾延迟（主因）** | 并行批次耗时 = **该批最慢的那章** `max(t_i)`，不是均值 `t̄`。LLM 输出长度方差大，`max` 明显大于 `t̄` | ❌ **无关**。即使供应商无限快，`max > mean` 依然成立 |
| 单章内部修复重试 | `generate_chapter` 有 `max_repair_attempts=1`（最多 2 次尝试，`openai_compatible.py:1011`），某章多一次调用 → 拉长该批尾部 | ❌ 无关 |
| 修订轮次 | 最坏每章 +1 次（`_MAX_REVISIONS_PER_CHAPTER = 1`），并发下**仍是一轮**，不是 7 轮串行 | ❌ 无关 |
| 供应商 TPM（token/分钟）配额 | 7 章 × `LLM_MAX_OUTPUT_TOKENS=8192` ≈ **57k 输出 token 同时在飞**。这是**吞吐配额**问题，不是并发数问题 | ⚠️ 唯一相关的供应商项，且**取决于账号档位**——需实测，不该预设 |

**综合预估**：`c=7` 时**实测约 5–6.5×**（尾延迟折损 10–25%）。7× 是渐近上限。

> ⚠️ **上述数字是模型推算，不是实测**。仓库里**没有任何模型调用耗时数据**（`app/` 中 `perf_counter|monotonic|time.time()` 只出现在工具调用与入站限流处，模型调用路径零命中）。
> **§3.1 第 2 项的埋点是把「预估」变成「实测」的前提，必须最先做。**
> 埋点还能同时回答一个更要紧的问题：**串行路径离 600s 超时到底有多近**。

## 五、瓶颈与风险

按严重度排序。

### 🔴 P0-1 持久化写竞争 → 整阶段降级（正确性风险）
- **现象**：`sqlite3.OperationalError: database is locked`
- **后果**：`graph.py:485` 注释要求写失败必须使阶段失败 → 冒泡到 `service.py:292` → **整份报告变兜底稿**
- **处置**：启用 WAL + `busy_timeout=5000`；若仍偶发，改为**单写者队列**（`asyncio.Queue` + 1 个持久化任务）彻底消除竞争
- **验证**：并发 7 路下连续跑 N 次，断言零 `OperationalError`

### 🔴 P0-2 无耗时埋点 → 收益不可证、瓶颈不可见
- **处置**：先加 `duration_ms`（§3.1 第 2 项），再动并发

### 🔴 P0-3 阶段 600s 预算与单次调用超时相同（既有配置隐患，并发后更需处理）
- **现象**：`LLM_TIMEOUT_SECONDS = 600` **等于** `STAGE_TIMEOUT_SECONDS = 600`。
  即：**一次挂死的 LLM 调用就能吃光整个阶段预算**，必然导致 `stage_timeout` → `StageStatus.FAILED`（无兜底稿）。
- **并发后仍存在**：并行批次耗时 = `max(t_i)`。若最慢那章接近 600s，阶段照样超时。
- **处置**：
  1. 把 `LLM_TIMEOUT_SECONDS` 降到明显小于阶段预算（建议 **180–240s**），让慢调用**降级为单章兜底**而不是拖垮整阶段；
  2. 用 S0 埋点的实测数据标定「`max(t_i)` 距 600s 的余量」，再决定是否需要同时调大 `STAGE_TIMEOUT_SECONDS`。
- **验证**：断言「单章超时 → 该章走 fallback，其余章正常，阶段仍 COMPLETED」。

### 🟠 P1-1 供应商限流 / 重试放大（**不是并发数问题**）
- **澄清**：7 路并发**不构成**供应商侧压力，不该据此降并发。真实的供应商相关风险只有两类：
  1. **TPM 吞吐配额**：7 章 × 8192 输出 token ≈ 57k token 同时在飞。低档位账号可能触顶 → 需**实测**确认账号配额，而不是预设限流。
  2. **重试放大**：`max_retries=2` 使失败请求 ×3 重放（7 并发失败 → 峰值 21 请求）。这是**故障态**的放大，正常态不存在。
- **处置**：默认全量并发；把 `Semaphore` 作为**运维旋钮**（可临时调低），并在埋点里记录 429 率与重试次数。**用数据决定是否需要降档，而不是提前降档。**
- **验证**：压测观察 429 率；若为 0，说明无需限流。

### 🟠 P1-2 输出非确定性（会破坏测试与审计）
| 来源 | 影响 | 处置 |
|---|---|---|
| `guard.py:101` `call_number` | 并发下 `call_number` 与章节的对应关系不再固定 | 事件里补 `chapter_id`，别依赖序号 |
| `quality_issues`（`graph.py:482-483` 按完成顺序累加） | 列表顺序随调度变化 → 快照/断言抖动 | 汇总时按 `chapter_ids` 顺序重排 |
| `state["chapters"]` 写入顺序 | ✅ **无影响**（dict 按 key 取，`finalize` 按大纲顺序读） | 无需处置 |

### 🟡 P2-1 异常语义变化
`asyncio.gather` 默认取消兄弟任务，会摧毁「单章失败只降级该章」的现有保证。
**处置**：`return_exceptions=True` + 逐章结果判定（见 §2.2 要点 1）。

### 🟡 P2-2 调用预算语义
`guard.py:94` `max_model_calls` 是**计数上限**：并发不改变总数，但会在**更短时间内集中消耗**。若预算是「每分钟」语义（当前不是），需要重新评估。当前是总数 → ✅ 安全。

### 🟡 P2-3 ContextVar 传递
session 必须在 **gather 之前**建立，否则子任务看不到 session → 计数/事件丢失、`max_model_calls` 预算失效。
**处置**：写测试断言并发路径下 `model_calls` 计数正确（应等于串行）。

### 🟢 P3 日志与事件并发
`guard._emit` 为同步写入，单事件循环下无竞争；但事件**落盘顺序**会变。若下游有按序消费假设，需确认。

## 六、测试方案

> 本节把并发化改造的验证方法**完整写在这里，可独立执行**。
> 每个方法按「测试目标 / 适用场景 / 主要步骤 / 判定标准」四要素组织。

### 6.0 为什么分两层（层次分工）

| 层 | LLM 供给 | 上游输入 | 回答什么问题 | 单轮成本 |
|---|---|---|---|---|
| **A. 并发正确性**（CI 层） | **确定性桩模型** | 桩夹具 | 顺序依赖 / 状态污染 / 降级语义 / 锁错误 | **0** |
| **B. 真实模型并发专项** | **真实模型** | **合成夹具**（允许捏造） | 尾延迟分布 / 真实加速比 / TPM 限流 / 600s 超时余量 | **≤7 次真实调用** |

两层**互补，不可互替**：

* **桩模型给确定性** → 「逐字节等价」这条最强守卫**只在桩下才可能成立**；
* **真实模型给真实行为** → 尾延迟、限流、超时余量**桩模型测不出来**（桩是常数时延、代打是本地产出，用它们测并发等于用尺子量温度）。

> ⚠️ **对上一版 §6.3 的更正**：上一版把「逐字节等价」写成无条件的「最强守卫」。
> 那在**真实模型下永远不可能通过**（模型输出非确定）。本版把它**限定在 A 层（桩模型）**；
> B 层的等价性改由**哨兵判定**承担（见 §6.3）。两层的判定项编号不重叠，避免重复计分。

### 6.1 前置：加埋点（否则两层都无法判定）

在 `RuntimeAwareChapterWritingModel.generate_chapter`（`model_gateway.py:41-60`）计时，把 `duration_ms` 与 `chapter_id` 写入 `MODEL_CALL_COMPLETED` 事件。

**为什么是前置**：当前**模型调用零耗时埋点**（`app/` 中 `perf_counter|monotonic|time.time()` 只出现在工具调用 `tool_gateway.py:217`、`data_fetcher/executor.py:492` 与入站限流 `rate_limit.py:23`，模型调用路径零命中）。不加埋点，A 层的计数断言与 B 层的加速比都无从计算，**也无法标定距 600s 的余量**。

### 6.2 A 层：并发正确性（桩模型，零成本，进 CI）

**测试目标**：在**完全确定**的条件下，证明并发实现没有破坏任何既有语义。

| # | 判定项 | 判定方法 |
|---|---|---|
| **S1** | **逐字节等价**（最强守卫） | `CHAPTER_WRITE_CONCURRENCY=1` 与 `=7` 两次运行的 `ChapterWritingResult`（`service.py:307` 的 `writing.model_dump()`）**逐字节相同** |
| **S2** | 调用计数不变 | 并发下 `model.calls` 仍等于串行值（7 / 8） |
| **S3** | 预算不失效 | 并发下 `session.state.model_calls` 与串行一致（验证 ContextVar 在 `gather` 子任务中被正确继承，`guard.py:140`） |
| **S4** | 单章降级语义保持 | 注入一章必然失败 → **只有该章**走 per-chapter fallback（`graph.py:321-338`），其余 6 章正常，阶段态仍 `COMPLETED`，`gather` 未取消兄弟任务 |

**适用场景**：CR 门禁与每次改动后的回归。**零 LLM 调用、秒级完成**，可高频跑。

**主要步骤**：
1. 用桩模型替换 `generate_chapter`（内容确定、时延为 0）；
2. 跑 `=1` 与 `=7` 两组，采集产物与计数；
3. 逐条判定 S1–S6；
4. S5 单独做 N 轮压测。

**判定标准**：**S1 / S4 必须全绿**——S1 失败说明并发引入了顺序依赖或状态污染，S4 失败说明异常语义被破坏。二者任一红即 BLOCK。

### 6.3 B 层：真实模型并发专项（低成本，回答"真的更快吗、会不会超时"）

**测试目标**：

| # | 目标 | 要回答的问题 |
|---|---|---|
| T1 | **正确性（确定性可判）** | 并发后 7 章是否各就各位、无跨章污染？（用哨兵标记使其成为**确定性判定**，不依赖真实模型的输出稳定性） |
| T2 | **真实加速比** | 相比串行，wall-clock 实际快了几倍？尾延迟折损多少？ |
| T3 | **降级语义** | 真实并发下单章失败/超时时，是否仍**只降级该章**，不使整份报告变兜底稿？ |
| T4 | **超时余量** | `max(t_i)` 距 `STAGE_TIMEOUT_SECONDS`(600s) 还有多少余量？ |
| T5 | **限流与重试** | 真实并发下 429 与重试是否为 0？（若非 0，是下调并发度的**唯一**正当理由） |

**适用场景**：① 并发化改造上线前的准入验证；② 后续任何「节点内并发」改动的复用（可读性评审逐段并发、Agent 1 多 Skill 并发）；③ 并发度调参后的复核。
**不适用**：① 全量用例回归；② 验证「智能体生产能力」或真实取数链路质量（上游是夹具，测不到）。

#### 关键设计一：合成上游夹具（允许捏造）

本层三层分工：

| 层 | 来源 | 是否真实 | 理由 |
|---|---|---|---|
| 上游输入（证据池 / claims / 图表引用） | **显式构造的夹具** | ❌ 合成 | 本专项测 **Agent 4 的并发行为**，不是 Agent 1 的采集质量。夹具能精确控制场景、压低 token，并植入哨兵 |
| **LLM** | **真实模型** | ✅ 真实 | 尾延迟 / 限流 / 超时余量只有真实模型能回答 |
| SkillHub | **不调用** | — | 上游已由夹具提供，取数成本归零 |

#### 关键设计二：哨兵标记（让真实模型下的正确性判定变成确定性）

真实模型输出非确定，因此「逐字节等价」不可能成立。但既然**上游可以捏造**，就给夹具植入**每章唯一的哨兵**：

* 第 i 章的证据统一带前缀 `EV-SENT-CH0{i}-*`，对应 claim 带 `CLM-SENT-CH0{i}-*`；
* 随后做两条**与模型输出稳定性无关**的确定性断言：
  * **正向**：第 i 章引用的证据/结论**只能**来自 `CH{i}` 组，且该组**必须被用满**（漏用即失败）；
  * **反向（污染检测）**：第 i 章产物中**不得出现**任何 `CH{j}`(j≠i) 组哨兵。

> 这是本层相对「跑两轮比对」的核心优势：**用构造输入换取确定性**，单轮即可给出可复现的是/否结论，**无需多轮重跑求稳定**。

#### 主要步骤

1. **构造上游夹具**：生成**最小可跑**的上游输入（7 章所需的最少证据与 claim），顶部显式声明 `input_source=synthetic` 与哨兵命名规则。
2. **取基线（零额外成本）**：从已归档的串行跑（`eval/transcript/{run_id}/traces.jsonl` 或 `baselines.json`）读取 7 章各自 `duration_ms` 与阶段 wall-clock。**不重跑串行**——这是成本减半的关键。
3. **单次并发真跑**：`CHAPTER_WRITE_CONCURRENCY=7` + 上述夹具，**不注入任何代打/桩模型**。夹具固定 → **唯一变量只剩并发度**。
4. **采集**：每章 `duration_ms`、阶段 wall-clock、429/重试计数、是否触发 `stage_timeout`、7 章产物。
5. **断言**：按下方判定标准逐条判定（K1/K2 走哨兵，其余走统计）。
6. **加速比计算**：`加速比 = 串行基线 wall-clock ÷ 本轮并发 wall-clock`；同时算**尾延迟比** `max(t_i)/mean(t_i)` 以解释折损来源。
7. **超时余量外推**：用本轮 `max(t_i)` 与 `STAGE_TIMEOUT_SECONDS` 求余量；余量不足则下调 `LLM_TIMEOUT_SECONDS`（见 K7）。
8. **可选重复**：默认 `k=1`；需评估方差时 `k=2`（**成本翻倍，需显式授权**），不做更大样本。

#### 成本控制（与「不大量调用大模型」的对齐）

| 项 | 设计 | 节省 |
|---|---|---|
| SkillHub 取数 | 夹具替代，**完全不调用** | 省掉全部取数调用与快照录制 |
| A/B 对照 | **复用已归档串行基线**，不重跑串行 | 省掉一整轮 7 次调用（**减半**） |
| 输入规模 | 夹具只放「7 章必需的最少证据与 claim」 | 降 prompt token，压低单次成本与时延 |
| 样本量 | 默认 `k=1`，不做大样本 | 省掉 k−1 轮 |
| 判定 | 哨兵使正确性**无需多轮求稳定** | 省掉为「求确定性」而做的重复跑 |
| **单轮真实调用预算** | **≤ 7 次**（7 章 × 1）；仅某章触发结构修复重试时上浮，最坏 ≤14 次 | — |

> **一句话**：把「测并发」从「跑两轮全链路」压缩成「**一轮 7 次真跑 + 一份历史基线 + 一份夹具**」。

#### 判定标准

| # | 判定项 | 判定方法 | 阈值 | 一票否决 |
|---|---|---|---|---|
| **K1** | 输出结构等价 | 7 章齐全、`chapter_id` ∈ `CH-01..07` 且**与哨兵组对应**（不串位）、每章 `sections=3`、`section_id` 前缀与所属章一致 | 全部成立 | ✅ |
| **K2** | 跨章污染（哨兵法，**确定性**） | 见上「关键设计二」的正向 + 反向两条断言 | 0 命中 | ✅ |
| **K3** | 证据引用合法性 | 全部 `evidence_ids` ⊆ 夹具证据池；`analysis` 类段落必有 `claim_ids` 与 `evidence_ids` | 0 违规 | — |
| **K4** | 并发持久化零锁错误 | `ChapterRepository.save_chapter` 全成功；无 `database is locked` / `OperationalError` | **0 次** | ✅ |
| **K5** | 真实加速比达标 | 加速比 ≥ 理论值 × 0.8（理论值 = `Σt / max(t_i)`），并记录尾延迟比 | 见左 | — |
| **K6** | 单章降级语义保持 | 与 S4 同判据，但在真实模型下复核 | 全部成立 | — |
| **K7** | 阶段超时余量 | `max(t_i) ≤ 0.6 × 600s`，且核验 `LLM_TIMEOUT_SECONDS` **严格小于** `STAGE_TIMEOUT_SECONDS` | 见左 | — |
| **K8** | 限流与重试基线 | 统计 429 / `MODEL_CALL_FAILED` / 结构修复重试次数 | 429 = 0（非 0 则触发并发度下调评审） | — |

**门禁**：**K1 与 K4 全绿是开启 `CHAPTER_WRITE_CONCURRENCY > 1` 的前置条件**（fail-closed）。K5–K8 未达标允许带警示放行，但必须记录并在下轮复核。

#### 诚实性约束

* 本层 LLM 为真实调用，但**上游是合成夹具**：产物必须同时标注 `input_source=synthetic`，**禁止**把它当作「真实取数链路」的结论对外引用。
* 夹具必须**显式声明来源、可追溯**，不得冒充真实证据；这与本方案「不得把故障包装成合法数据」的红线一致（本层是**主动构造测试输入**，属正常夹具实践，不是伪造故障）。
* 本层结论**只回答「Agent 4 并发行为」**，不得用于推断 Agent 1/2 的生产能力或真实数据质量。

#### 与 A 层的分工小结

A 层回答「**并发有没有改坏东西**」（确定性，零成本，进 CI，含逐字节等价）；
B 层回答「**并发真的更快、且不会超时吗**」（真实行为，≤7 次调用）。
两者判定项编号不重叠（S* / K*），结果分开记录。

### 6.4 观测指标（建议纳入评测）
- 阶段 P50 / P95 wall-clock，以及 **「距 600s 预算的余量」← 最关键的运维指标**
- 单次模型调用 P50 / P95 `duration_ms`
- 并行批次的**尾延迟比** `max(t_i)/t̄`（衡量尾延迟损耗，而非供应商能力）
- 429 / 重试率、`MODEL_CALL_FAILED` 事件数（用于**判断是否需要动 Semaphore**）
- 单位时间 token 吞吐

## 八、一页纸摘要（给评审）

- **能并行**：7 章零依赖，累加器按 key、`finalize` 按大纲顺序取 → 输出顺序天然稳定
- **并发度**：**直接给 7（全量）**。7 路并发对商业 LLM API 无压力，不该自我设限；
  `Semaphore` 只作安全阀（防未来大纲扩容 + 故障态重试放大），默认让它形同虚设
- **策略**：节点内 `asyncio.gather(return_exceptions=True)`；
  图简化为 `START → generate_all → finalize → END`
- **加速比**：渐近 7×，实测预期 **5–6.5×**（折损来自尾延迟数学，与供应商容量无关）
- **并发是刚需，不只是优化**：阶段 600s 硬超时（`workflow/graph.py:90`）在外层，
  `chapter_writer` 的兜底稿救不回来 → 串行有真实 FAILED 风险
- **两个必须先做的前置**：
  1. ⚠️ SQLite 写竞争（否则并发会把「慢」变成「整篇兜底稿」）
  2. ⚠️ 模型调用耗时埋点（否则收益无法证明，**也无法标定距 600s 的余量**）
- **测试方案是两层**（§6）：
  - **A 层 · 并发正确性**（桩模型，零 LLM 调用，进 CI）：**逐字节等价** S1 是最强守卫，另含计数/降级/锁/顺序无关 S2–S6
  - **B 层 · 真实模型并发专项**（真实模型 + 合成夹具，**≤7 次真实调用**）：**哨兵判定** K1/K2 把「跨章污染」变成确定性判定
  - 两层互补：桩模型给确定性，真实模型给真实行为；**判定项编号不重叠**（S* / K*）
- **顺带修一个既有隐患**：`LLM_TIMEOUT_SECONDS`(=600) 与 `STAGE_TIMEOUT_SECONDS`(=600) 相等
  → 一次挂死调用即拖垮整阶段，建议降到 180–240s
- **最大不确定性**：账号 TPM 配额（唯一与供应商相关的项）—— **实测标定，不预设限流**
