## 4 R1 编辑提交和版本完整性

### 4.1 根因、影响与证据

`backend/app/engine/state_machine.py` 中，后台 `_execute_stage` 持有旧状态快照；返回后只检查 cancelled，没有按输入版本验证提交。临时复现中编辑已保存 r2，后台结束却把 state 写回 r1，编辑消失，历史仍记 to_revision=2。

direct_edit 的异常回退只包 `_apply_direct_edit`，约 705–716 行；约 731 行的 `_commit_state_with_history` 在外面。提交函数约 571–576 行先写成功历史再保存状态。历史损坏/状态保存异常后，dataset 可能已经变新而 state 仍 r1，甚至存在假成功历史。

失效有两个相反错误：图表编辑的 downstream_stale 成功重建后不被消费，导致新版也一直 409；融合内容本身编辑又没有撤销旧导出资格，旧正文仍 200。另 `_sync_chart_artifacts` 约 497–511 行仍将主图校验失败吞掉、降级 echarts 并保留旧 svg_uri。

影响用户编辑内容、版本单调性、恢复、下载和图表版本一致性。优先保证已保存内容不被旧任务覆盖、失败不产生新成功状态。

### 4.3 修改步骤

1. 在同一 run 的读取、动作状态检查、expected_revision 检查、提交与派发登记间建立互斥；所有后台提交也必须进入同一保护。先确认部署写入进程范围；发现多进程而必须引入新锁/存储架构时停止确认，不能把 asyncio.Lock 宣称为跨进程保护。
2. 每次执行捕获输入 revision 与执行 generation/token。耗时调用在保护区之外；返回后重新加载当前状态，以比较并交换方式提交。旧输入结果不得把整个旧 state 保存回去，revision 不可倒退。
3. 对运行中编辑给出明确策略。本轮优先拒绝会与当前执行冲突的直接编辑；若业务要求允许，则先取消并确认旧执行不可提交，再产生新 generation，不能仅标记“取消请求已发出”。
4. 提交前验证历史与快照可读取，将修改后的 state、JSON、主 SVG、历史、快照准备到独立临时位置。把最终提交也纳入失败恢复范围；不能只回滚应用阶段。
5. 故障恢复只恢复本次持有提交权的版本，不能用旧备份覆盖其他请求。历史先记成功后 state 失败的顺序必须消除；恢复本身失败时保留临时证据、记录需恢复状态并封住当前交付，不能仅记日志后继续使用混合版本。维持此前边界：请求内异常回退必须实现；任意进程崩溃跨文件事务不冒称已实现。
6. 将主 SVG 重建失败和可选补充位图失败分开。主图结构、渲染、落盘失败应使请求失败并恢复；可选位图失败可降到本次已成功生成的 SVG。不能保留上一版 svg_uri 冒充本次成功。
7. 用失效 generation 或等价版本元数据替代永久布尔封锁。编辑使依赖结果失效，成功重建只消费其实际覆盖的失效代次；中途又编辑则不能消费新失效。
8. report_fusion 内容编辑同样使本阶段 MD/HTML/PDF/manifest 失效，沿现有恢复入口重新导出后才恢复当前资格。下载检查依据当前版本和发布资格，不扫描任意历史 stale 标记永久拒绝。

## 5 R2 财务查询、资格与覆盖计数

### 5.1 根因与定位依据

执行报告的“仅规划器没写指标”结论不完整。`data_fetcher/agent.py:208–212` 的 `_FIELD_NAME_NOISE` 含营业收入、归母净利润等；`_compile_query:270` 无条件删除，`_validate_tasks:917` 起执行前必经该编译。离线实际输出：

```text
原查询：五粮液 近5年 营业收入 归母净利润
编译后：五粮液 近5年
```

同文件约 187、201 行提示词要求指标仅放 expected_fields，和前段财务示例冲突。`skillhub.py` 的 IwencaiGateway.call 约 374 行最终请求主要使用 query、page、limit、is_cache、expand_index；expected_fields/time_range 不会自动变成外部财务查询条件。

还有三类相关残留：

1. `_validate_tasks:979–999` 在存在部分评分并且要求 leader_identification 时，又只准 ranked_candidates，未真正解耦身份和评分。
2. `_normalize_security_code:1044–1057` 剥交易所后缀，`_build_query_eligible_entities:1084` 按裸代码合并；显式 `.SH` 查询仍能命中 `.SZ` 候选。
3. `_evaluate_requirement:1241–1253` 将名称集合与代码集合相加计数，同一公司算两家。离线 4 家已识别、仅 2 家有收入与利润时，财务覆盖却通过；真实 run 只有泸州老窖，但事件曾显示覆盖两家。

因此既不能只改提示词，也不能在资格层机械追加全部 expected_fields。现有两轮集成测试没有把被接受任务真实送到假 Gateway，而是手造财务响应再融合，漏掉了编译破坏语义。

### 5.2 文件和边界

### 5.3 修改步骤

1. 将查询编译改为按技能/领域和明确需求处理。证券代码、证券简称等返回元字段与营业收入等真正检索指标分开；不能再用同一“字段噪声表”删除财务语义。
2. 建立确定的最终查询构造顺序：识别目标→确认需求指标→保留/合并期间→去说明性噪声→校验语义完整→生成 gateway_query。不得在编译末尾盲目截词而丢主体、指标或期间。
3. 统一 planner 正反例。expected_fields 可记录预期输出，但若外部协议依赖 query，必须在发送前把受支持的目标指标和时间要求落实到 query。不要向 Gateway 添加服务端并不支持的参数来“解决”。
4. 无可识别指标的财务任务先进入有界规划修复；可从已明确的本任务 requirement/task.expected_fields 恢复，无法恢复则清楚拒绝。一次有限修复失败就保留原因，不追加全套八大指标无限重试。
5. 记录 raw_query、compiled_query、gateway_query、需求 ID 和更改原因，方便区分模型输出、编译丢词、服务端回错域。日志不得包含密钥。
6. 财务响应须按实际目标指标和期间验收。仅返回行情字段即便 records 非空，也不能满足财务需求；保留“只返回行情/缺目标指标”等结构化原因。
7. 完全分离合法实体资格与评分。明确用户目标/研究样本范围可以约束查询，但 leader_score 为空不构成无资格。排名需求影响排序和补采，不恢复旧全拒逻辑。
8. 身份使用市场/交易所/代码；裸代码只在当前候选唯一时匹配，显式后缀不一致拒绝。名称、别名和 must_include 走同一解析，不保留短子串绕过路径。
9. 覆盖按规范主体去重，名称和代码只是属性；对每家检查收入、利润、有效期间、来源及单位。不能全域有收入和利润就认为每家都有。

4. 将来源中文 stage 映射成经过审核的活动政策；每个角色候选绑定主体、品类/活动、允许角色和适用主题。品牌、ODM、零部件、渠道、服务、场景分别处理。
5. 在 V2 公司检索规划阶段从 registry 获取分活动、有限数量的种子；仍沿 search→fetch→extract→verify→membership 流程取证，不直接向 supported_assertions 写名单。
6. 原文须明确支持提供该产品/服务或执行该活动；行情记录、同名出现、整机配置包含某部件，不能证明主体独立提供部件。身份数据和业务证据不能互相代替。
7. 角色通过并不证明客户供货。实际 supplies_to 必须有该对主体、方向与时间范围的证据；政策结构、工艺顺序和企业交易关系分别建模。
8. 画像解析应精确到范围与别名，显式 profile_id 范围不符报错；旧关键词投影防止泛主题先命中吞掉细主题。画像注册清单、版本与数据发布版本统一记录。

验收分别检查“结构合法、被运行选中、候选可召回、角色落位正确、证据支持”五件事。名单外未知公司继续走证据发现，不仅因不在名单删除；冲突和未知结果留痕，不伪装通过。

新增 `test_profile_reference_release.py`、`test_seed_candidate_limits.py`、`test_membership_role_scope.py`。覆盖品牌/ODM隔离、白酒上下游口径、跨主题多角色、同词不同品类、名单外合法主体、空来源/草稿名单、禁止凭名单制造供货边。

## 10 D3 产业链路径、证据与连线统一

### 10.1 具体根因

1. 实际两个样本没有 `artifacts/chain/v2/bundle.json`，仍走旧路径。A1、A2、A3 各自读进程环境 CHAIN_ENGINE，没有把本次解析的路径与版本稳定绑定到 run。
2. 旧 `chain_render._render_lane_grid:695–811` 明确只画两根列间箭头，`render_chain_svg:814` 只有该版式；结构图的具体 edges 未渲染。不是“当前 SVG 没有 line 标签”，也不是导入修正后就恢复了所有关系。
3. V2 `view.render_bundle:65–117` 只画受支持的 precedes，且跳过同列边、使用 path 无箭头头部；前端 `ChartGallery.vue:878–881` 元素白名单没有 path，sanitizeInlineSvg 会删除它。只切 V2 不能保证页面保留关系线。
4. 图层仍把节点“有若干 evidence_record_ids”当整体 evidence。笔记本核心卡列 7 家主体，但它的 3 条引用仅是华勤收入占比及环旭的涨跌幅/股价，不能支持该 7 家在当前活动中的角色。节点引用还与 ChartSpec.evidence_ids 不相交，必须明确汇总与解析。
5. V2 A3 使用 chain2: 前缀的证据 ID；A4/A5 原有允许集合主要来自 report.evidence_index。A2 的 chain_context 独立解读不等于完成统一引用目录。修复 R4 的未知图证据检查时，必须同时完成合法 V2 证据桥，不能让新链图全部被误拒或为兼容而放开未知 ID。
6. A3 适配器最终 chart_refs 把 status 写成 ready，StageResult 为 waiting_review/error=None，未把 result.chain_quality 的失败/部分覆盖完整映射为交付资格。用户明确要求产业链而 V2 bundle 缺失时，不能无声当作制图完成。

### 10.2 主路线与文件范围

本轮主路线：保留现有 V2 研究与严格证据模型，先在白酒/notebook 新 run 显式启用、固定版本；旧链图作为兼容的结构草案，不把名单或旧 source_tier 自动提升为已审核事实。其他主题按 D2 分批迁移，不全局切换并假定全部可用。

| `chain_research/service.py`、`profiles.py`、`membership.py`、`models.py` | 复用 D2 的受控候选、范围、角色和证据 |

### 10.3 固定运行和发布版本

1. 创建 run 时解析一次 engine、research_strategy、profile_id/version、reference_release_id 和 source_policy_version，持久化为执行快照。后续阶段和 resume 从快照读取，不各自根据当前环境重新选路。
2. 兼容旧 run：缺快照时明确标记 legacy，不默认换引擎/套新名单。新主数据发布不悄悄改变历史报告。
3. V2 显式运行若 bundle 缺失、范围不符、预算失败，输出结构化 chain_quality 和原因；用户要求链图时阻止其成为“完整链图交付”。用户明确无图模式仍保持既有语义。
4. 画像 draft 或仅 partial 覆盖时保留范围说明，不能硬标 verified。可输出受限草稿，但正式交付资格与普通成功图分开。

### 10.4 统一节点、角色、边和证据

1. 以同一 bundle + profile_snapshot + reference release 编译 canonical view。每个公司参与项绑定 organization_id、activity/category、role、membership_decision_id、assertion_ids 和 evidence_ids；不是一张卡挂几条记录就给所有公司盖 evidence。
2. 工艺和场景节点由画像政策表示，保留 profile_refs；其存在不需要虚构企业。企业参与、产品提供、工艺先后、实际供货分别表达，不能以一类边替代另一类。
3. evidence_bridge 只处理 supported 断言实际引用的证据和通过的 membership，生成 chain2 命名空间的最小引用投影、源 URL/原文定位/内容 hash/时间/来源家族。投影用于合法引用和目录，不进入 dataset.financials，不重新提升候选状态。
4. A2/A4/A5 获得相同命名空间解析结果，目录和图只引用本图实际使用证据；不将 cb.evidence 全量挂上来充覆盖。未知 ID、旧版本 ID、错范围证据仍拒绝。
5. 行情、市值、PE 不能单独支持“该主体是本活动供应商/品牌/制造商”；可作为金融事实另用。瓶颈、已落地、毛利分布等额外结论也必须有各自证据，否则不显示确定性徽标或数值。
6. ChartSpec 的图标题、结构快照、inline_svg、svg_uri、数据/视图指纹和质量来自同一个生成版本。标题编辑与节点编辑后同步快照，不能再出现外层已改但结构仍旧。

### 10.5 渲染规则

1. 主图使用关系布局，展示经审核的活动/产品依赖和有证据的关系；目录式 overview 可保留为明确的辅助视图，不将两根总箭头当作全部关系。
2. 支持同列工艺边与跨列边；依据位置绕线，不能沿用 `x != tx` 就跳过同列关系。避免穿字、压卡、反向无箭头和循环误读。
3. 选择当前前后端均支持的 line/polyline/polygon 等安全图元绘边与箭头，保留消毒。不要只在 V2 输出 path 然后让前端删掉，也不为方便放开脚本、href、foreignObject 或任意 style。
4. 为每条可展示边输出稳定 edge/assertion ID，并在 view_mapping 中记录 from/to、关系类型、来源和渲染状态；用这些映射验收，不统计背景 line。被省略的边必须有可读原因和完整明细，不静默消失。
5. 画像政策支持的一般结构边用明确的结构/政策样式，事实支持的关系用其证据样式；没有客户交易证据不画成企业间实际供货。不能把旧 LLM 15 条边全部无条件升级为真实交易线。
6. 组织名称保留完整可读，超出容量换行/分面或在受控明细中展示，不裁成另一家公司。全景链参与者可全球覆盖，金融样本仍遵守用户 market_scope，不能把“全球产业参与”混成“A 股证券池”。
7. 浏览器预览、磁盘 SVG、HTML 和 PDF 使用同一视图/图形；产业链主图重建失败遵守 R1，不能降到旧图继续交付。

### 11.3 新 run 的真实验收

必须新建白酒产业链与笔记本电脑产业链两类任务；图形和金融样本范围显式记录。不能复用当前 cancelled run 或仅对旧 financials=0 的 dataset 续跑融合来宣称修复成功。

人工路径按以下顺序验收：取数暂停→至少 3 家核心公司有效财务→合法编辑并有真实历史→旧 revision 409→批准仅派发一次→制图暂停→改单图保全其他图→主图失败注入不假成功→报告待更新→重建→融合暂停→最终批准→三格式当前下载。
