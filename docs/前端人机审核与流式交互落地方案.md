# 前端人机审核与流式交互落地方案

> 当前若只需查看前端界面和验证审核交互，请先执行[前端人机审核交互原型 AI 严格执行方案](./前端人机审核交互原型-AI严格执行方案.md)。该原型使用前端 Mock 数据，不依赖后端；本文件保留为后续正式接入方案。

## 目标与边界

本方案将行业研究报告的五个智能体改造成可审、可改、可追溯的协作界面。用户不必等待整条工作流结束后才看到结果；在后端具备异步任务与事件能力后，用户可以在产出到达时查看、审核并发起定向修改。

核心原则是：**能用按钮完成的确定操作，不使用对话框；只有需要表达非标准修改意图时，才使用受限对话框。** 对话框不能成为删除、重跑、切换模板等按钮的替代品。

本方案不增加第六个“审核智能体”。审核是 Agent 1 至 Agent 5 的共同交互层：每个智能体负责自己的结果，前端负责选择对象、收集用户意图、展示影响范围和版本差异，后端负责校验、重跑与保留审计记录。

## 已确认的现状

- 前端已有运行详情页、阶段审核按钮和每三秒一次的轮询，但轮询依附于页面组件，进入一个已经运行的任务时不能稳定恢复；运行状态没有独立的 Pinia store。
- `POST /runs` 与审核提交仍是最长五分钟的同步请求。新建任务未获得 `run_id` 前，前端无法可靠地订阅或轮询它。
- 当前审核组件已有“通过、风险确认、修改重跑、重新生成”等阶段级动作；缺少的是对具体证据、结论、图表、章节、段落的精确审核和新旧版本对比。
- Agent 1 已能解释部分采集修改；Agent 2 和 Agent 4 会把意见交给模型，但还没有可定位对象、可展示生效结果的交互闭环。
- Agent 2 的现有接口禁止直接编辑 `evidence_items`。证据是 Agent 1 的单一写入对象，因此“排除证据”必须记录为排除决定并触发受影响结果更新，不能由前端直接删除证据。
- 报告融合虽存在 `chapter_order` 参数，但当前实现仍强制七章标准顺序。首期不提供可生效的拖拽排序按钮，避免制造“看似修改成功”的假功能。

## 产品决策

### 审核对象与审核状态

所有审核对象统一采用以下状态，组件根据状态显示或禁用按钮：

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| `running` | 正在生成或重跑 | 查看已完成内容、查看日志、保留草稿；不可提交审核 |
| `reviewable` | 当前版本可审核 | 通过、退回、发起定向修改、风险确认 |
| `provisional` | 上游结果更新后，本对象可能过期 | 查看影响原因、重新生成；不可直接正式通过 |
| `stale` | 当前页面版本落后于服务端版本 | 查看差异、刷新、迁移未提交草稿 |
| `approved` | 当前版本已通过 | 查看、导出、发起新修订 |
| `failed` | 生成失败 | 查看错误、重试、改参数后重跑 |

正式通过必须基于当前版本。用户提交修改后生成的是新版本，系统不得把“提交修改”自动当成“审核通过”。

### 按钮与对话框分工

| 智能体 | 按钮完成的确定操作 | 对话框仅允许输入的内容 |
| --- | --- | --- |
| Agent 1 数据采集 | 添加/移除关键词和指标、切换时间范围、切换数据源、排除/恢复证据、重新采集 | 新研究问题、口径限制、尚未列出的数据范围 |
| Agent 2 数据分析 | 通过/驳回结论、标记证据不足、切换分析深度、查看引用、恢复已驳回结论 | 因果解释要求、反证方向、需要比较的维度 |
| Agent 3 图表生成 | 删除图、移出/纳入报告、切换可用模板、编辑标题、选择配色、重新生成、打开预览 | 非模板化布局意图、需要强调的业务重点、图中叙事顺序 |
| Agent 4 章节写作 | 通过/退回章节、选择章节/段落、直接编辑文字、调整篇幅、调整语气、恢复上一版 | 改写策略、需保留或避免的表达、章节重点 |
| Agent 5 报告融合 | 选择报告风格、信息密度、输出格式、摘要长度、生成/下载产物 | 全局叙事要求、摘要组织顺序、整体表达偏好 |

“删除”“排除”“重生成”“切换模板”不得再在对话框中出现同义入口。删除使用二次确认；重生成直接使用当前参数；任何需要确认数据影响的操作显示影响说明弹层，而不是让用户重新输入自然语言。

### 受限对话框规范

对话框使用共享组件 `ReviewConversationDialog`，但必须由当前审核对象打开。标题区固定展示：阶段、对象名称、对象 ID、当前版本和修改范围。

每个阶段的输入框顶部显示以下限制文案：

| 阶段 | 对话框提示 |
| --- | --- |
| Agent 1 | 仅补充研究问题、数据口径或范围。删除证据请在证据表使用“排除”。 |
| Agent 2 | 仅说明分析方向或反证要求。驳回具体结论请点击结论卡片的“驳回”。 |
| Agent 3 | 仅描述非标准图表需求。删除、重生成、模板和配色调整请使用图表卡片按钮。 |
| Agent 4 | 仅说明改写原则。直接改写文字请在段落编辑器完成。 |
| Agent 5 | 仅说明报告整体叙事要求。导出格式、报告风格和图表密度请在报告设置修改。 |

对话提交流程固定为：**输入意见 → 解析或归纳修改意图 → 显示作用对象与影响范围 → 用户确认 → 创建新修订 → 显示新旧对比 → 用户通过或继续修改**。

自然语言解析失败、目标不明确、或请求了当前阶段不支持的能力时，系统必须显示“未执行”的原因；不得把原始意见拼接进数据查询语句后静默执行。

## 运行详情页布局

运行详情页继续使用现有路由，不拆成新的产品页面。推荐桌面端布局如下：

```text
┌──────────────────── 运行顶部栏 ─────────────────────────────┐
│ 行业与任务名  版本 v12  实时连接状态  [查看历史] [导出]      │
├───────────────┬────────────────────────────┬─────────────────┤
│ 审核队列      │ 当前阶段内容区             │ 审核检查器      │
│ 阶段与单元    │ 数据 / 分析 / 图表 /       │ 证据、差异、    │
│ 状态与数量    │ 章节 / 完整报告 标签页     │ 风险与影响范围  │
│ 筛选：待审等  │ 保留用户当前选择，不自动跳转 │                 │
├───────────────┴────────────────────────────┴─────────────────┤
│ 固定操作栏：草稿状态｜通过｜退回｜预览修改｜确认执行          │
└──────────────────────────────────────────────────────────────┘
```

- 左侧为“审核队列”，不只是阶段步进器。第一期按阶段展示，后续后端提供单元事件后再展开为章节、图表、结论等单元。
- 中央内容区复用现有数据、图表、报告阅读组件。新产出只显示“有 N 项新结果”提示，不强制滚动、不覆盖用户正在编辑的对象。
- 右侧“审核检查器”随当前选中对象变化，展示证据、风险、修改影响和版本差异。窄屏时收纳为右侧抽屉。
- 底部操作栏只显示当前对象允许执行的动作；一次操作只锁定自身，不阻断用户浏览其他已完成结果。

## 五个智能体的界面与交互

### Agent 1 数据采集

**主界面**：证据表格。列为证据编号、标题、来源、发布日期、采集时间、数据口径、质量等级、被哪些结论引用、状态。

**按钮**：`查看原文`、`复制引用`、`排除`、`恢复`、`补充指标`、`修改时间范围`、`重新采集`。

点击 `排除` 时弹出影响确认：列出会变为 provisional 的结论、图表和章节；要求选择排除原因。点击确认后，创建审计记录，保留原始证据，不物理删除。

`提出采集修改` 打开受限对话框，仅用于输入新问题或口径要求。解析预览应将其转换为可确认的关键词、指标、范围等结构化变更；用户可以逐项移除后再执行。

### Agent 2 数据分析

**主界面**：结论卡片列表。每张卡显示结论文本、置信程度、引用证据编号、反证条件、状态和版本。

**按钮**：`通过`、`驳回`、`证据不足`、`查看引用`、`调整深度`、`恢复结论`。

`驳回` 必须绑定具体 `claim_id`，显示必填的简短驳回原因；它映射到既有 `rejected_claim_ids`，而非修改证据事实。若用户认为证据本身错误，按钮应是 `请求数据更正`，将需求退回 Agent 1，而不是让 Agent 2 删除证据。

`讨论并修改` 只能提出“比较成本与价格传导”“增加反证分析”等解释请求，不能录入或改写数值事实。分析生成后，右侧检查器对照展示旧结论、新结论、引用变化与受影响的后续对象。

### Agent 3 图表生成

**主界面**：图表卡片网格，每张卡独立显示图号、标题、来源、使用的证据、版本、是否已纳入报告和审核状态。

**按钮**：`预览`、`编辑标题`、`换模板`、`换配色`、`重新生成`、`移出报告`、`删除`、`描述特殊修改需求`。

其中 `编辑标题`、`换模板`、`换配色` 均为小型表单或下拉菜单，直接提交明确参数；`删除` 只二次确认；`重新生成` 直接复用本图当前参数。`描述特殊修改需求` 是唯一打开对话框的入口。

图表卡片要同时支持 ECharts 数据图和 `generated_image`。图片图表不应因为没有 ECharts `option` 就被过滤掉；预览框需要支持受鉴权产物下载后的 object URL，并在关闭时释放。弹窗预览不能只初始化 ECharts。

AI 生成的产业链结构图仅用于展示结构关系，禁止显示未经证据支持的数值、份额、排名或虚构企业。企业 Logo 可以出现，但只能来自本次报告已核验企业名单和许可的 Logo 素材。生成结果自动执行节点完整性、箭头方向、文字可读性、企业/数据凭空增加检查；失败时以“待人工确认”显示，不自动进入正式报告。:codex-annotation{index="1"}

单图定向重生成需要后端提供 `chart_id` 级操作和独立版本。现有图表审核参数主要是阶段级，首期不能把“整阶段重生”伪装成“仅修改此图”。

### Agent 4 章节写作

**主界面**：结构化章节树和段落阅读器。每一章、节、段落必须有稳定 ID，不能依赖用户在 HTML 中选择到的临时文本位置。

**按钮**：`通过本节`、`退回本节`、`编辑段落`、`恢复上一版`、`调整篇幅`、`调整语气`、`让 AI 修改`。

`编辑段落` 打开内嵌文本编辑器，保存到既有 `manual_edits`；每次保存都展示证据引用保留情况。`让 AI 修改` 对话框只接收改写原则。用户提交后，仅重写选定章节、节或段落，未选择内容保持不变，并生成差异视图。

### Agent 5 报告融合

**主界面**：报告设置面板、最终预览与产物区。

**按钮**：`专业/通俗语气`、`简洁/标准/详细`、`紧凑/均衡/详细图表密度`、`Markdown`、`HTML`、`PDF`、`预览`、`重新融合`、`下载`。

`提出报告修改` 只处理摘要结构和全局叙事要求。章节顺序首期只读显示为“七章标准顺序”；待后端改造渲染链后，才开放拖拽并明确标记为“自定义报告模板”。最终产物区按修订版本展示，避免用户下载到旧的 HTML 或 PDF。

## 实时运行与状态设计

### 传输契约

后端应支持异步启动。`POST /api/v1/runs` 在请求头 `Prefer: respond-async` 下立即返回 `202`，至少包含：

```json
{
  "run_id": "run_...",
  "operation_id": "op_...",
  "status": "queued",
  "state_version": 1
}
```

保留同步响应以兼容旧客户端。异步任务必须先持久化 `run_id` 与操作记录，再入队；不能依靠前端计时估算进度。

新增 `GET /api/v1/runs/{run_id}/events` 事件流。由于当前鉴权使用 Authorization 请求头，前端应使用 `fetch` + `ReadableStream` 实现 SSE，而不是原生 `EventSource`；原生 `EventSource` 不能安全携带现有 Bearer Token。

每条事件至少包含 `event_id`、`seq`、`run_id`、`operation_id`、`stage`、`unit_id`、`unit_revision`、`state_version`、`type` 和 `payload`。前端按 `event_id` 或单调 `seq` 去重，不能只按 revision 去重，因为同一个 revision 可能有多条事件。

事件断开后携带最后的事件游标重连；若发现序号缺口，调用 `GET /runs/{id}` 拉取快照并恢复。连续重连失败时回退到现有轮询。401 时进入重新登录状态，不得无限重试。事件连接由 run store 统一管理，切换页面或浏览器隐藏时按需暂停，避免多个组件为同一任务创建重复连接。

### Pinia 状态模型

新增 `stores/run.ts`，以 `run_id` 为一级键，不使用单一 `currentStage` 作为唯一运行状态：

```text
runs[runId]
  ├── snapshot：服务端完整状态、stateVersion、lastEventSeq
  ├── stages[stageId]
  │     └── units[unitId]：status、unitRevision、result、risk、updatedAt
  ├── reviewQueue：可审核对象 ID 列表
  ├── operations：异步操作、进度与错误
  ├── connectivity：SSE / polling / reconnecting
  └── drafts：未提交的表单与其 baseVersion
```

编辑草稿与服务端结果分开存放。收到新版本时，若草稿所属对象未变化，保留草稿并提示用户；若对象已更新，标记为 stale，允许用户比较后迁移或丢弃。后续支持单元级并发审核时，使用对象的 `unit_revision` 做乐观并发控制，不因无关对象的全局版本增长而误判冲突。

| `backend/app/api/routes.py`、运行服务与工作流入口 | 异步创建任务、状态快照、SSE 事件流、操作查询、幂等键和版本冲突返回 |
| `backend/app/schemas/workflow.py` | 对象级审核请求、修改预览请求、异步启动响应、事件模型与严格的阶段编辑 schema |
| 审核记录仓库 | 保存对象 ID、原版本、新版本、用户操作、理由、影响范围、风险确认、执行结果和时间 |
| `backend/app/common/feedback_interpreter.py` | 只产生可预览的结构化建议；不支持或不明确的意见不执行；删除原始意见拼接到查询条件的降级路径 |
| Agent 1 服务 | 支持证据排除账本和恢复；计算下游失效范围；保留原始证据与排除原因 |
| Agent 2 服务 | 支持 `claim_id` 级驳回和恢复；将数据错误请求转回 Agent 1；不允许通过 Agent 2 写证据 |
| Agent 3 服务 | 支持 `chart_id` 级重生成、单图版本、模板能力清单及生成图审核结果 |
| Agent 4 服务 | 支持章节/节/段落的稳定 ID、最小范围重写、引用再校验与差异产物 |
| Agent 5 服务 | 输出按 revision 可追溯的 Markdown、HTML、PDF；章节拖拽在实际渲染链支持前保持关闭 |

## 交付顺序

### P0 审核界面基础

先完成前端不依赖事件流的部分：独立 run store、进入运行页自动恢复轮询、非阻塞进度提示、阶段级审核队列、对象选择、按钮与草稿、证据/结论/图表/产物的版本展示。同步接口仍可工作。

同时修复数据采集的危险降级：自然语言解析失败时必须提示并等待用户确认，不得将原始文本追加到查询。

### P1 异步任务与受限对话

接入 202 异步启动、持久化任务、SSE、断线回退轮询和事件去重。实现受限对话框与“修改预览”接口。此时先以阶段事件驱动队列，后端尚无单元事件时不假装具备并发单元审核。

### P2 精确对象级修订

实现证据排除账本、结论级驳回、单图重生成、章节/段落最小范围改写、可读的版本差异和下游失效传播。后端提供单元 ID、依赖关系和独立 revision 后，审核队列才开放批量审核与单元级并发。

### P3 报告发布与高级能力

补齐正式发布门禁：所有依赖对象均通过当前版本审核才允许正式输出。支持自定义报告模板与经后端支持的章节排序；在此之前不开放无效的拖拽排序。

## 验收标准

1. 用户进入一个已运行任务后，在不刷新页面的情况下能看到状态继续变化；断线重连、重复事件和事件缺口不会让进度倒退或重复插入结果。
2. 用户在阅读历史报告、下载 Markdown/HTML/PDF 或查看证据时，运行任务不会用全屏遮罩锁住界面。
3. 点击一个证据的 `排除` 后，系统显示影响范围，保留审计记录，并只使依赖它的结论、图表、章节变为 provisional。
4. Agent 2 不允许修改证据事实；对错误数据只能发起 Agent 1 更正请求。非法编辑请求返回可读错误，不静默忽略。
5. 图表卡片可独立预览 ECharts 图和生成图片；图片图表不会因缺少 ECharts option 而消失。单图重生成不影响未选图表。
6. 用户编辑一个段落后，未选章节保持原版本，引用保留或校验失败原因可见，版本差异可读。
7. 两名用户同时审核同一对象时，后提交者得到冲突提示、看到新旧差异，自己的草稿仍可恢复；双击按钮不会创建两次重跑任务。
8. 对话框明确说明允许输入的范围；用户在对话框输入“删除”或“重生成”时，界面引导到对应按钮，不执行模糊自然语言操作。
9. 正式报告只能引用当前已通过的对象版本；报告预览、Markdown、HTML、PDF 的 revision 一致且可追溯。
