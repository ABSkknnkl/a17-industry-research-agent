# 流水线式并行重构：方向与思路（v3.1）

- 日期：2026-09-08
- 性质：**方向性评估与重构思路**，不是落地实施手册（不写代码改动清单、不写测试用例、不贴实现）
- v3 变化：吸收外部复核（codex）意见 + 代码级事实澄清，较 v2 **更保守、以正确性优先**。
- v3.1 修订：**撤回"人审 Agent2 时推测性预生成 Agent4"的错误结论**。只要 Agent4 依赖 Agent3 的真实图表、而 Agent3 在 Agent2 硬门批准之后才跑，链路 `1→2(批准)→3→4` 即串行锁死，**Agent4 不能跨阶段预生成/提前**。"只等 Agent1&2"仅在**人机审核关口**意义上成立，不代表 Agent4 藏在 Agent2 里。可做的并行**只剩段内**。

---

## 0. 结论先行

1. **最该做、最安全的收益 = Agent4 章节"受控并发"**（不是 5 阶段全量并行，也不是跨阶段真流水）。但并发前必须先冻结一个**只读 ReportPlan**，并发后必须有一道**确定性引用检查 + 跨章一致性 Reduce**。
2. **跨阶段真流水（②→④）当前不成立**：章节并非只吃一个维度（CH-01/CH-05 会回退到全部 claims），且普遍依赖 Agent2 末段产出的图表/质量问题/情景风险；"维度闭包"只是 prompt 过滤规则，缺正式调度契约。
3. **图表不是瓶颈、也不该绕过**：默认走确定性 ECharts spec（AI 出图路径默认关），②→③→④ 中 ③ 近乎零成本；正确表述是"Agent2 完成后即时出图 → Agent4"，而非"分析一半就出图"。
4. **"只等 Agent1&2"只在人机审核意义上成立**：默认硬审核门只在 Agent1/2（`run.py:40-42`），Agent3/4/5 不卡人工。但**不能**据此推测预生成 Agent4——Agent4 依赖 Agent3 真实图表、Agent3 在 Agent2 批准后跑，链路串行锁死。批准 Agent2 后，3→4→5 仍按序生成（只是不再逐阶段卡人工）。这段的**时长**靠**段内并发**缩短，而非靠跨阶段重叠消除。
5. **路径仍是原地渐进（抽内核 + 绞杀者迁移），但优先级收敛**：先做 Agent4 并发（带 ReportPlan/Reduce）与基线度量；上下文/记忆/封装作为地基按序补；MCP、长期语义记忆、通用运行时内核**放到赛后**。

## 2. 对两个待澄清观点的判定

### 观点1：Agent2 分析一半 → 出图 → 喂 Agent4

- ✅ **保留**：图表快（F1）、**不绕过 Agent3**。②→③→④ 中 ③ 是近乎零成本的确定性跳板，实际"坍缩"，因此把它当串行瓶颈或主张绕过它都是错的。
- ❌ **修正**：**"半程出图"不成立**（F2）——中点时没有 chart_candidates。正确形态是"**Agent2 两段都完成 → ③ 瞬间出图 → ④**"。
- ⚠️ **更深一层**（F3）：即便图表即时可得，章节也不是"一个维度就能写"——CH-01/CH-05 需要全部 claims，且多数章要吃 supplement 的质量问题。所以真正能提前启动的章节有限，"按维度流水"缺正式契约支撑。

### 观点2：用户只等 Agent1&2，Agent4 并行也完成了

**先厘清边界——你只反驳"人机审核"这一点**（用户看到的仍是流水线、硬门只在 1&2）。这点**成立**，我保留；但我上一版把它引申成"人审 Agent2 时后台预生成 Agent4"，**这个引申是错的，撤回**。

- ✅ **成立**：用户需要动手审核的关口集中在 Agent1/2（+ Agent5 最终发布），体验仍是五阶段流水线。
- ❌ **不成立（撤回）**：不能由此推出"Agent4 在人审 Agent2 的窗口里被推测性预生成、于是审完 2 就几乎不用等"。理由——**只要 Agent4 依赖 Agent3 的真实图表**（赛题要求章节关联引用已生成图表），而 **Agent3 在 Agent2 硬门批准之后**才运行，链路 `1→2(批准)→3→4` 就是**串行锁死**的，Agent4 不可能提前到 Agent2 审核窗口里跑。**"跨阶段预生成 Agent4 草稿"作废。**
- ✅ **唯一真实的并行收益 = 段内**：Agent4 拿到 Agent3 的图后，7 章**内部**受控并发（⌈7/k⌉× 而非 7×）；Agent2 两段若依赖矩阵证明独立也可并发。这些压缩**每个阶段自身的耗时**，但不改变阶段先后，也不让 Agent4 藏进 Agent2。
- 净结论：审完 Agent2 后，用户仍需等"3→4→5 生成"（只是这段不要求逐阶段人工批准）；这段时长靠**段内并发**缩短，而非跨阶段重叠消除。

## 3. 四类基础能力：现状问题 → 优化方向（优先级已按复核收敛）

### 3.1 Skill（能力封装与编排）

**现状问题**
1. 技能包与运行时**双契约漂移**：`skills/` 的 `cli.py` 是死重，运行时走 `catalog.py:18-95` 硬编码 + `client.py` 直连；`data_interpreter/skill_loader.py:38-51` 又只把部分 `SKILL.md` 正文当提示词读。
2. 确定性能力（`calculations/anomaly/reconciliation/normalizer`）埋在 Agent 内部，改一处跑全链路回归。
3. 注册表全硬编码、无发现；gateway 的 `before/after_hooks` 存在但**未接线**（`registry.py:23-48`），无技能级 HITL。

**优化方向**
- 把确定性能力抽成**可独立版本化/测试**的能力单元（借鉴外部技能库"自描述 + 脚本优先 + 渐进披露"范式），降低回归半径。
- 统一技能契约、消除双源漂移；死重 cli.py 要么接线要么清理。
- 用未接线的 hooks 落成**技能级 guardrail + HITL 确认**（危险写/导出/导入走确认闸并回报审计计数）。
- **收敛（复核采纳）**：`SKILL.md` 只作**文档与路由提示**；生产运行时的真相源应是**版本化、白名单化、强类型的 manifest/registry**，**不做"扫描文件系统即自动执行"**。动态 Skill 发现降级为赛后。

### 3.2 MCP（外部工具与数据源统一接入）

**现状问题**：全仓无 MCP；外部数据源是两个硬编码 HTTP 客户端（问财 `skillhub/client.py:22-29`、博查 `websearch/client.py:195-250`），仅靠一个 Protocol 对齐；加数据源要改代码 + 硬编码进 catalog。

**优化方向（后置）**
- 可复用的思想是"把外部接入收敛到统一边界后面（统一工具描述 schema + 可插拔传输 + 发现 + 信任控制）"，而非现在就上 MCP 协议。
- **复核采纳**：赛题直接评分的是"≥6 类问财 SkillHub 能力 + 数据可靠性"，**不是是否用 MCP**。故 MCP 化**放到赛后**；当前只把两个 client 归拢为"数据源适配器"注册进同一网关即可。

### 3.3 上下文管理（组装 / 裁剪 / 隔离 / 传递）

**现状（优点，保留）**：隔离是白名单式且严格（`data_interpreter/service.py:286-290`、`graph.py:263-271,511-521`、`stages.py:15`）；章节按章裁剪（`chapter_writer/prompt_adapter.py:40-185`）。

**现状问题**
1. 只有 char 阈值、无 token 级窗口管理（`config.py:125,42,43`）——B4/B5 截断史根因之一。
2. 无 large-result store：超限直接截断丢内容（`tool_gateway.py:117-138`），`workflow/README.md:62` 自认"待升级为摘要+产物引用"未做。
3. 无摘要/压缩：修复回路把原文 `[:30000]` 直接回塞（`openai_compatible.py:918`）。
4. 分段是 schema 切分非上下文切分（F5）：两段各吃完整 prompt，单次上下文未下降。
5. `stage_results` 是无 reducer 的整包 dict、整写覆盖（`state.py:20`、`graph.py:133-134`）——阶段内多任务并发回写时的写冲突根源。

**优化方向**
- token 预算器替代裸 char 阈值；large-result store + 产物引用（长结果落盘、上下文只放引用/摘要、按需分页读）；摘要压缩中间件。
- 让"分段"真正切上下文（各段只带自己需要的证据子集），既省 token 又降限流。
- 把 `stage_results` 升级为**带 reducer / 单元级版本**的传递契约——**首先服务于段内并发的结果合并**（如 Agent4 并发章节、Agent2 并发分段把各自产物安全写回）。复核提醒：若将来真要跨阶段并行，仅加 reducer 还不够，需另补不可变输入快照、依赖版本+内容哈希、幂等任务 ID、迟到结果拒收、修订取消在途、原子提交/CAS、重试去重；但按 v3.1 结论，当前**不做**跨阶段并行，这些属远期条件项。

### 3.4 记忆（短期会话 + 长期持久化）

**现状问题**
1. 持久层半成品/死配置：`infrastructure/db/` 空壳（`README.md:3` 规划 5 表未实现）；无 ORM；`DATABASE_URL`/`app.db` 死配置（`config.py:33`）。真实只有 `checkpoints`/`writes`/`chapter_checkpoints` 三表。
2. run/审核记录无业务表，风险台账塞进 `input_data`（`graph.py:485-500`）；列表靠 `alist(None)` 全库扫描（`runner.py:103`）。
3. 无保留/压缩策略，快照含全量 `stage_results` 无限增长（实测 22 run → 66MB）。

**优化方向**
- **尽快补**：业务持久层（run/stage/feedback/artifact 表 + 索引）、产物版本、依赖血缘、幂等、stale 状态；清死配置与空壳。
- 加保留/压缩策略（TTL、快照瘦身）治膨胀。
- **收敛（复核采纳）**：金融场景"历史结论向量化回喂"风险大（数据过期、口径/复权/行业分类变化、旧结论污染新研究、来源难解释）。**改为"带有效期的研究缓存"**，缓存键至少含 `query + research_as_of + provider + skill 版本 + schema 版本 + 数据口径`。泛化长期语义记忆**放到赛后**。

## 4. 正确性模型（采纳复核修正）

### 4.1 版本语义：从"绝不回滚"改为"不可变 + 作废"

v2 的"绝不回滚已写章节"与"发现矛盾级联作废重消费"自相矛盾（作废即回滚）。正确设计：
- 已产生版本**不可覆盖**；
- 上游 `revision` 变化后，下游产物标记 **superseded / stale**；
- 用户**不能批准、导出或继续编辑 stale 版本**；
- **重新生成新版本**；历史版本仅用于审计与对比。
> 该模型主要服务于**修订级联**（上游被打回时下游作废）与段内并发产物管理；跨阶段预生成不适用（见 §2 观点2、§4.5）。

### 4.2 Agent4 并发的前置：冻结只读 ReportPlan

不能简单 `gather(7 章)`。并发前冻结一个只读 **ReportPlan**：`research_as_of`、核心结论与论证顺序、术语表、数据口径与单位、claim/evidence 注册表、图表—章节放置关系、章节间引用关系、禁止重复的内容边界。然后：

```
Agent1 → 硬审核 → Agent2 → 硬审核 → Agent3 确定性(近零成本)出图
      → 冻结 ReportPlan → Agent4：7 章受控并发 Map
      → 确定性引用检查 + 跨章一致性 Reduce → Agent5 融合 → 最终发布审核
```

一致性检查发现事实冲突时，**重新生成受影响章节**，而不是让 Agent5 悄悄改数字或统一结论。

### 4.3 Agent2 两段并发的前置：字段依赖矩阵

"schema 字段不重叠"≠"语义独立"（F2/F5）：supplement 的风险/情景/图表候选很可能依赖 core 的趋势与 claims。直接并发可能导致风险结论与核心判断矛盾、图表候选引用不存在的 claim、瞬时 token 翻倍、限流后反而更慢。**先列字段依赖矩阵**：真正独立的维度才并行；依赖 core claims 的部分仍在 core 定稿后跑。

### 4.4 段内并行的结果合并

段内并发（Agent4 多章、Agent2 多段）产生的多份产物回写 `stage_results`，需要**单元级 reducer + 确定性合并/校验**（Agent2 的 `_validate_payload` 合并、Agent4 的跨章 Reduce），并配合 §4.1 的 stale 作废。这是当前唯一需要落地的并行合并语义。

### 4.5 为什么不做跨阶段流水/预生成（v3.1 结论）

链路上 ② 是硬审核门、③ 供 ④ 真实图表且 ③ 近零成本——两头夹住，`1→2(批准)→3→4` 无法在不违反审核语义与图表依赖的前提下重叠。故**撤销 v2 的"②→④ 黄金流水段"与 v3 的"预生成 Agent4 草稿"**；跨阶段并行仅在"未来赛题允许跳过中间审核 + 章节可用 planned_charts 降级（与赛题图表要求冲突）"时才重议，当前**不做**。

## 5. 等价性验证：拆成两套标准（采纳复核）

"终态逐字段一致 / 哈希一致"只适合确定性模块，不适合 LLM 生成。拆两套：
- **确定性层**（计算结果、证据引用、图表数据、融合清单）：**逐字段一致**——这是等价性的锚（`calculations.py`、`fusion.py` 纯函数）。
- **生成层**（LLM 文案）：验证 **schema 合规、claim/evidence 覆盖、数字一致性、禁幻觉规则、章节覆盖率、质量评分**，**不要求文案哈希一致**（同输入两次生成也可能不同）。

方法仍用现有 V8 评测 + 录制回放**双轨跑**（串行 vs 段内并发），但断言按上述两层分别设定。

## 7. 红线（更新）

1. **每阶段人工审核能力保留**：默认硬门在 Agent1/2，Agent3/4/5 可选审核/风险提示，Agent5 最终发布审核；演示仍能展示每阶段的修订能力。任何并行优化不得削弱这一赛题卖点。
2. **证据单写者 + 层级锁死**：证据只由 Agent1 写入，层级只降不升。
3. **并发上限可配**：LLM 与 SkillHub 都有配额，收益建立在有界并发（Semaphore）之上。
4. **等价性分层**：确定性层逐字段一致；生成层不追求文案哈希一致（§5）。
5. **不为"通用 Agent 内核"牺牲赛题真正看重的东西**：数据质量、图表关联、人机审核、最终报告效果优先于架构通用性。
