# 拆掉固定 7 章 21 节大纲 · 修改方案

> 需求：章节结构由报告内容决定，不再固定 7 章 21 节。
> 2026-09-17 · 状态：待评审（**未改任何代码**）

---

## 〇、先澄清一件事：前端不用改

用户原话「报告什么样子前端就应该填对应的内容」——**前端已经是这样的**。核实结果：

| 前端位置 | 章节来源 | 是否硬编码 |
|---|---|---|
| `ReportPreview.vue`（目录结构） | `fusion.chapters` | ❌ 动态 |
| `ReportPreviewView.vue`（侧栏目录） | `fusion.chapters` | ❌ 动态 |
| `StageDigest.vue`（章节正文） | `data.chapters` | ❌ 动态 |
| `MetricCards.vue`（章节/小节统计） | 遍历 `data.chapters` | ❌ 动态 |
| `StageStepper.vue`（阶段小结） | 遍历 `data.chapters` | ❌ 动态 |
| `MetricCards.vue:166` | 文案「标准 7 章 21 节」 | ✅ **唯一硬编码**（纯文案） |

前端仅有的 `CH-0x` / `SEC-0x-0y` 字面量都在 **mock fixture 数据**与 mock 交互脚本里，不在渲染逻辑里。

**结论：这是后端改动，前端只需删一句文案。**

## 一、固定结构实际被「五层」强制（这是工作量所在）

| # | 层 | 位置 | 约束 |
|---|---|---|---|
| 1 | **常量** | `backend/app/agents/chapter_writer/outline.py:23` | `REPORT_OUTLINE` 7 章 × 3 节，标题与 purpose 全写死；`OUTLINE_VERSION = "2026.1"` |
| 2 | **运行时模型** | `backend/app/schemas/chapter.py:24-26` | `chapter_id` 必须匹配 `^CH-\d{2}$`；`sections` **恰好 3 个**（`min_length=3, max_length=3`） |
| 3 | **跨端契约** | `contracts/schemas/chapter-writing-result.schema.json` | `chapters` **minItems=7 / maxItems=7**；`sections` **minItems=3 / maxItems=3** |
| 4 | **服务层校验** | `chapter_writer/service.py:173-196` | 目标章节/小节 ID 必须属于 `REPORT_OUTLINE`，否则 `WAITING_REVIEW` 拒绝 |
| 5 | **融合层质量门** | `report_fusion/service.py:36` + 质量检查 | `CANONICAL_CHAPTER_ORDER = ['CH-01'…'CH-07']`，用户自定义顺序被拒；`chapter_count / section_count` 作为完整性判据 |

### 为什么当初要固定（不能简单删）

固定大纲不是偷懒，它承担三个职责，**拆掉前必须给每一项找到替代**：

1. **确定性兜底**：`fallback.py:140` 用 `REPORT_OUTLINE` 在 LLM 全失败时仍产出完整报告
2. **质量门基准**：判断「报告写全了没有」——没有基准就无法判定完整性
3. **评测可重复性**：V8 评测（101 用例）依赖稳定结构做快照

## 三、修改方案（四阶段）

### 阶段 A｜放宽约束（不动生成逻辑，先让契约能容纳可变结构）

| 文件 | 改动 |
|---|---|
| `app/schemas/chapter.py` | `OutlineChapter.sections`：`min_length=3, max_length=3` → **`min_length=1, max_length=8`**<br>新增章节数量约束（放在 `ChapterWritingResult.chapters`）：**`min_length=3, max_length=12`**<br>`chapter_id` 正则 `^CH-\d{2}$` **保留不变**（编号仍连续两位数，只是数量可变）<br>`section_id` 正则 `^SEC-\d{2}-\d{2}$` **保留** |
| `contracts/schemas/chapter-writing-result.schema.json` | `chapters.minItems/maxItems`：7/7 → **3/12**<br>`sections.minItems/maxItems`：3/3 → **1/8** |
| `backend/tests/test_contracts.py` | 同步断言新边界 |

**为什么保留 ID 格式**：`CH-01`/`SEC-01-02` 是跨阶段引用的稳定键（图表 placement、段落归属、锚点 `#chapter-1`）。放开**数量**，不放开**格式**，能把改动面收敛在数量上。

### 阶段 B｜大纲改为「生成 + 校验」（核心）

新增 `backend/app/agents/chapter_writer/outline_builder.py`：

```
输入：A2 结构化结论（claims / dimension_coverage）+ 用户研究问题 + report_depth
  ↓
LLM 产出大纲候选（章节数、章标题、每章节标题 + purpose）
  ↓
确定性校验（不通过 → 拒绝并重试；仍失败 → 回退 REPORT_OUTLINE）
  · chapter_id 连续（CH-01…CH-0N，无跳号）
  · 章节数 ∈ [3, 12]，每章节数 ∈ [1, 8]
  · 标题非空、去重；每节 purpose 非空
  · 章节必须能覆盖 A2 已产出的核心结论（覆盖度校验，避免跑题）
  ↓
输出：当次 run 专用大纲
```

配套：
- 大纲随 `ChapterWritingResult` **落盘**（新增 `outline` 字段），供阶段四渲染、阶段五融合、审核页展示与前端目录使用
- `OUTLINE_VERSION` 语义从「固定大纲版本」改为「**大纲生成规则版本**」（生成规则变了才递增）
- `REPORT_OUTLINE` **保留**，降级为「LLM 失败时的确定性兜底大纲」

### 阶段 C｜去掉五层中的硬编码依赖

| 位置 | 现状 | 改为 |
|---|---|---|
| `chapter_writer/service.py:173-196` | 校验 ID ∈ `REPORT_OUTLINE` | 校验 ID ∈ **当次 run 大纲** |
| `chapter_writer/service.py:232-237` | 遍历 `REPORT_OUTLINE` 决定写哪几章 | 遍历**当次大纲** |
| `chapter_writer/fallback.py:140` | 用 `REPORT_OUTLINE` 拼兜底稿 | **保留**（这就是它的职责），但接受传入大纲 |
| `report_fusion/service.py:36/137` | `CANONICAL_CHAPTER_ORDER` 固定比对 | 改为**从上游 `chapter_write.chapters` 推导顺序**，不再比对固定 ID 集合 |
| 融合质量门 | `chapter_count == 7`、`section_count == 21` | 改为与**当次大纲**比对（`大纲节数 == 实产节数`）；总数为 0 视为失败 |

> **质量门是这次改动最容易被忽略、也最危险的一环**：去掉固定基准后，如果不换成「与当次大纲比对」，「报告写全了没有」就无从判断，质量门会退化成永远通过。

### 阶段 D｜前端与评测

| 位置 | 改动 |
|---|---|
| `MetricCards.vue:166` | hint 由「报告结构（标准 7 章 21 节）」改为**由数据算出**（如「本次报告结构」） |
| 其余前端 | **零改动** |
| `backend/tests` 21 处 | 改为「按当次大纲断言」+ 保留一组「固定兜底大纲」用例 |
| `eval/` 3 个文件 | `surrogate_models.py` 与 2 个 transcript 需同步 |

## 四、需要你拍板的 4 个问题

### 1. 大纲由谁定？（最关键）

| 选项 | 说明 | 代价 |
|---|---|---|
| **A. LLM 从结论生成** | 最贴合「按报告定」 | 结构不可预测；同一主题两次跑可能不同；评测难 |
| **B. LLM 生成 + 阶段四可见可改**（**我推荐**） | 阶段四本来就是审核门，把大纲展示在审核页，用户可改章节 | 需在审核页新增大纲编辑（前端工作量） |
| **C. 创建任务时用户指定** | 最可控 | 不算「按报告定」，是「按用户定」 |

推荐 B：既满足「按报告内容生成」，又保留人工兜底，且复用已有审核门。

### 2. 兜底是否保留？
建议**保留** `REPORT_OUTLINE` 作为 LLM 失败时的兜底——否则 LLM 异常时报告会没有章节，退化为不可交付。

### 3. 章节数上下界？
建议 **3–12 章**、**每章 1–8 节**（避免退化成一章或二十章；上下界可在 `settings` 里配置）。

### 4. 评测基线怎么办？
现有 V8 评测（101 用例）依赖固定结构。建议：
- 结构类断言从「`== 7`」改为「**ID 连续 + 与当次大纲一致**」
- 另立「结构弹性」用例组，验证 3 章 / 12 章等边界

## 五、风险与边界

| # | 风险 | 处置 |
|---|---|---|
| 1 | **质量门失去基准** → 永远通过 | 必须改为与当次大纲比对（阶段 C） |
| 2 | 三层约束只改一层 → 契约/模型校验冲突 | 阶段 A 一次性同步改（schema + 契约 + 契约测试） |
| 3 | 21 处测试与评测快照大面积失效 | 分批改，先改契约层再改断言；保留兜底大纲用例 |
| 4 | LLM 生成的大纲跑题 | 加大纲↔结论的**覆盖度校验**；不通过拒绝重试 |
| 5 | 章节数不稳导致前端目录长度差异大 | 前端已动态渲染，无需改；但需确认目录在 12 章时的可读性（可能要滚动） |
| 6 | 跨阶段引用（图表 placement_section_id、锚点） | ID 格式不变，引用机制不受影响 |

## 六、建议落地顺序

1. **阶段 A**（契约放宽 + 契约测试同步）——可独立验证，不影响现有行为
2. **阶段 B**（大纲生成器 + 落盘 + 兜底回退）——新能力，用单测覆盖
3. **阶段 C**（服务层/融合层去硬编码 + 质量门改为相对判据）——行为切换点
4. **阶段 D**（前端文案 + 21 处测试 + eval 同步）
5. 端到端：跑一次完整流水线，确认前端目录按真实报告渲染

> 已核实：`backend/app/core/config.py` **没有**任何章节相关配置项，
> 章节数上下界需**新增**配置（建议与报告深度 `report_depth` 联动：brief 更少章、deep 更多章），
> 避免边界值散落在 `outline_builder.py` 与契约两处。
