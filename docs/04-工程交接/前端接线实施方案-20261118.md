# 前端接线实施方案

日期：2026-11-18 ｜ 范围：`a17-industry-research-agent/frontend` ｜ 目标：让已画好的页面、表单、按钮真正跑通，不新增功能

---

## 0. 结论先说

前端**路由、列表、创建、下载、Skill 库、事件流、版本历史已全部接通真实接口**，不存在整页未接线。真正的问题集中在**人机审核弹窗**：控件读写字段名与后端实际产出不一致，导致「点了有成功提示、但内容没变」甚至「保存后报告摘要被清空」。

因此本方案只做三件事：

1. 修 4 个 P0 接线缺陷（写入无效 / 数据丢失 / 假数据当真数据提交）；
2. 统一空态、禁用、异常提示口径，补齐 5 处 P1 展示错位；
3. 用新能源汽车归档数据 + 12 例问题数据，把人机审核按钮的门禁跑成可回归的用例。

**不改后端业务算法，不改流水线状态机。** 后端仅在「mock 联调服务器」侧做增强。

## 1. 判定口径

一个控件算「未接线」，当且仅当命中以下任一条：

| 判据 | 说明 |
|---|---|
| A. 读空 | 组件读的字段在真实 `stage_results[*].data` 中不存在，落到硬编码兜底 |
| B. 写空 | 提交的 `edited_data` 键没有任何下游消费者，改了等于没改 |
| C. 丢弃 | 提交参数被后端契约静默忽略 |
| D. 覆盖 | 未修改的字段以空值下发，覆盖掉已有内容 |
| E. 未挂载 | 组件/页面没有任何引用入口 |

核对基准：`data/runs/run-20261118150031-7ca33ff730f5`（新能源汽车，全五阶段已完成，revision 2）与 `run-20261117223001-0f456856f2a5`（半导体设备，停在阶段一）。

## 2. 待接线清单

### P0 — 必须修（影响审核有效性 / 造成数据丢失）

#### P0-1 阶段二「补充背景知识与修正判断」：读假研判、写死字段

- **位置**：`components/StageInterventionModal.vue:292-342`
- **现状**：读 `data.findings / key_findings / claims`；真实 `data_interpret.data` 只有 **`insights[]`**（`insight_id / title / conclusion / significance / confidence / evidence_record_ids`）。三个键全部落空 → 弹窗恒定显示内置样例 J-1「产业处于高景气周期与出海放量红利期」、J-2「上游供给扩张带动成本曲线优化」。
- **后果**：用户裁决的是假研判；提交写 `findings` + `key_findings`，后端 `state_machine.py:806` 只做 `cur_data.update()`、`:831` 只做 `ir_json.update()`，**无字段白名单**，于是新增两个无人消费的键，真实 `insights` 原封不动流向 A3/A4/A5。人工裁决 0 生效（判据 A+B）。
- **改法**：
  - 读：`insights` → `{ id: insight_id, title, text: conclusion + '\n' + significance }`，保留 `confidence / evidence_record_ids / related_*` 原样透传。
  - 写：只回写 `insights`，删除 `findings` / `key_findings` 双写。
  - `decision === 'reject'` 不物理删除，标 `review_status: 'rejected'` 并保留证据 ID，保证证据链可追溯。
  - 删除 J-1/J-2 兜底，空数组走空态。
- **验收**：弹窗条目数 == `insights.length`；提交后 `GET /runs/{id}` 的 `insights` 内容随裁决变化，且 `evidence_record_ids` 不丢。

#### P0-2 阶段五「投资评级与执行摘要定稿」：保存会清空报告摘要

- **位置**：`StageInterventionModal.vue:993-1018`
- **现状**：`initFusionSummary` 读 `data.executive_summary`，但**融合阶段 data 里没有这个键**（摘要对象在 `artifacts/report_view.json`，文本在 `data_interpret.executive_summary`）→ 编辑框初始为空。提交时无条件带 `executive_summary: ''`。
- **后果**：`backend/app/core/report_exports.py:60-63` 把字符串转成 `{...prior, headline: ''}`，**报告执行摘要标题被清空**（判据 D，数据丢失）。
- **改法**：
  - 初值优先取 `report_fusion.data.executive_summary_headline`（若无则回退 `data_interpret.executive_summary`）；两处都取不到时编辑框置只读 + 提示「摘要需重新融合后编辑」。
  - 提交做 dirty-check：**未改动的键不下发**；`executive_summary` 为空串时禁止提交。
- **验收**：T10 用例——只改评级提交，`edited_data` 不含 `executive_summary`；导出 MD/HTML 的 headline 与提交前一致。

#### P0-3 阶段五「8 张核心指标卡定制」：标签、数值、涨跌幅三处错位

- **位置**：`StageInterventionModal.vue:958-986`
- **现状**：真实 `key_metrics[]` 字段为 `name='revenue'（英文）/ entity='比亚迪' / value=803964958000 / unit='元' / change_pct=0.03456（小数）`，**没有 `label`、没有 `change_rate`**。
  - `label: m.label || m.name || m.title` → 卡片标题显示 `revenue`
  - `value: String(m.value)` → 显示 `803964958000`
  - `change_rate: m.change_rate || m.change` → 恒为空
- **后果**：`report_exports.py:64-72` 用 `label/value/unit` 生成 `metric_cards`，报告里出现「revenue 803964958000 元」（判据 A）。
- **改法**：
  - `label = entity + fieldLabel(name)`，中文名复用 `api/labels.ts`，不新造词典；
  - 金额类按 `unit` 归一到亿元（保留 2 位小数）并同步改写 `unit`，百分比类保持 `%`；
  - `change_rate` 由 `change_pct * 100` 格式化，`null` 显示「—」而非 0；
  - 透传 `evidence_record_ids`（后端按 `evidence_ids || evidence_record_ids` 取值）；
  - 去掉 `metrics_cards` 双写（不在 `ReportViewModel.model_fields` 内，属死键）。
- **验收**：T03 用例非法值被拦截；合法值提交后导出文件中卡片为「比亚迪 营业收入 8,039.65 亿元 · +3.46%」。

#### P0-4 阶段一「定向补采」：18 个硬编码假数据点

- **位置**：`components/PartialRefetchPanel.vue:133-359`（`initGroups`）、`:495-521`（payload）
- **现状**：清单固定 18 点 `F-01…P-04`，数值 `¥1,342 亿 / 21.4% / 612 万辆`、可信度 96/91/62 全为写死；只有企业名取自真实 `source_records`，取不到时回落「样本龙头甲/乙」。
- **后果**：提交 `data_point_ids: ['F-01', ...]`，而后端 `state_machine.py:1119-1127` 的 `_supplement_demand` **只读 `domains / entities / query_hint / reason / probe_mode`**，`data_point_ids` 仅在演示模式 `replay_probe` 中生效 → 非演示任务的点选被静默丢弃，且 `query_hint` 里带着假数值去检索（判据 A+C）。
- **改法**：
  - 清单由 `data_fetch.data.source_records[]` 生成：`id=record_id`、`label=metric`、`entity=entity_name`、`period`、`value+unit`、`source=skill_name`；
  - 缺口判定改用 `question_requirement_coverage` / `metric_requirements`，不再用「value 为空」猜；
  - 无 `source_records` 时整表空态，只保留「清单外补充诉求」（走既有 `replenish` 契约）；
  - 保留现有 `domains/entities/query_hint` 组装逻辑，后端契约不动。
- **验收**：T02 用例空态且不发点级请求；真实 run 下清单条数 == `source_records.length`，勾选后 `query_hint` 中不含任何样例数值。

## 4. 状态与交互处理统一规范

所有审核控件按同一套状态机实现，避免各写一套：

```
idle → validating → submitting → (success | conflict | error) → idle
```

| 状态 | 触发 | UI 表现 |
|---|---|---|
| `idle` | 弹窗打开 | 从真实数据初始化；无数据显示空态，**禁止样例兜底** |
| `validating` | 点提交 | 前端校验：必填、数值可解析、空串归一 `null`；不通过只提示，**不发请求** |
| `submitting` | 校验通过 | 按钮 `loading` + 同组按钮 `disabled`；执行类动作展示 `PipelineOverlay` |
| `success` | 2xx | `ElMessage.success` + `emit('submitted')`；阶段五通过跳下载页 |
| `conflict` | 409 | `ElMessage.warning`（透出后端原文）+ `emit('conflict')` + 自动 `GET /runs/{id}` |
| `error` | 其他 | `ElMessage.error`（含 `code`），保留用户已填内容，**不清空表单** |
| `finally` | 任意结束 | `submitting=false` + `hidePipelineOverlay()`，按钮恢复可点 |

**按钮门禁矩阵**（`ReviewActions.vue`，实现须与下表逐格一致）：

| 条件 | 主通过按钮 | 重跑/介入按钮 | 取消任务 |
|---|---|---|---|
| 正常无风险 | `btn-approve` 可点 | 可点 | 可点 |
| `acknowledgement_required_codes` 非空 | 换成 `btn-risk-notice` | 可点 | 可点 |
| `blocking_risk_codes` 非空 | **不渲染** | 可点（用于修复） | 可点 |
| `demo_probe_pending === true` | **不渲染** | 可点 | 可点 |
| `runtime_alert.recoverable === false` | **不渲染** | **全部 disabled** | 可点 |
| 融合 `quality_notice` / `exports_stale` | **不渲染**（签发挂起） | 可点 | 可点 |
| `chapter_write` 有缺口且 ack 非空 | 不渲染 | 「修订问题章节」+「确认缺口并继续质检」 | 可点 |
| `submitting` | loading | disabled | disabled |

**三条硬约束**：

1. 禁用按钮**不得发出任何 HTTP 请求**（用 Playwright 断言请求数为 0，而不是只看样式）。
2. `accept_with_risks` 的 `accepted_risk_codes` 必须与当前 `acknowledgement_required_codes` **排序后全等**，否则后端 `review_decisions.py:94-96` 直接拒绝。
3. 决策类动作必须携带 `decision_id` + `risk_snapshot_sha256`；弹窗打开期间若 revision 变化，先关闭风险窗再重取。
