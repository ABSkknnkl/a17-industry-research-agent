## 1. 这个功能到底是什么（大白话）

报告要 18 个数字，AI 已经抓到 13 个，还缺 5 个，另有 2 个来源不可信。

- **以前**：只有一个按钮——「重来一遍」。18 个全部重跑，慢、费钱，本来抓对的还可能被搅乱。
- **现在**：清单上一条一个数，勾「我要补这个」，勾了谁就只补谁，没勾的一动不动。

三种结果：

1. **缺失的**（红色「缺失」）→ 补回来
2. **不可信的**（旁边标 62%）→ 换个可信版本回来，旧值被顶掉，但会告诉你从多少变成多少
3. **一个都不勾** → 什么都不做，点了会提示「请至少勾选一个数据点」

唯一像「删」的动作，是同一指标抓到新值时旧值被替换；不允许静默替换，必须出新旧对比。

## 2. 原来错在哪（三个硬伤）

### 2.1 颗粒度错了
原来勾的是「产业链上下游」「宏观政策驱动」这种整章级模块。勾一个等于重写一章，已经对的数据也被重算，成本高且容易把对的改成错的。

研究员真正想说的是「2024Q3 的月度产销缺了，补一下」「宁德的口径换合并报表」——这是数据点级的话。

### 2.2 默认全勾是反模式
四个选项默认全选，用户点一下就是「重跑一遍」，人工把关的价值直接归零，退化成贵的重试按钮。

### 2.3 「其余数据完整保留」埋了雷
新旧两批数据如果时间窗、口径不同，报告里同一指标会出现两个数，跨章节对不上。必须有版本/口径标记和 diff，否则「保留」是负债不是资产。

## 3. 改成了什么样

### 3.1 覆盖条（一眼看懂现状）
`13 已采 / 共 18 · 5 缺失待补 · 2 低可信待核`，右侧有「只选缺口」「清空」「全部 / 只看缺口」筛选。

### 3.2 点级清单
4 个分组（财务、产业链、宏观、竞争格局），共 18 个数据点骨架。每行 6 列：

```
复选框 | 指标名 + 实体·期间 | 当前值 | 来源标签 | 可信度圆点+百分比 | 缺口原因
```

- 缺失行的值显示红色「缺失」
- 来源按类型着色（年报=绿、公告=蓝、协会=灰、政策=橙、研报=灰）
- 可信度：≥85 绿、70–84 黄、<70 红
- 每行可整行点击切换，复选框本身不会双重翻转（已验证）

### 3.3 默认选择
默认只勾「有缺口 / 可信度 < 70 / 值为空」的 8 项，其余 10 项留白。

### 3.4 重采口径（结构化，不再让人打一段自由文本）
| 字段 | 默认 | 作用 |
|---|---|---|
| 时间范围 | 最近 3 年 | 防止新旧数据时间窗错位 |
| 标的池 | A股核心标的 | 可多选：港股对标 / 未上市龙头 / 全球同业 |
| 财务口径 | 合并报表（年报口径） | 可切单季度 / 扣非 / 按原文披露不调整 |
| 取数方式 | **大模型探针** | 可切「常规单次查询」 |
| 补充说明 | 空 | 唯一需要打字的地方 |
| 记住这套口径 | 勾选 | 下次打开自动带入（字段已下发，持久化未做） |
| 生成数据底稿说明 | 勾选 | 供报告附录 / 合规备查 |

### 3.5 提交前给成本
右下角实时显示：`已选 N 个数据点 · 预计新增 M 条记录 · 约 X 分钟`（每点按 6 条、每条 5 秒估算）。

对 deadline 敏感的研究员，这个数比任何文案都有说服力。

### 3.6 明确告知重采后会发生什么
底部一行浅色提示：重采完成后给出新旧对比（哪几个数变了、从多少变成多少、影响哪些章节），未勾选的数据保持原值不动。

## 4. 和 LLM 探针的关系：不重复，但要合并

### 4.1 两者本是不同维度
- **局部子域重采**：决定「取什么」（购物清单）
- **大模型探针**：决定「怎么取」（会自己改写查询、换 skill、最多 4 轮自纠错的跑腿）

### 4.2 为什么用户会觉得重复
查代码发现：`partial_refetch` 在重建 demand 时把 `probe_mode` 丢了，`probe_meta` 永远取到 `static`。于是两条路最后都落到同一个主链路取数，看起来当然像重复。

而主链路 `fetch_supplemental` 的问题很具体：

```python
query = query_hint or f"查询{ent_str}...营业收入、归母净利润、销售毛利率、资产负债率"
```

它**确实**会用你的 query_hint，但只发**一次**、不改写、不重试。问财对着一长串中文「点名清单」基本给不出东西——这不是 bug，是它本来只适合固定口径的批量补采。

### 4.3 合并后的分工
```
勾点（取什么）
   └─> 探针（怎么取）：自己选 skill、写 query、看返回结果再调整，最多 4 轮
          └─> 成功 / 明确失败（不会假装成功）
```

探针不是重采的替代品，是重采的**执行引擎**。

### 4.4 一个边界
后端仍按 `domains[0]` 定位子域。所以跨组勾选时只有第一组生效。演示和真实使用建议集中在同一组（目前实现里财务组排第一，正好是点级重采最常用的场景）。

## 6. 数据契约

提交给后端的 `edited_data`：

```json
{
  "action_type": "partial_refetch",
  "domains": ["financials"],
  "data_point_ids": ["F-01", "F-02"],
  "entities": ["比亚迪"],
  "query_hint": "补采 2 个数据点：比亚迪·营业收入(FY2025Q3)；比亚迪·归母净利润(FY2025Q3)；时间范围：最近 3 年；标的池：A股核心标的/港股对标；财务口径：合并报表（年报口径）",
  "reason": "局部子域重采",
  "probe_mode": "llm_dynamic",
  "calibration": {
    "time_range_years": 3,
    "universe": ["a_share", "hk"],
    "finance_basis": "consolidated",
    "remember": true
  },
  "attach_worksheet": true
}
```

兼容性：

- 后端读的是 `domains` / `query_hint` / `entities` / `probe_mode`，其余字段忽略不报错
- `entities` 只下发本次 run 真正识别到的公司名（过滤掉「行业大盘」「上游环节」这类非主体）

## 9. 遗留与下一步

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | 预览页的金额/百分比是示意数据 | 拿真实报告对照会露馅 | 从 `source_records` 绑定真实值（需按 metric + entity 匹配，约 20–30 行） |
| 2 | 后端只认 `domains[0]` | 跨组勾选时只有第一组生效 | 后端按 `domains` 逐个循环，或前端限制只能在同一组内勾选 |
| 3 | 后端未消费 `data_point_ids` | 报告层做不到「只换这几个数、其余不动」 | 后端按点逐个调用探针，成功一条替换一条，失败的保持原值并标注 |
| 4 | 没有真正生成 diff / 数据底稿 | 合规价值打折 | 重采后对比新旧记录，输出变更表 + 一页底稿 |
| 5 | 「记住这套口径」只下发字段 | 下次打开不会自动带入 | 加账号级存储（`user_settings.json` 或后端偏好表） |
| 6 | 探针成本 | 每点最多 4 轮 LLM 调用 | 默认只对点级清单开；全量取数保持主链路 |

## 11. 一句话结论

对券商研究员和买方分析师，这个功能的价值不在于「能勾几个框」，而在于**每条数据都能说清从哪来、按什么口径、改了什么、能不能复现**。审核环节本身就在产出审计轨迹——这是纯 AI 一键出报告给不了的东西。对只看结论的零售用户，这个入口应当隐藏。
