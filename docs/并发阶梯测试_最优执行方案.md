# 并发阶梯测试 · 最优执行方案（测试模块全开）

> 目标：在**测试模块全部功能开启**的前提下，求**墙钟时间最短**的并发执行方案。
> 范围：仅测试模块；**不含智能体5（report_fusion）与产业链生图**（二者不参与测试）。

## 0. 结论先行

**最优解 = 全局任务队列 + 单一并发池 + 爬坡探测限流阈值 + 全速冲刺。**

预期墙钟 **2.5 ~ 3 小时**（对比「20 批串行 + 阶梯全量」的 ~10 小时，提速 **3~4 倍**）。

派生出的三条调度原则：

| # | 原则 | 取代 |
|---|---|---|
| 1 | **全局队列单池**：100 份一次入队，只有「并发数」一个限流器 | ❌ 20 批串行（每批尾部等待 = 空转） |
| 2 | **爬坡用探针，不用全量**：阶梯只为找阈值，6~8 条探针即可 | ❌ 全量按 3/4/5 分档跑（低档位重复劳动） |
| 3 | **批是逻辑分组，不是调度屏障**：分批只用于指标汇总 | ❌ 批 A 跑完才开批 B |

## 2. 时间模型与最优并发度

### 2.1 模型

单份报告 4 阶段**内部串行**（取数→解读→图表→章节），因此：

```
墙钟 W(N) = ⌈M / N⌉ × T(N)        M = 报告总数（100）
吞吐 rate(N) = N / T(N)            （份/分钟）

T(N) ≈ T₀ · (1 + β(N-1))     , N ≤ N_cap   （资源充裕，β≈0）
T(N) ≈ T₀ · (N/N_cap)^α      , N > N_cap   （超载：限流重试，α > 1）
```

### 2.2 求解

- 当 `N ≤ N_cap`：`W = M·T₀/N` → **随 N 单调递减** → 越大越快
- 当 `N > N_cap`：α>1 时 `W ∝ N^(α-1)` → **随 N 递增** → 越大越慢

```
∴ 最优并发度 N* = N_cap （恰好不触发限流的临界点）
```

**这是一个「找拐点」问题，不是「选一个大数」问题。** N_cap 未知（已知 >4），必须实测。

### 2.3 理论下限

任一份报告内部 4 阶段串行，故：

```
W_min ≥ max 单条耗时 ≈ 16.6 分钟（实测长尾）
```

要逼近这个下限需 N ≥ 100（全部同时跑）→ 必然限流。**所以现实最优在 N_cap 处，不在极限。**

### 2.4 限流阈值的先验估计

| 层 | 单份占用 | N=8 | N=12 | N=16 |
|---|---|---|---|---|
| 技能并发（`SKILL_CONCURRENCY_LIMIT=7`） | 7 路 | 56 路 | 84 路 | 112 路 |
| 章节并发（`CHAPTER_CONCURRENCY=7`） | 7 路 | 56 路 | 84 路 | 112 路 |

4 并发（28 路）实测无压力 → **N_cap 的经验区间估计为 8 ~ 16**。

## 3. 最优调度结构（三处改动）

### 改动 1：批串行 → 全局队列

**现状（我原方案）**：20 批 × 5 条，批间串行。

```
批A ████████░░░░      ← tail 等待：批内最慢者（16.6min）决定批次结束
批B ░░░░░░░░████████  ← 前面 11 分钟池子是空的
```
每批浪费 ≈ (max − avg) ≈ 4.5 分钟 × 20 批 ≈ **90 分钟纯空转**。

**最优**：100 份全部入队，池子永远满载。

```
队列 → [池子 N 个槽位] → 完成即刻补位
```

**收益：约省 1.5 小时。**

### 改动 2：全量阶梯 → 探针爬坡

阶梯的目的是**定位 N_cap**，不需要 100 份都走一遍。用 6~8 条**代表性探针**（各簇首条 C-001/011/021…）在一轮内测完 3~4 个档位。

```
档位序列（AIMD 式）：6 → 12 → 24 → (回落) 16
判据：出现 402/429/quota 或 单条耗时中位数上升 >30% → 判定超载
N* = 最后一次「无超载」的档位
```

**收益：避免低档位重复劳动约 3 小时。**

### 改动 3：并发数取 min(池容量, 需求)

池容量 = N*，但单批逻辑仍按 5 条聚合指标（满足"分批"这项测试功能）。

# 附录 A · 「先跑智能体1 + 3 终端」方案的时间核算

## A.1 单份耗时拆分（禁生图，3 个真实 run 平均）

| 阶段 | 耗时 | 占比 |
|---|---|---|
| **智能体1 取数** | **1.2 分** | **9.8%** |
| 智能体2 解读 | 3.0 分 | 24.4% |
| 智能体3 图表 | 5.3 分 | 43.1% |
| 智能体4 章节 | 2.7 分 | 22.0% |
| ~~智能体5 融合~~ | ~~1.2 分~~ | 已排除 |
| **单条 1→4 合计** | **12.3 分** | — |

> 交叉验证：4 并发实测单条 12.1 分 ≈ 12.3 分 ✅ 数据自洽。

## A.2 关键事实

**取数只占 9.8%。** 所以「把取数单独提前跑」这件事本身的收益上限极低 ——
即使取数并发开满、耗时压到 0，最多也就省 **11 分钟**。

**真正的加速杠杆是「同时在跑的份数」，不是「分几个阶段」。**

## A.3 对比核算（M = 100 份）

| 方案 | 阶段A（取数） | 阶段B（2→4） | 合计 | vs 基准 |
|---|---|---|---|---|
| **基准**：单池 N=12 一次到底 | — | ⌈100/12⌉×12.3 = 9×12.3 | **111 分** | — |
| 两阶段 + **3 终端各串行**（N_B=3） | ⌈100/20⌉×1.2 = 6 | ⌈100/3⌉×11.0 = 34×11.0 | **380 分** | ❌ **慢 3.4 倍** |
| 两阶段 + **3 终端各 4 路**（N_B=12） | 6 | ⌈100/12⌉×11.0 = 9×11.0 | **105 分** | ✅ 快 5% |
| 两阶段 + **3 终端各 8 路**（N_B=24） | 6 | ⌈100/24⌉×11.0 = 5×11.0 | **61 分** | ✅✅ **快 45%** |

## A.4 结论

1. **「先跑取数」本身只省 ~6 分钟**（取数仅占 9.8%）→ 分阶段不是加速来源。
2. **「3 终端」的价值完全取决于每终端内是否并发**：
   - 每终端**串行**跑 → 并发仅 3 → **慢 3.4 倍**（这是最需要避免的坑）
   - 每终端内部**各开 8 路** → 总并发 24 → **快 45%**
3. 3 终端真正的价值是**规避单点限流**（把压力分散到 3 个进程），而不是「3 倍并行」。
4. 因此**最优组合** = 取数高并发前置（N_A≈20）+ 3 终端 × 每终端 8 路（N_B≈24）
   → 预计 **~1.0 小时**，仍须先用探针实测 N_cap 确认 24 路不触发限流。

## A.5 两个必须知道的风险

| 风险 | 说明 |
|---|---|
| **磁盘** | 100 份 `dataset.json` 落盘，单份 6~29MB → **合计 1~3GB**。磁盘不足会让阶段2 直接失败。 |
| **补数闭环断裂** | 系统本有 3→1 补数回路（`adapters.py:764`：图表 <4 张且有诉求时回采）。但阶段1 提前跑完后该回路依赖的 `dataset.json` 已固化，**无法再回到阶段1 重取**——分阶段会让这个缺口变硬。 |
| **收益前提** | 上面的「快 45%」建立在 N_B=24 不触发限流之上；若 24 路撞限流，会退化成 A.3 第 2 行的形态。**必须先跑探针。** |
