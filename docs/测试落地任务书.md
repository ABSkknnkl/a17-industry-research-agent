### 1.2 状态机语义（测试用例的预期结果以此为准）

- **五阶段**：`data_fetch → data_interpret → chart_generate → chapter_write → report_fusion`
- **run 状态**：`pending / running / waiting_review / approved / completed / failed / cancelled`
- **六种审核动作**：`approve`、`accept_recommendation`、`accept_with_risks`（三者同分支，推进）；`customize`、`revise`（同分支，带反馈重跑）；`regenerate`（清空当前阶段重跑）
- **审核门**：默认 `review_stages` 含全部五阶段（`state_machine.py:160` 与 `:648`），实际默认勾选前两个；阶段完成后若命中 `review_stages` → `waiting_review`（`:795`，**已无 report_fusion 硬排除**）；未命中则自动通过，其中 `report_fusion` 置 `completed`、其余置 `approved`（`:803`）
- **断点续跑**：`resume` 带 `from_stage`，前置阶段产物依赖表见 `state_machine.py:609` 附近（如 `report_fusion` 依赖 `chapter_result.json`）

## 6. 执行方式与"实际结果"填法

### 6.1 三步验证"测试文件能否使用"

1. **可收集**：`pytest --collect-only` 零 error（import 错误、fixture 缺失、路径问题都在这一步暴露）
2. **可运行**：全绿，或每条失败都能归因到 §7 的四类之一
3. **可自证离线**：见 §6.3

运行环境（已验证的调用方式）：
```
PYTHONPATH=<项目根>:<agents_core 五个子目录>
解释器：/Users/Zhuanz1/PycharmProjects/同花顺/backend/.venv/bin/python
```
> 后端测试较慢（源库经验：`backend/tests` 单跑约 6 分钟），分批跑、输出重定向到文件再 grep（管道 grep 汇总行常静默无匹配）。

### 6.2 结果一次写死，不重跑（用户裁决）

- 真实/离线跑**只做一轮**，产出即冻结：落 `data/runs/` 或 `eval/transcript/{run_id}/`，记 tar 快照 SHA-256
- 之后所有判定走 **replay**（源库 `transport.py` 的 record/replay，strict miss=fail，可照抄）
- 报告"实际结果"列一次填死，每条附 `run_id` + 快照 SHA-256
- **必须在报告首部写显式声明**：「实际结果对应快照版本 {SHA-256}；此后的代码变更未重新验证。」不要让读者以为结论仍然有效。

### 6.3 零真实外呼的自证（对应 F0-06 模式真实性）

- 每条测试记录 `provider_mode`，取值只能是 `mock` / `replay`；**禁止**标 `live`
- 若用合成夹具，额外标 `input_source: synthetic`（V8 的诚实性双标注：禁止用 live 掩盖上游为合成）
- 断言层加一道护栏：测试期间若发生任何对外网络调用 → 直接 fail（可复用源库 conftest 的 autouse 断网思路）

### 6.4 "实际结果"列填法（禁止只写"通过"）

格式：`状态 ｜ 关键实测值 vs 判据 ｜ 证据指针 ｜ run_id`

示例：
- `pass ｜ CR3=42.31%，engine.py 重算 42.31%，偏差 0.00% ≤ 0.01% ｜ interpretation_report.json#/calculated_metrics/3 ｜ run-20260923094843-353`
- `fail ｜ chart_result.json 出现 2 张 industry_chain（判据 ≤1）｜ chart_result.json#/charts[7,11] ｜ run-20260923094843-353`
- `blocked ｜ A3 阶段抛 KeyError('evidence_ids')，已隔离，现场存 blocked/A3__E-23.json ｜ traces.jsonl#L142 ｜ run-...`
- `skipped ｜ C1/dupont_roe 无基准值（baselines.expected=null，黄金样本未含该计算）｜ baselines.json#/baselines/0`

## 7. 缺陷记录与执行结论规范（沿用 V8 §12，不改）

### 7.1 四态

`pass`（全检查点通过）/ `fail`（普通缺陷：流程跑通结果不符）/ `blocked`（阻断故障被隔离桩跳过，**等同 fail**，计入缺陷统计）/ `skipped`（合法跳过：与该用例技能无关或触发条件未满足，**不含**阻断隔离）。
报表明确三态：**通过 / 条件失败 / 阻断故障（已隔离跳过）**，禁止把 `blocked` 混入 `skipped`。

### 7.2 根因归因 A–E（信号硬判优先于模型判定）

| 码 | 类别 | 典型判据 |
|---|---|---|
| A | 提示词缺陷 | 指令模糊、约束缺失、输出格式要求不严谨 |
| B | 模型底座缺陷 | 幻觉、工具调用能力不足、推理不足（本轮不跑真实模型 → B 类**只能登记不能确认**，须在报告注明） |
| C | 工具 Schema/MCP 缺陷 | schema 错误、参数校验缺失、服务异常 |
| D | 记忆/上下文缺陷 | 上下文丢失、历史污染、窗口溢出、状态重复无进展 |
| E | 业务逻辑缺陷 | 业务规则本身设计错误 |

### 7.3 每条缺陷固定 8 字段

被测对象 / 故障等级（阻断性故障 · 普通功能缺陷）/ 复现输入 / 实际现象 / 原始快照片段（指向 `blocked/{agent}__{case_id}.json`）/ 根因分类(A–E) / 修复建议 / 测试结论（该智能体是否满足上线标准）。

### 7.4 四类问题分流（决定"能不能动手"）

| 类 | 例 | 处理 | 谁能改 |
|---|---|---|---|
| ① 评测器/接线缺陷 | 评分器读不到 stage status、假停测 | 发现即修，不碰生产代码 | **你可以直接改** |
| ② 用例预期偏差 | 用例写错了期望 | 即改用例 | **你可以直接改** |
| ③ 确定性生产 bug | 产物结构错、门禁失效 | 根因明确也**只登记不修** | **只有用户能授权并执行** |
| ④ 模型行为 bug | 提示词、结构化输出、写作质量 | 记 8 字段根因，攒批 | 本轮不涉及（不跑真实模型） |

### 7.5 门禁

- `must_pass` 用例的 `blocked` 数 **必须 = 0**，否则整份报告判 **BLOCK**
- 一票否决项命中即 BLOCK：`D2 / P2 / R2 / C1 / T1 / T2 / T6 / K1 / K4`
- 报告末尾统计：阻断故障数 / 普通缺陷数 / A–E 各归因计数 / must_pass 阻断数 / 未验证项清单

### 7.6 已知的"能力缺失"要登记为缺陷，不是删测试项

本项目相对源库缺失三层：**鉴权与限流审计**（源库 `security/` 534 行测试）、**跨端 JSON Schema 契约层**（源库 `contracts/schemas/` 8 份 + `test_render_contract` 456 行）、**独立评测台**（源库 `eval/` 1010 文件）。这三条要在报告的"风险与未验证项"里写明，附影响面（多用户/公网部署风险、前后端契约漂移风险）。
