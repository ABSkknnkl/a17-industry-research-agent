# 白名单与行业画像补充方案

编写日期：2026-10-31。依据两份用户提供的白名单、ChainKnowledgeGraph 本地数据和当前项目实现。本文只给出补充方案，尚未改动原始资料、生产白名单、行业画像或业务代码。

## 1 建议采用的做法

先清洗公司身份和分类，再把行业归属与产业链角色分开，最后生成并审核行业画像。三份资料的用途不同，不能合成一个“名单内都对、名单外都错”的总白名单。

| 资料 | 适合补充的内容 | 不能直接证明的内容 |
|---|---|---|
| 全核心行业白名单 | 20 个研究主题的公司候选、细分角色、跨市场证券和别名线索 | 公司代码必然正确、角色已获原始披露验证、供应商与客户之间实际供货 |
| 申万行业白名单 | 按文件自述的申万指数成分/行业归属快照、证券名称代码对照、主题召回候选 | 一家公司的产业链位置、主业纯度、指数权重排名就是业务龙头排名 |
| ChainKnowledgeGraph | 历史公司名称/全称、所属行业、主营产品线索 | 当前证券状态、当前业务和营收占比、可直接使用的工业上下游关系 |

不需要首先安装 Neo4j 或重建知识图谱。项目已有 JSON/JSONL 数据与加载器，先在此基础上增加规范化数据和适配层，风险更小。数据库迁移不属于这次数据补充的必要前提。

## 3 要补的三层数据

### 3.1 公司与证券身份

为主体分配内部稳定 organization_id，为每个证券分配 security_id。上市证券采用交易所+代码识别，保留有效期；跨市场多地上市通过经过确认的主体关系挂到同一公司。未上市主体也可有 organization_id，但不能虚构证券。

建议字段：organization_id、规范公司名、历史名/简称、证券列表、主体类型、identity_status、来源行引用、源文件哈希、源声明日期、核对日期。identity_status 至少区分待核对、已确认、冲突；身份确认不自动确认业务角色。

核心名单现在按公司名去重，只适合作为输入线索；不可继续把名字当唯一身份。也不可把同集团母子公司、品牌与运营主体、ADR 与普通股不加核实地合并。

### 3.2 分类归属与研究主题映射

分别保留三套命名空间：

1. 申万文件的分类/指数节点及父子关系，例如 801010 等代码。
2. 历史图谱的行业节点，例如 110000 等代码；不假定与前者代码相同。
3. 项目研究主题，例如人工智能、低空经济、半导体设备、笔记本电脑。

建立显式多对多映射，记录映射范围、包含条件、排除条件和审核状态。“人工智能”跨多个申万行业；“半导体/集成电路”要结合 subfield 区分芯片设计、制造、设备、材料，不能只按名字映射到一个画像。

申万成分记录保留 rank/weight，但字段名和使用说明必须体现“该成分口径下的权重排名”。它只能帮助排序检索候选，不能直接写成市场份额、营收排名或产业链龙头资格。

### 3.3 公司在具体主题中的业务角色

白名单的基本单位应是“公司 + 研究主题 + 活动/品类 + 角色 + 适用范围”，不是“公司在全系统是否白名单”这一布尔值。

建议字段包括 organization_id、theme_id、category_id、activity_key、role、原始 segment/subfield、role_status、身份核验状态、业务证据引用、适用地区/日期、审核原因。

原始 tier 保留为 source_declared_tier。公司的全局最高 tier 不能覆盖它在每个细分角色中的 tier，更不能升级为模型置信度或事实支持状态。

同一家企业可能跨行业、跨产品、同时承担不同角色，须按范围保存；一家企业在某主题是部件商，不代表在所有主题都不能作为品牌商。

下面是拟议的新数据目录，不是已创建或已被加载的功能：

## 4 白名单应如何发挥作用

建议采用分层候选与归属约束：

| 数据状态 | 允许用途 | 禁止用途 |
|---|---|---|
| 未核身份或存在代码冲突 | 进入待核对队列 | 自动进入已审核公司池，继承错误代码对应公司的业务 |
| 身份明确、只有申万归属 | 行业召回、查询公司财务、候选排序 | 仅凭分类确认是整机品牌或证明实际供货 |
| 核心名单给出角色、但无可定位原文 | 定向检索种子、画像草稿候选 | 直接变成 V2 supported 断言 |
| 角色经原始资料核验且在适用范围内 | 对应主题/品类的已审核参与者，辅助落位 | 跨主题放行、推断未核实客户关系 |
| 未出现在任何名单 | 保留未知状态，走现有证据发现 | 仅因不在名单就删除、拒绝或判为错配 |

是否纳入财务研究样本与是否适合某张产业链图的品牌位，必须分开。财务查询依赖合法实体和研究目标，不应再与业务龙头评分、白名单排名绑定，避免重复此前财务任务被错过滤的问题。

## 5 行业画像如何补

### 5.1 先统一视角，再映射环节

核心名单把贵州茅台、五粮液放在“下游”；当前白酒画像将品牌活动放在 midstream。不能直接把下游→downstream 全局替换，须按该研究主题的活动定义映射。

白酒可区分酿造原料、包材、内部酿造工序、品牌产品、流通渠道、消费场景和第三方服务。品牌商不能因为供应链还有上游就变成下游“消费者”；也不能在每个厂内工序都填一遍品牌名。

模板字段至少包括：主题和别名、视角/颗粒度/地域、产品类别、活动、允许角色、默认组织方式、展示政策、检索词、排除范围、版本与复核时间、来源依据。

白名单缺失的制造工艺、内部/外包组织方式、应用场景、认证服务等，不能由公司名和 subfield 自动推断为已审核事实，须作为草稿缺口补资料。

### 5.2 当前两条画像路径分别处理

| 路径 | 当前情况 | 补充方式 |
|---|---|---|
| `chart-generator/chart_profiles/` | 23 个专用画像及通用画像；旧加载器按有序关键词首个命中 | 增加/修订主题映射与候选，保持原画像行为，防止泛词吞掉细主题 |
| `chain-research/chain_research/profile_data/` | notebook、liquor 两份，当前为 draft；profiles.py 显式注册这两个 ID | 按 IndustryProfile 严格结构编写新主题，并更新注册/解析与测试；不能只加 JSON 就认为运行会用 |

旧画像包含 leading_brand、leading_upstream 等公司列表，新 IndustryProfile 的核心是 categories 和 activities，没有可随意添加的公司白名单字段。公司角色数据应在独立主数据层维护，通过检索种子/候选接口送给研究流程，不往严格画像对象里强塞 companies。

旧 validate_profile 还会拒绝 leading_brand 与 leading_upstream 重叠。真实多角色公司需要范围化表达；若现有旧结构无法无损表达，不得通过关闭校验硬塞两边，应列为需要确认的契约扩展。

### 5.3 推荐扩充批次

先做已有画像的白酒，再做光伏、锂电池/储能、半导体分支，随后覆盖其余主题。这个顺序优先验证已有路径、数据冲突和分类拆分，不按公司数量一次性发布全部画像。

- 白酒：可复用现有两套结构，验证品牌/渠道/包装角色映射，不把上游包材厂当作白酒品牌。
- 光伏：先隔离润阳股份、美科股份两条身份冲突，再细分硅料、硅片、电池片、组件、设备与运营。
- 锂电池/储能：共用或重叠企业按产品和活动拆开，不能把锂电池、储能系统、整车视为同一个画像。
- 半导体：将原“半导体/集成电路”角色映射到芯片、设备、材料等主题；指数行业相同不代表角色相同。

20 个主题不是必须一一生成 20 份画像。已有 23 个旧画像与这 20 个主题存在拆分、交叉和缺口，需输出逐主题映射表，分别标记复用、扩展、拆分和新增。

## 6 接入现有代码的方向

以下为后续实施定位，不是本轮已经执行的修改：

| 文件/模块 | 应承担的工作 | 保留边界 |
|---|---|---|
| 拟新增离线导入/校验脚本 | 原文件解析、代码规范化、冲突输出、发布候选差异 | 不直接覆盖生产白名单和旧 KB；不调用模型自动洗掉冲突 |
| `chart_generator/chain_kb.py` | 通过适配读取已审核身份/别名和历史主营线索；逐步减少仅按名称合并 | 保持 missing/unknown 不构成删除依据；不启用未经审核的关系表 |
| `chart_generator/chain_profile.py`、`chain_loader.py` | 旧画像内容与主题映射、注册、结构校验 | 不把所有名单成员塞进 known_company_names 作为全局豁免 |
| `chart_generator/chain_topology.py` | 按主题/品类/角色消费已审核归属结果 | 不允许“白名单命中”绕过范围和角色；不据缺失直接删名 |
| `chain_research/profiles.py`、`profile_data/` | 新画像注册与精确范围解析 | draft 不升级成 reviewed；explore 和专用画像策略仍区分 |
| `chain_research/service.py` | 在公司检索阶段注入有界、分活动候选种子，沿原流程取证验证 | 不把导入名单直接写成最终 supported 关系；不增加无界检索预算 |
| `chain_research/models.py` | 现有 IndustryProfile、ChainEvidence、ChainAssertion 约束 | 有源文件说明不等于有原文证据；不降低 supported 验证要求 |

当前 V2 研究先解析画像、建立活动，再安排检索、抽取与验证。候选种子适合在检索规划时进入各活动，而不是绕过检索直接进入最终图。原始材料中没有客户证据时，只能表达公司提供某产品/参与某活动，不能生成公司之间 supplies_to 关系。

旧 topology 当前对画像已知名存在豁免。因此这次核心名单只能以经核身份、经核角色、限定主题的结果进入旧画像；不能把 591 个公司名全部追加到豁免集合，否则错误角色也会绕过 KB 检查。

## 7 分阶段产出与验收

### 第一步 数据清洗和冲突报告

产出原始快照清单、主体/证券候选、14 条名称差异、2 条 A 股未命中、5 条 market 缺失和 11 个计数差异。先核对三条严重代码冲突，保留人工处理记录，不在原文件上静默改值。

验收：每条源记录均被计入“接受候选、待审核、冲突或明确拒绝”之一，没有静默丢弃；原始文件哈希不变；同一输入重复导入不产生重复记录。

### 第二步 主题和角色映射

产出 20 个主题到两套画像与申万分类的映射表，以及原始 segment/subfield 到产品类别/活动/角色的待审映射。保留多角色，不依据指数权重升级角色。

验收：每条角色都有主题范围；无法映射则 unresolved，不能塞进“其他”后自动通过；白酒品牌与渠道、半导体品牌与部件、跨行业同名角色有正反例。

### 第三步 小批画像和候选接入

先发布经审核的白酒画像和对应候选，再按批次扩展。旧画像和 V2 画像分别通过各自加载器；新画像带版本、来源、范围和复核日期。缺证据的公司角色仍只作检索种子。

验收：明确区分“文件能解析、运行能选中、名单能召回、角色能正确落位、事实有证据”五项，不能只检查 JSON 合法。注册范围不冲突，泛主题不覆盖细主题。

### 第四步 回归后切换发布

离线回归至少覆盖：同代码不同名不误合并；多地上市不重复主体；BJ 不被沪深名单错杀；供应商不进品牌位；未知公司不因缺名单被删除；草稿名单不能变 supported；真实多角色不被全局单一标签覆盖；工艺卡不被强行填企业；名单不能制造客户供货边。

保留已有产业链金标准和单元测试，新增本次冲突/角色映射夹具。比较旧新结果的身份解析、角色正确率和误删情况，不能只追求 KB 命中率提升。真实运行验证白酒、光伏、锂电池/储能、半导体样本，预算维持有界。

发布 manifest 记录三份源数据版本/哈希、画像版本、审核范围和差异。新 run 固定使用发布版本，旧 run 保持原版可追溯；回退切换发布引用，不删除历史数据。

## 8 实施边界与停止条件

本次建议先完成离线数据清洗与映射审阅，再接运行路径。不要把它混入之前 5 个严重 Bug 修复包，也不要以补画像替代修复数据丢失或状态放行缺陷。

沿用用户要求：实际实施中如果发现根因/数据语义与方案明显不同、必须修改计划外模块、需要架构重构或破坏既有契约，立即停止后续改动。报告具体差异、已确认原因、受影响文件/数据与可选方向，等用户明确确认后再继续。不得为完成导入而关闭身份、角色或证据校验。
